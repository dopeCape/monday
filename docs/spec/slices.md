# Ordered slices

Each slice is sized to one agent session, ends shippable on its own, and is gated by typecheck, module tests and the smoke (ADR 0009). Order follows the modules so every slice has what it needs. "Done when" is the test a reviewer runs.

## Phase 0: foundation

1. **Monorepo and packages.** Bun workspaces, `apps/desktop` from the existing scaffold, `apps/server` with the four entrypoints as stubs, `packages/shared` with the domain types from `CONTEXT.md`, `packages/ui` from `design/`. Done when: `bun run typecheck` passes and the desktop app renders the Stream preset from `packages/ui` with fixture data.
2. **Settings schema and config file.** Schema in `packages/shared`, TOML parser with comment-preserving edit, precedence and pinning per ADR 0001, Rust watcher, Shell reads knobs from it. Done when: editing `monday.toml` changes the palette live and the Appearance page shows the key as pinned.
3. **Server core.** Hono app, Postgres via drizzle, migrations, `jobs` table with leases and the in-process kicker, heartbeats, `/health` and `/capabilities`, embedded Postgres started by the Sidecar, per-launch token. Done when: the Sidecar boots from Tauri, creates the database, and the client pairs on loopback.
4. **Encryption.** Envelope keys, root key generation and recovery file, `store_content` seam that every body-derived write goes through. Done when: a message written through Mailstore is unreadable in `psql` and readable through the API.

## Phase 1: mail

5. **Providers: JMAP and IMAP.** Sync (state strings, QRESYNC or CONDSTORE tiers), send (EmailSubmission, SMTP), labels both ways, IDLE and EventSource in the Sidecar, polling fallbacks. Fake Provider with recorded mailboxes for tests. Done when: a Fastmail account and a Dovecot account sync end to end and the nightly contract test passes.
6. **Store and Changes feed.** SQLite schema via rusqlite commands, live queries, `/changes` with WebSocket wake, Outbox with intent replay and last-writer-wins. Done when: archive while offline replays on reconnect and the row never flickers.
7. **Inbox screen.** The stream and split layouts from `inbox.md` over the Store: rows, sections (deterministic rules only at this point), actions with native or emulated semantics, snooze Jobs, undo toasts, three keymaps, first-sync progress. Done when: the smoke screenshots every preset, density and theme against baselines.
8. **Reader and compose.** Thread view, collapsed history, attachments as encrypted blobs, drafts server-owned and mirrored, send as a scheduled Job with the Undo bar, send later, reply-all rule, rich text editor with plain-text alternative. Done when: a reply drafted offline sends 30 seconds after reconnect and appears in Fastmail's Sent.
9. **Providers: Gmail and Graph.** OAuth wizards from ADR 0008 with live-validated paste, Pub/Sub pull, history.list, Graph delta and webhooks (Cloud only), XOAUTH2 for their IMAP path. Done when: both nightly contract tests pass and the wizard completes in the target time on a fresh Google project.
10. **Search and palette.** FTS5 over the Cache, operator parser, pre-warm Job, headers index on the Server, results view, the single palette input. Done when: results render under 50 ms on a 50,000 thread fixture.

## Phase 2: intelligence and agent

11. **Hosted runtime and Meter.** LangChain providers, Roles, task-to-Role map as Settings, Meter rows, key storage per device and the share switch. Done when: a Brief for a fixture thread is produced by Haiku 4.5 and appears in the Meter with a cost estimate.
12. **Routing and sections.** Predicates, the classify call, thresholds, Needs a decision, corrections to Examples and Predicates, two-stage sub-groups, re-run with preview, Section rules, brief policy. Routing page from the mock. Done when: the fixture mailbox routes into the expected groups with the expected confidences and a correction changes the Predicate.
13. **Briefs.** Background computation under the brief policy, staleness, action chips as tool calls. Done when: opening a needs-reply thread shows a Brief that was computed before open, and a newsletter shows none until opened.
14. **Agent host and tool server.** The MCP tool server with tiers and approvals inside, Activity log, Sessions, LangGraph loop with Postgres checkpoints and interrupts, composer UI from `agent-composer.md` in bottom-bar mode. Done when: "archive every newsletter older than a week" previews above 10, applies, and Undo restores them, all through the Hosted runtime.
15. **Local runtimes.** Claude Code, Codex and OpenCode adapters behind AgentSession, detection, built-in tools stripped, Developer mode with its warning, runtime switch mid-Session. Done when: the same instruction as slice 14 works through the user's installed Claude Code and the Activity log shows identical entries.
16. **Workflows.** JSON schema, step runner on Jobs, triggers, built-in steps and the five integrations, agentic step via LangGraph with Budget, Placement, Dry run, Standing approvals, failure policy, versions, the Workflows page. Done when: the "Candidate intake" workflow from the mock runs on a fixture arrival, pauses at Slack without a Standing approval, and completes after one.
17. **Settings screens.** Every section of `settings.md` rendered from the schema, Devices and pairing UI, Activity log view, Meter view. Done when: no settings control exists outside the schema and the Agent can change any of them.

## Phase 3: calendar, external, onboarding

18. **Calendar.** Provider calendar operations from research 6, Local calendar and iMIP for IMAP, Week, Day, Agenda and Month, Today panel, invite bar, the scheduling tool with the approval card, 5 minute polling and Cloud webhooks, notifications. Done when: "set up a call with Aoife Thursday 15:00" creates one event on Google with a Meet link and Google sends the invite, not monday.
19. **External MCP.** `/mcp` on the Cloud and loopback on the Sidecar, `monday mcp` launcher, keys from Settings, OAuth 2.1 with the consent page, scope filtering, approvals routed to the owner's client, rate limits. Done when: a Claude Code session outside monday reads the inbox with a read key and is refused a send.
20. **Onboarding.** The conversation from `onboarding.md`, proposal lists with move counts, catalog Workflows with Dry runs, "set me up" rerun. Done when: a fresh Fastmail account ends onboarding with approved Groups and one enabled Workflow inside 5 minutes.
21. **Cloud modes and upgrade.** Vercel and Netlify entrypoints, kickers, pooled Postgres, capability flags, the three upgrade cards with Deploy buttons, pg_dump migration and re-pairing, the "both" failover with heartbeats. Done when: a Sidecar-only install upgrades to Vercel, the laptop closes, and a scheduled send still goes out.

## Phase 4: ship

22. **Distribution.** CI matrix for the Bun server and embedded Postgres per target, Windows exe signing, Tauri bundles for DMG, NSIS, AppImage, deb, rpm, updater with minisign, Homebrew cask, winget, Flatpak, AUR, Nix flake, COPR, apt repo, standalone server download and container image. Done when: a release tag produces every artifact and the updater moves a previous build forward on all three platforms.
23. **Release readiness.** Rename per issue 20, provider credentials per issue 19 wired into nightly contract tests, docs site with the self-host guides, the 5 minute install measured on a clean machine per platform. Done when: the measured install times are recorded in the README and under target.

## Phase 5: judgments (ADR 0012)

24. **Judge seam and TypeSafe.** The `judge` seam on the Hosted runtime, the TypeSafe provider with retries and fallback, its key under the envelope with a share switch, Meter lines, Settings, live key validation, onboarding's runtime step with the three cards, the TypeSafe card in Settings › AI. Done when: a TypeSafe key pasted in onboarding is validated, stored, shared, and a Judgment on a fixture Thread appears in the Meter under `judge.route`.
25. **Judgments on arrival.** Routing on Choice with confidence and Examples in the state, Needs a decision from confidence, the arrival request (brief policy as a Score, needs reply, waiting, newsletter, automated, chips, urgency) stored per Thread and carried on the feed, Sections judged, the brief policy reading the score. Done when: the fixture mailbox routes and sections on TypeSafe with the expected confidences, a newsletter gets no Brief, the term sheet gets one before open, and the same run on the language model path gives the same placements.
26. **Sections, Groups and actions the user defines.** User-defined Sections with sentence, conditions, Judgment and placement; custom actions per Group or Section; the Agent's organization tools; the nav and the stream rendering every Group, Sub-group and placed Section live; the reader toolbar and chips rendering custom actions with their Tiers; the Routing page editing all of it. Done when: "put newsletters in a folder called Reading and give invoice threads a forward-to-accounting button" creates the Section and the action from one turn, both show at once, the action asks before it forwards, and Undo removes both.
27. **Typed sentences everywhere.** The palette answers a typed sentence through one Judgment request with confidence-gated Tiers, Workflow `judged` conditions and triggers with Dry-run probabilities, guardrails on bodies entering a turn, Brief verification. Done when: "set up a call with Aoife Thursday 15:00" typed in the palette opens the scheduling card without a Session, and a Workflow condition "the message is a complaint" gates a Run in a Dry run.

## Phase 6: Signals and what they power (ADR 0014)

In the order the user approved: the foundation, then Recommended actions, Templates, Boards, then the smaller four. Specs: `signals.md`, `actions.md`, `templates.md`, `views.md` (Boards until ADR 0016), `signal-features.md`, `meetings.md`.

M1. **Meetings from mail, ahead of the Signal store.** Ships before 28 to 35 and needs only 18 and 27. The meeting request (one Thread, every meeting question, one request, TypeSafe or the language model's prompt path) on arrival at `automate` as a `meeting` Job and on open otherwise, stored in `thread_meetings` with the Message it read and carried on the feed as a `meeting` change; candidate spans, date parts resolved in code across zones and DST, free and busy by `find_free_time`'s rules, the slot search; the chips in the reader and on row hover (Offer times, Schedule with `schedule_event`'s card, Works for me, Suggest another time, Pick a time in the event editor); the grounded reply in the user's voice; `meeting_options` for the agent; the Settings and words. Done when: acceptance criteria 1 to 11 of `meetings.md` pass.

28. **Measure the batching.** `POST /intelligence/eval/batching` behind `ai.judge.eval_enabled`, the sampler (newest, random recent, random older, labelled Threads), the three arms with two repeats, the comparison, `scripts/judge-batching-eval.ts` with `--fake`, the report format. No product behaviour changes. Done when: the script against the fake judge writes every table in `signals.md` ("Measure first"), and the lead has run it live and committed `docs/research/judge-batching.md`.
29. **One Thread per request for the Backlog sort.** The Backlog sort asks one Thread per request with the Group Choice and speculative Sub-group Choices; `routing.backfill.batch_size` kept or retired per the report; `packBatches` removed if retired. Done when: a Backlog sort of the fixture mailbox makes one request per Thread and places every Thread as before, and a Sub-group placement costs one request.
30. **The Signal store.** `signal_defs`, `signal_versions`, `signal_answers`; the Signal request replacing the arrival request (shipped Signals as today, one Thread, all questions, split only by budget); Question versions and the stale rule; the `signals` feed change; `thread_signals` in the Cache; migration of `thread_judgments` and `section_judgments`; Sections reading Signals, `when.signals`, Waiting on you on `waiting_on_me`. Done when: every Section shows the same fixture Threads as before the migration, the old tables are gone, and a reworded question marks answers stale without emptying a Section.
31. **Backfill, rate and budget.** The `signals-backfill` Job and `signal_backfills`, sharing requests with a running Backlog sort; the limiter (arrival first, 429 cooldown); the monthly background budget from the Meter; the confirm-above card with its estimate; progress lines. Done when: an injected 429 halves background concurrency while arrivals continue, and a spent budget pauses the walk with its reason.
32. **The new shipped Signals and Facts.** `waiting_on_me`, `personal`, `has_deadline` with the date parts and code assembly, `money_involved` with amount candidates and direction, `frustrated`, `owner_promised`, `they_promised`; every Fact in the table; `lowTrust` for non-English and image-only; the Signals page and the tune tools on Signals. Done when: the fixture invoice has `deadline_at` 3 October and amount $1,315.50 from the fake judge's picks, and the Store answers a money-and-deadline query offline.
33. **Groups and Custom actions in the one request.** The Group Choice and Sub-group Choices ride in the arrival Signal request; Section and Custom action statements become owned Signals; the Unsure band and hysteresis in Sections. Done when: a fixture arrival costs one judge request for routing, Sections, Briefs policy and Custom actions together.
34. **Recommended actions I.** The catalog's fit Signals; Reply, Archive, Snooze (with its arguments), Forward and Hand to someone (with the recipient Choice); chips in the reader and on row hover; keys; replacing `CHIP_NAMES` and the Brief's action choice; thresholds as Settings. Needs 32. Done when: acceptance criteria 4, 7 and 8 of `actions.md` pass.
M2. **Meetings onto Signals.** Needs 30, 32 and 34. The meeting Nouls, the length Choice and the `meeting_*` date parts become shipped action Signals in the one Signal request, the gate a FactGate, `thread_meetings` readings migrate into `signal_answers` and the table goes, the sender's offset becomes a Fact, the chips join the Recommended action row with its limits, keys and learning. Done when: M1's acceptance criteria still pass with the meeting questions riding in the Signal request and no second request per Thread.
35. **Recommended actions II and learning.** RSVP, Add to calendar, Pay or file (with link-domain checks), Unsubscribe (RFC 8058 and mailto, the new `list.unsubscribe` tool), Track a package, Run a Workflow; `recommendation_events`, threshold learning, muted senders. Done when: acceptance criteria 1, 2, 3, 5 and 6 of `actions.md` pass.
36. **Templates I.** `templates` rows sealed and synced, the Cache mirror, built-ins, the picker and trigger, Placeholders with types, filling by span selection, Send blocking, Use in every account, Export and Import. Done when: acceptance criteria 1, 2, 6 and 7 of `templates.md` pass.
37. **Templates II.** Suggestions while typing (two requests with the gate and the reject-all floor), the on-open suggestion that names the Reply chip, writing a Template from examples with the duplicate Score, the Agent's Template tools. Needs 34 for the chip name. Done when: acceptance criteria 3 and 4 of `templates.md` pass.

## Phase 7: Views (ADR 0016)

Boards generalize to Views (`views.md`): Fields per Thread, Extractions that select instead of generate, code-only queries, the Block catalog and actions on items. Each slice keeps every Board acceptance criterion passing.

45. **Views I: the rename and the document.** Board becomes View everywhere: migration 0031 renames the tables and keeps every row, the feed kind, the Signal owner kind, `boards.*` Settings to `views.*` with config file aliases and the saved values moved, the tools with the old names as aliases, the nav heading. The View schema in `packages/shared` (`view/`): Fields, conditions with Extraction and Lane tests, queries (filters, dedupe, group by with time buckets, aggregates with money per currency, sort, limit, period and compare), the Block catalog and the actions catalog, validation; a Board document read as a View with one Block. Done when: acceptance criteria 1 to 9 of `views.md` pass and the query engine's tests cover every aggregate, bucket, dedupe and the three-valued filter.
46. **Views II: Extractions.** Candidate finders for every `find` kind in the Facts module, each Extraction a Choice Signal owned by the View with per-Thread options and a gate, picks normalized by code and kept sealed, the draft's Extractions riding in the one Signal request of the test with their picks returned, the `view_values` feed change, `GET /views/:id/values` and `POST /views/values`, the Cache's `view_values`. Done when: acceptance criteria 14 and 15 pass and the fixture orders' totals and order numbers come from the fake judge's picks.
47. **Views III: Blocks on the Device.** Every Block drawn from the View's queries over the Cache, charts in plain SVG in `packages/ui`, the grid widths, the View screen, the card's preview of each Block, the `view` Panel. Done when: acceptance criteria 10 to 13 render from the fixture mailbox.
48. **Views IV: authoring and actions.** The drafting prompt with the catalog, the Field vocabulary and good and bad questions; `create_view`, `revise_view`, `update_view`, `delete_view`, `list_views`; Wrong value corrections as Examples; the actions catalog and its runner over the Custom action, Recommended action and Workflow paths. Done when: acceptance criteria 16 and 17 pass. Deferred: the Workflow trigger on entering a Lane.
49. **Views V: the test on the right Threads.** From a real session ("my orders with spend per month" read nothing): the scope's exact facts (folder, dates, senders, recipients) in SQL on the Server and the Device, over expression indexes on the sender (migration 0032), so the test, the View and its count see the newest Threads in scope across the whole mailbox; a whole address in `from_any` and `to_any`; a revision keeps the tried Threads its (perhaps changed) scope still admits and fills the rest with the newest of the new scope; the test prefers Threads whose text holds the values its Blocks add up, found by code without the judge, and says how many it passed over; rupees written "Rs."; the item finder finds the products on real receipts (Amazon.in, Myntra, H&M shapes) and never a bare count or price; the create and revise results carry each Field's coverage over every tried Thread (resolved, none, below the floor, no candidates, capped), the senders and example values, and the read-only `inspect_view_thread` explains one Thread; many values per Extraction (a Noul per candidate, kept by threshold, capped, sums and counts over every value), a View's grain (`item`, `message`) with per-row Signals (`each`), the Cache's `view_values.items`, and a Message Row opening its Thread on that Message; `subject_any` over the clear subject prefix in SQL on both sides (a full-search `query` scope deferred); the drafting prompt with many values, grains, subject words, the coverage words and two worked examples that validate as written. Done when: acceptance criteria 18 to 20 pass.
