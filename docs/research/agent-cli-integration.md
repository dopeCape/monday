# Driving Claude Code, Codex and OpenCode from the monday client

Research for issue #2 (part of the wayfinder map #1). Verified against primary sources on 2026-09-16. Versions checked: Claude Code 2.1.273 with Claude Agent SDK 0.3.273, Codex CLI 0.154.0, OpenCode 1.18.31, Agent Client Protocol v1 (schema 1.21.0, TypeScript SDK 1.4.0).

## Summary

All three CLIs can be driven programmatically from a local process, all three stream events, all three can be handed monday's own tools, and all three can route approvals back to a host UI. But they do it through three different native surfaces, and only OpenCode speaks the Agent Client Protocol (ACP) natively; Claude Code and Codex reach ACP only through adapters maintained by Zed and JetBrains under the `agentclientprotocol` org, not by Anthropic or OpenAI.

The one mechanism that all three CLIs (and ACP) share is MCP: every harness can connect to an MCP server over stdio or streamable HTTP and call its tools. Nothing else is common: session APIs, event shapes, approval requests and auth all differ.

Three facts change the product assumptions in `design/`:

1. **"Cost: your CLI subscription" is only clean for Codex.** OpenAI's app-server exposes ChatGPT login and reports the plan type, and no policy forbids third-party clients. Anthropic's docs say third-party developers may not offer claude.ai login or route requests through Pro/Max credentials, and that products built on the Agent SDK should use API keys; the same page says an end user may sign in to the *unmodified* Claude Code binary with their own subscription, including when a platform hosts it. So monday must spawn the user's own installed `claude`, never run or store the login itself, and should treat subscription use as user-chosen and possibly subject to Anthropic approval. OpenCode removed its Anthropic OAuth plugin in 1.3.0 because "Anthropic explicitly prohibits this", so OpenCode plus Claude means an Anthropic API key (ChatGPT, Copilot and other provider logins still work in OpenCode).
2. **Built-in tools can be stripped so the agent only sees monday's tools** in Claude Code (`tools: []`) and OpenCode (`permission: { "*": "deny" }` plus per-agent `tools`), and mostly in Codex (`features.shell_tool=false`, `web_search="disabled"`, `tools.view_image=false`, read-only sandbox; `apply_patch` has no off switch, but a read-only sandbox makes writes fail). ACP has no such knob in the spec.
3. **Codex's headless `codex exec` and the `@openai/codex-sdk` have no approval hook at all**; approvals only exist on the app-server JSON-RPC surface. So monday must use `codex app-server`, which OpenAI labels experimental but also calls "the first-class integration method we maintain moving forward" and uses for its own VS Code extension and desktop app.

## Recommendation

**Build a common `AgentSession` interface with one thin adapter per CLI over each CLI's native surface, and expose monday's tools to every adapter through a single MCP server.** Do not make ACP the only path.

Concretely:

- **One MCP server for monday's tools** (`search_mail`, `read_thread`, `draft`, `send`, `archive`, `change_setting`, `create_workflow`, ...). Serve it from the client-local process over streamable HTTP on loopback (all three CLIs support it) with a stdio launcher as fallback. This is also what an ACP client would pass in `mcpServers`, and what the API-key provider layer (#14) can call directly, so the tool surface is written once.
- **Approval lives in the tool, not in the harness.** For monday's own tools, the MCP implementation asks the UI before executing anything that leaves the mailbox (send, delete, unsubscribe) and only then returns. That makes the approval model in #9 identical across Claude Code, Codex, OpenCode, ACP and API-key models. The CLI permission systems are used for one thing only: locking down the CLI's built-in tools (no Bash, no file edits, no web fetch) and denying anything unexpected.
- **Per-CLI adapters** handle what is genuinely different: process spawn and detection, session create/resume/fork, prompt and steer, cancel, event normalisation into monday's transcript model, auth status, and usage reporting.
  - Claude Code: spawn the user's installed `claude` in `-p` mode with `--input-format stream-json --output-format stream-json`, either through `@anthropic-ai/claude-agent-sdk` with `pathToClaudeCodeExecutable` pointed at the detected binary, or by speaking the stream-json protocol directly. Use `tools: []`, `settingSources: []`, `mcpServers` pointing at monday's server, `canUseTool` for the harness-level gate.
  - Codex: spawn `codex app-server` (stdio JSON-RPC, omit the `jsonrpc` field), `initialize` with `clientInfo.name = "monday"`, `thread/start` with per-thread `config` overrides (monday's `mcp_servers`, `features.shell_tool=false`, `web_search="disabled"`, read-only sandbox, `approval_policy` never for host tools since approval happens inside the tool). Answer `item/*/requestApproval` and `mcpServer/elicitation/request`.
  - OpenCode: spawn `opencode serve --port 0 --hostname 127.0.0.1` with `OPENCODE_SERVER_PASSWORD` and `OPENCODE_CONFIG_CONTENT` (permission ruleset, monday's `mcp` entry, a `monday` agent with built-ins off), talk to it with `@opencode-ai/sdk/v2`, stream `/event`, reply to `permission.asked` and `question.asked`.
- **ACP as a fourth, optional adapter later**, not as the foundation. It costs little once the interface exists, it would open monday to Gemini CLI, Copilot CLI, Goose and the rest of the ACP registry, and it is a fallback if a native surface breaks. It should not be the primary path because the stable spec has no way to disable built-in tools, no host-executed tools other than fs and terminal, only session-level usage, approval options limited to allow/reject with no input editing, and the Claude and Codex adapters lag the CLIs and would run a second copy of the agent via `npx` (Node 22) instead of the user's installed binary, which matters for the Anthropic policy above and for the design's "detected on this machine, no extra setup" promise.

Where the adapters run: the CLIs live on the user's machine, so the adapter host must be client-local. Since all three surfaces are JSON over stdio or HTTP, a TypeScript process is the natural host; whether that is the local sync-server sidecar or a small bundled "agent host" is a decision for the architecture ticket. Note the Bun caveats below if that process is compiled with `bun build --compile`.

## Claude Code (Claude Agent SDK and `claude -p`)

Sources: https://code.claude.com/docs/en/agent-sdk/overview, https://code.claude.com/docs/en/headless, https://code.claude.com/docs/en/agent-sdk/custom-tools, https://code.claude.com/docs/en/agent-sdk/permissions, https://code.claude.com/docs/en/agent-sdk/user-input, https://code.claude.com/docs/en/agent-sdk/sessions, https://code.claude.com/docs/en/agent-sdk/streaming-output, https://code.claude.com/docs/en/authentication, https://code.claude.com/docs/en/legal-and-compliance, https://code.claude.com/docs/en/cli-reference, https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/latest, https://raw.githubusercontent.com/anthropics/claude-agent-sdk-typescript/main/CHANGELOG.md

**Surfaces.** The docs now describe one engine with three doors: the TypeScript SDK `@anthropic-ai/claude-agent-sdk` (0.3.273, Node 18+), the Python SDK `claude-agent-sdk` (0.2.153), and the CLI in print mode (`claude -p`). "To drive the same agent loop from another language, run the CLI as a subprocess with the `-p` flag." Both SDKs bundle a native Claude Code binary via per-platform optional packages and spawn it; `pathToClaudeCodeExecutable` (TS) or `cli_path` (Python) points the SDK at a separately installed binary instead. The old "Claude Code SDK" name and `@anthropic-ai/claude-code` as an SDK are deprecated.

**Session lifecycle.** `query({ prompt, options })` with `resume: <id>`, `continue: true`, `forkSession: true`, `sessionId: <uuid>`, `persistSession: false` (no disk state). Multi-turn is done by passing an `AsyncIterable<SDKUserMessage>` as the prompt ("streaming input mode is the preferred way"); each turn emits its own `result`. `Query.interrupt()` and an `abortController` cancel; the result carries `terminal_reason` such as `aborted_streaming`. Transcripts live at `~/.claude/projects/<cwd-slug>/<session-id>.jsonl`; the docs say the entry format "is internal to Claude Code and changes between versions". `CLAUDE_CONFIG_DIR` relocates all state and `CLAUDE_CODE_PROJECT_DIR_NAME` names the project dir, which the docs describe as suited to "a host that embeds Claude Code". The experimental V2 `createSession` API was removed in 0.3.142.

**Streaming.** Message union includes `system` (`init` carries `session_id`, `tools`, `mcp_servers` with status, `model`, `permissionMode`, `apiKeySource`, `capabilities`), `assistant` (one message per completed content block; tool calls are `tool_use` blocks with `id`, `name`, `input`), `user` (tool results as `tool_result` blocks, `tool_use_result`), `stream_event` (raw API deltas, only with `includePartialMessages: true`, main session only), `result` (`subtype`, `total_cost_usd`, `usage`, `modelUsage`, `permission_denials`, `structured_output`, `session_id`), plus `api_retry`, `permission_denied`, compaction boundaries. Subagent messages carry `parent_tool_use_id`.

**Custom tools.** In-process: `tool(name, description, zodShape, handler)` and `createSdkMcpServer({ name, tools })`, passed in `mcpServers`; tools are named `mcp__<server>__<tool>`. External: `McpStdioServerConfig`, `McpSSEServerConfig`, `McpHttpServerConfig` (`url`, `headers`). The SDK does not run OAuth for MCP servers. Restricting built-ins: "`tools: []` ... All built-ins are removed. Claude can only use your MCP tools"; a bare name in `disallowedTools` removes that tool; `--restricted` removes command and code-running tools and WebFetch; `settingSources: []` stops loading the user's `~/.claude/settings.json`, CLAUDE.md, hooks and `.mcp.json` (managed policy settings, `~/.claude.json`, auto memory and claude.ai MCP connectors still load; `strictMcpConfig: true` or `ENABLE_CLAUDEAI_MCP_SERVERS=false` suppress the connectors). `systemPrompt` accepts a custom string or the `claude_code` preset with `append`. `agents`, `hooks` (about 30 TS events including `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Elicitation`), `maxTurns`, `maxBudgetUsd`, `outputFormat` (JSON schema), `model`, `effort` are all options.

**Permissions.** Evaluation order: hooks, deny rules, ask rules, permission mode, allow rules, then `canUseTool`. `canUseTool(toolName, input, { signal, suggestions })` returns `{ behavior: 'allow', updatedInput?, updatedPermissions? }` or `{ behavior: 'deny', message, interrupt? }`; "The callback can stay pending indefinitely." `AskUserQuestion` also arrives through `canUseTool`. `permissionMode` values: `default`, `acceptEdits`, `bypassPermissions` (needs `allowDangerouslySkipPermissions`), `plan`, `dontAsk`, `auto`; changeable at runtime with `setPermissionMode`. When driving `claude -p` directly, `--permission-prompt-tool <mcp_tool>` routes prompts to an MCP tool the host serves; `--permission-prompts none` (2.1.259+) denies anything that would prompt.

**Auth.** Credential precedence: cloud provider env (`CLAUDE_CODE_USE_BEDROCK`, `_VERTEX`, `_FOUNDRY`), `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`, one year, model requests only), then "Subscription OAuth credentials from /login. This is the default for Claude Pro, Max, Team, and Enterprise users." Credentials sit in the macOS Keychain or `~/.claude/.credentials.json`. `--bare` (recommended for scripted use, planned default for `-p`) "never reads OAuth credentials or the system keychain". `system/init.apiKeySource === 'none'` means OAuth or a third-party provider is in use, which lets monday show the right cost line.

Policy, quoted from the legal page: OAuth "is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications." "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication ... Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens; sign-in to a Claude account must complete through Anthropic's own flow." And: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code." Products that run Claude Code must not modify the binary or "remove, disable, or restrict any authentication method built into it", and "Each end user must authenticate with their own Anthropic API key, Claude subscription plan credentials, or 3P inference provider credential." The Agent SDK overview adds: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." The support article https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan says the planned move of SDK, `claude -p` and third-party app usage onto a separate monthly credit is paused and such usage "still draw[s] from your subscription's usage limits".

**Platforms.** macOS 13+, Windows 10 1809+ native (Git Bash optional, no sandbox natively), Ubuntu 20.04+/Debian 10+/Alpine 3.19+; binaries for linux, darwin and win32 on x64 and arm64. Bun runs the SDK; a `bun build --compile` binary needs `extractFromBunfs` (SDK 0.3.144+) or an external `pathToClaudeCodeExecutable`, which monday will have anyway.

**Stability.** 0.x with the patch number locked to the CLI version and a release for almost every CLI release. 2026 breaking changes: V2 session API removed (0.3.142), MCP servers connect in the background by default, Task tools replaced TodoWrite, `options.env` replaces the subprocess environment (0.2.113). The transcript format is explicitly unstable. `claude-agent-acp` 0.78.0 depends on SDK 0.3.270, so the adapter lags by a few days.

**Cannot.** Offer subscription login inside monday or hold OAuth tokens; use `--bare` with a subscription; register skills programmatically; stream structured output (only in the final result); `--betas` is API-key only; cost figures are estimates ("Do not bill end users ... from these fields").

## Codex (`codex app-server`, `codex exec`, `@openai/codex-sdk`)

Sources: https://learn.chatgpt.com/docs/app-server (developers.openai.com/codex redirects here), https://learn.chatgpt.com/docs/non-interactive-mode, https://learn.chatgpt.com/docs/codex-sdk, https://learn.chatgpt.com/docs/config-file/config-reference, https://learn.chatgpt.com/docs/extend/mcp, https://learn.chatgpt.com/docs/permissions, https://learn.chatgpt.com/docs/auth, https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/common.rs, https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/thread.rs, https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs, https://github.com/openai/codex/blob/main/sdk/typescript/src/exec.ts, https://github.com/openai/codex/releases/tag/rust-v0.154.0, https://openai.com/index/unlocking-the-codex-harness/

**Surfaces.** (a) `codex exec "<prompt>"` with `--json` JSONL, `--output-schema`, `--sandbox`, `--ephemeral`, `--ignore-user-config`, `codex exec resume`. (b) `codex app-server`: "the interface Codex uses to power rich clients (for example, the Codex VS Code extension). Use it when you want a deep integration inside your own product: authentication, conversation history, approvals, and streamed agent events." JSON-RPC 2.0 with the `jsonrpc` header omitted on the wire; `--listen stdio://` (default), `unix://`, `ws://` (experimental, unauthenticated by default on non-loopback), `off`. Schema and TypeScript bindings are generated per binary version with `codex app-server generate-ts`; there is no npm protocol package. (c) `@openai/codex-sdk` 0.154.0 (Node 18+, ESM only) spawns `codex exec --experimental-json` and exposes `startThread`, `resumeThread`, `run`, `runStreamed`; it is pinned exactly to the same `@openai/codex` version. (d) `codex mcp-server` was removed in 0.154.0. OpenAI's own words: "Codex App Server will be the first-class integration method we maintain moving forward ... By default, we'd recommend that clients use Codex App Server", and the SDK "supports fewer languages and a smaller surface area"; the docs say to use the SDK "if you are automating jobs or running Codex in CI".

**Session lifecycle.** `initialize` once per connection with `clientInfo` ("Use `clientInfo.name` to identify your client for the OpenAI Compliance Logs Platform"; enterprise integrations can ask to join a known-clients list) and `capabilities.experimentalApi`. `thread/start` (params include `model`, `cwd`, `approvalPolicy`, `sandbox` or experimental `permissions`, `config` map of overrides, `baseInstructions`, `developerInstructions`, `ephemeral`, `dynamicTools`), `thread/resume`, `thread/fork` (`lastTurnId`), `thread/list`, `thread/archive`, `thread/delete`, `turn/start`, `turn/steer` (append to the in-flight turn), `turn/interrupt`. One active turn per thread, many threads per process; unloaded after 30 minutes idle (configurable in 0.154). Rollouts are JSONL in `~/.codex/sessions`; `CODEX_HOME` relocates everything.

**Streaming.** Notifications `thread/started`, `turn/started`, `turn/completed` (status `completed`, `interrupted`, `failed`), `item/started`, `item/completed`, deltas `item/agentMessage/delta`, `item/commandExecution/outputDelta`, `item/reasoning/textDelta`, `item/mcpToolCall/progress`, `item/fileChange/patchUpdated`, `thread/tokenUsage/updated`, `account/rateLimits/updated`. Item types: `userMessage`, `agentMessage`, `reasoning`, `commandExecution`, `fileChange`, `mcpToolCall` (`server`, `tool`, `arguments`, `result`, `status`), `dynamicToolCall`, `webSearch`, `plan`, `contextCompaction`. `codex exec --json` and the SDK emit only whole items (`item.started`, `item.completed`, `turn.completed {usage}`), no token deltas.

**Custom tools.** MCP servers under `[mcp_servers.<id>]` in `config.toml` (stdio `command` or streamable HTTP `url` with `bearer_token_env_var`, `http_headers`), with `enabled_tools`, `disabled_tools`, `required`, `startup_timeout_sec`, `tool_timeout_sec`, `default_tools_approval_mode` (`auto`, `prompt`, `writes`, `approve`) and per-tool `approval_mode`. Any config key, including `mcp_servers.*`, can be overridden per thread via `thread/start.config`, and `config/mcpServer/reload` re-reads config. Without MCP: `dynamicTools` on `thread/start` (requires `experimentalApi: true`); the server sends `item/tool/call` to the client, the client returns content items, and the tool definitions are persisted in the rollout so `thread/resume` restores them. Not available in exec or the SDK. Built-ins: `features.shell_tool=false` removes the shell tool, `web_search="disabled"` removes web search, `tools.view_image=false`; there is no key to remove `apply_patch`, so use a read-only sandbox (or a `:read-only` permission profile). Sandbox and permission profiles "explicitly do NOT constrain: Web search tools, App connectors and MCP servers".

**Permissions.** Policies: `untrusted` (unsupported now), `on-request` (default; `on-failure` is an alias and deprecated), `granular` (experimental), `never`. App-server approvals are server-to-client requests with ids: `item/commandExecution/requestApproval` (answers `accept`, `acceptForSession`, `decline`, `cancel`, `acceptWithExecpolicyAmendment`), `item/fileChange/requestApproval`, `item/permissions/requestApproval` (grant a subset with `session` or `turn` scope), `mcpServer/elicitation/request` (form or URL), `item/tool/requestUserInput` (experimental). `codex exec` defaults to `approval_policy = never` and has no approval handler; the SDK's `approvalPolicy` option just sets that config, with no callback.

**Auth.** "Sign in with ChatGPT" (browser) or `codex login --with-api-key`; `codex login --device-auth` for headless; `~/.codex/auth.json`, or keyring via `cli_auth_credentials_store`. App-server: `account/read` returns `{type: "chatgpt", email, planType}` or `{type: "apiKey"}`; `account/login/start` with `type` `apiKey`, `chatgpt` (returns `authUrl`), `chatgptDeviceCode` (returns `verificationUrl` and `userCode`), or experimental `chatgptAuthTokens` for "host apps that already own the user's ChatGPT auth lifecycle"; `account/rateLimits/read` gives `usedPercent`, `windowDurationMins`, `resetsAt`, credits and `planType`. No written OpenAI policy against third-party clients using ChatGPT login was found; the app-server docs assume it and ask for a `clientInfo.name`. API-key use is "billed at standard API rates" and loses some ChatGPT workspace features.

**Platforms.** npm `@openai/codex` (Node 16+) with optional binaries for linux, darwin and win32 on x64 and arm64; brew cask; install scripts; native Windows with `elevated` or `unelevated` sandbox modes (Windows 11 recommended, 10 best effort); Linux sandbox uses bwrap and seccomp. Bun: the SDK uses `node:readline` and a 2026-09-15 issue (#45727) reports JSONL splitting on U+2028/U+2029 under Bun 1.4.x. Spawning `codex app-server` directly and splitting on `\n` avoids the SDK entirely.

**Stability.** The `app-server` subcommand is labelled experimental in the CLI and the docs say it is not supported "for production workloads", while the blog calls it the maintained first-class path and says the JSON-RPC surface "is designed to be backward compatible, so older clients can talk to newer servers safely". Omit `experimentalApi` to stay on the stable subset (`initialize`, `thread/*`, `turn/*`, `command/exec`, `model/list`, `fs/*`, account methods); experimental: `dynamicTools`, `permissions`, `thread/turns/list`, `thread/items/list`, `chatgptAuthTokens`, `plugin/*`. Two to three stable releases per week; 2026 removals: `codex mcp-server`, `approval_policy = untrusted`, `--full-auto` deprecated, `sandbox_mode` being replaced by permission profiles.

**Cannot.** Approvals in exec or the SDK; per-token streaming in exec or the SDK; disable `apply_patch` by config; dynamic tools without the experimental capability; run outside a git repo without `--skip-git-repo-check` (exec and SDK); analytics are off by default for app-server (good for the no-telemetry rule) but OTel export exists as opt-in.

## OpenCode (`opencode serve`, `@opencode-ai/sdk`, `opencode acp`)

Sources: https://opencode.ai/docs/server, https://opencode.ai/docs/sdk, https://opencode.ai/docs/custom-tools, https://opencode.ai/docs/plugins, https://opencode.ai/docs/mcp-servers, https://opencode.ai/docs/permissions, https://opencode.ai/docs/agents, https://opencode.ai/docs/providers, https://opencode.ai/docs/acp, https://opencode.ai/docs/cli, https://github.com/anomalyco/opencode (repo moved from `sst/opencode`; MIT), https://github.com/anomalyco/opencode/blob/dev/packages/sdk/js/src/server.ts, https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/registry.ts, https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/cli/cmd/run.ts, https://github.com/anomalyco/opencode/releases

**Surfaces.** `opencode serve --port --hostname` starts "a headless HTTP server that exposes an OpenAPI endpoint" (spec at `/doc`, OpenAPI 3.1); `--port 0` picks a free port and the process prints "opencode server listening on ...". `@opencode-ai/sdk` 1.18.31: `createOpencodeServer({ port, hostname, config })` spawns `opencode serve` with the config passed as `OPENCODE_CONFIG_CONTENT`, `createOpencodeClient({ baseUrl, directory })` connects; the root export is a frozen v1 snapshot while `@opencode-ai/sdk/v2` is regenerated from the server's OpenAPI and is what `opencode acp` itself uses. `opencode run --format json` mirrors the event stream to stdout and, without `--auto`, auto-rejects permission requests. The official desktop app is Electron and embeds the server in a utility process; the server package itself is private and not consumable as a library.

**Session lifecycle.** `POST /session` (`parentID`, `title`), `GET /session/:id`, `PATCH /session/:id` (title, metadata, `permission` ruleset), `DELETE`, `POST /session/:id/fork` (`messageID`), `/abort`, `/summarize`, `/share`, `/revert`; `POST /session/:id/message` waits for the reply, `POST /session/:id/prompt_async` returns 204; body `{ parts, model?, agent?, system?, tools?, format?, noReply? }` with `format: { type: "json_schema" }` for structured output. Requests are scoped to a project by the `x-opencode-directory` header or `?directory=`; the SDK sets it from `directory`. Many sessions per server, but one running prompt per session (`SessionBusyError`). State is SQLite at `~/.local/share/opencode/opencode.db` (WAL), overridable with `OPENCODE_DB`.

**Streaming.** `GET /event` (instance) and `GET /global/event` (all instances, enveloped with `directory`) are SSE; first event `server.connected`. Events: `message.updated`, `message.part.updated`, `message.part.delta` (`field`, `delta`), `session.updated`, `session.idle`, `session.status`, `session.error`, `permission.asked`, `permission.replied`, `question.asked`, `question.replied`, `todo.updated`, `mcp.tools.changed`, plus a newer `session.next.*` family (`text.delta`, `reasoning.delta`, `tool.called`, `tool.progress`, `tool.success`, `tool.failed`, `step.started`). Tool parts carry `status` `pending`, `running`, `completed`, `error` with `input`, `output`, `metadata`.

**Custom tools.** Three routes. (1) MCP in `opencode.json` `mcp` (`local` with `command`, `environment`; `remote` with `url`, `headers`, optional `oauth`), tools named `<server>_<tool>`, or at runtime with `POST /mcp { name, config }`; `GET /experimental/tool/ids` lists everything registered. (2) TypeScript tools in `.opencode/tools/*.ts` or `~/.config/opencode/tools/` using `tool({ description, args, execute })` from `@opencode-ai/plugin` (Zod args; context has `agent`, `sessionID`, `directory`); "If a custom tool uses the same name as a built-in tool, the custom tool takes precedence". (3) Plugins (`.opencode/plugins/` or npm) with a `tool` map and hooks `permission.ask`, `tool.execute.before/after`, `tool.definition`, `chat.message`, `chat.params`, `auth`, `provider`. Tools and plugins are discovered from disk at instance start; there is no HTTP endpoint to register a TS tool at runtime. Built-ins (`bash`, `edit`, `write`, `read`, `grep`, `glob`, `lsp`, `apply_patch`, `skill`, `todowrite`, `webfetch`, `websearch`, `question`, `task`) are turned off with `permission: { "*": "deny", ... }` or a custom agent's `tools`/`permission` map; the top-level `tools` booleans are deprecated but still honoured. The `question` tool is only registered when `OPENCODE_CLIENT` is `app`, `cli` or `desktop`, or `OPENCODE_ENABLE_QUESTION_TOOL` is set.

**Permissions.** Config `permission` with `allow`, `ask`, `deny` per tool and glob patterns ("last matching rule wins"); per-agent overrides; `OPENCODE_PERMISSION` env JSON. At runtime the server emits `permission.asked { id, sessionID, permission, patterns, metadata, always, tool }`; reply with `POST /permission/:requestID/reply { reply: "once" | "always" | "reject", message? }` (legacy `POST /session/:id/permissions/:permissionID { response }`); `always` lasts for the current server process. Questions: `question.asked` and `POST /question/:id/reply { answers }`. Plugins can decide with the `permission.ask` hook without a UI.

**Auth.** Provider credentials in `~/.local/share/opencode/auth.json`, set with `opencode auth login`, `PUT /auth/:id`, or `POST /provider/:id/oauth/authorize` + `/callback` over HTTP. OpenAI: "ChatGPT Plus/Pro" OAuth through the in-tree Codex plugin, or an API key. Anthropic: "There are plugins that allow you to use your Claude Pro/Max models with OpenCode. Anthropic explicitly prohibits this. Previous versions of OpenCode came bundled with these plugins but that is no longer the case as of 1.3.0" (release 1.3.0, 2026-03-22, "Removed anthropic oauth plugin"). GitHub Copilot, OpenCode Zen, OpenRouter, Ollama, LM Studio and 75+ providers otherwise. `OPENCODE_SERVER_PASSWORD` turns on HTTP basic auth for `serve`; without it the process warns that the server is unsecured.

**Platforms.** Bun-compiled binaries for darwin, linux (glibc, musl, baseline) and windows (x64, arm64) via npm `opencode-ai`, brew, curl, Chocolatey, Scoop, Docker; since 1.3.0 it also runs on Node. Docs still recommend WSL on Windows and several Windows ACP issues are open.

**Stability.** No documented API version or stability contract; Effect HttpApi groups self-label `0.0.1` and the permission and experimental groups are marked experimental; event types carry version suffixes (`message.updated.1`). 1.4.0 (2026-04-08) shipped a breaking data-model change in the SDK (tool diff metadata). Releases land every 2 to 5 days (120 between April and September 2026). `opencode acp` implements `initialize`, `newSession`, `loadSession`, `listSessions`, `resumeSession`, `closeSession`, `unstable_forkSession`, `setSessionConfigOption`, `prompt`, `cancel`, but pins `@agentclientprotocol/sdk` 0.21.0 (pre-1.0) and has open bugs (session/load omits `sessionId` #42442, subagent permission requests dropped #48232, MCP tools leaking across ACP sessions #40978, Windows `session/list` #49256).

**Cannot.** Register a TS tool over HTTP (only MCP); restrict tools per request (deprecated in favour of per-session `permission`); import the server as a library; run two prompts on one session; use a Claude subscription. Usage: `AssistantMessage.cost` and `tokens { input, output, reasoning, cache { read, write } }`.

## Agent Client Protocol (ACP)

Sources: https://agentclientprotocol.com/overview/introduction, https://agentclientprotocol.com/protocol/initialization, https://agentclientprotocol.com/protocol/v1/session-setup.md, https://agentclientprotocol.com/protocol/v1/prompt-turn.md, https://agentclientprotocol.com/protocol/v1/tool-calls.md, https://agentclientprotocol.com/protocol/v1/authentication.md, https://agentclientprotocol.com/protocol/v1/transports.md, https://agentclientprotocol.com/rfds/updates.md, https://agentclientprotocol.com/protocol/v2/migration.md, https://raw.githubusercontent.com/agentclientprotocol/agent-client-protocol/main/schema/v1/schema.json, https://github.com/agentclientprotocol/claude-agent-acp, https://github.com/agentclientprotocol/codex-acp, https://github.com/anthropics/claude-code/issues/6686, https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json

**What it is.** A JSON-RPC protocol "jointly governed by Zed and JetBrains" (Apache-2.0, org `agentclientprotocol`) for editors driving coding agents. v1 is stable (integer `protocolVersion: 1`, schema 1.21.0 on 2026-08-20) and has only grown additively through 2026 (session config options, `session/list`, `session/resume`, `session/close`, `session/delete`, `usage_update`, message ids, elicitation, terminal auth). v2 is a draft (`protocolVersion: 2`, alpha schemas) that changes the prompt lifecycle and removes the client `fs`/`terminal` surface; the project says not to ship it by default. Transport is stdio only in the stable spec (the client spawns the agent; newline-delimited JSON); streamable HTTP and WebSocket are a draft RFD with experimental entry points in the TS SDK. Libraries: `@agentclientprotocol/sdk` 1.4.0 (TS, Web Streams based, fluent `client()` API), Rust 2.1.0, Python 0.12.1 (1.0 rc), Kotlin, Java.

**Lifecycle and streaming.** `initialize` (client and agent capabilities, `authMethods`), `authenticate`, `session/new { cwd, mcpServers }`, `session/load` (replays history), `session/resume`, `session/list`, `session/close`, `session/delete`, `session/prompt` returning `stopReason` (`end_turn`, `max_tokens`, `max_turn_requests`, `refusal`, `cancelled`), `session/cancel`, `session/set_config_option` (categories `mode`, `model`, `model_config`, `thought_level`); `session/fork` is a draft RFD exposed as `unstable_forkSession`. `session/update` kinds: `agent_message_chunk`, `agent_thought_chunk`, `user_message_chunk`, `tool_call`, `tool_call_update` (kinds `read`, `edit`, `execute`, `fetch`, ...; content, diff or terminal), `plan`, `available_commands_update`, `current_mode_update`, `config_option_update`, `session_info_update`, `usage_update { used, size, cost? }`.

**Custom tools.** The only stable mechanism is the client passing `mcpServers` (stdio always; `http` when the agent advertises `mcpCapabilities.http`, which all three adapters do). Client-executed methods are limited to `session/request_permission`, `fs/read_text_file`, `fs/write_text_file`, `terminal/*` and `elicitation/create`. MCP-over-ACP (tunnelling MCP through the same connection) and proxy chains are proposals. Hooks, built-in tool disabling, system prompts, structured output and per-turn token usage are not in the spec; claude-agent-acp exposes some SDK options through `_meta.claudeCode.options` (hooks, `disallowedTools`, `tools`, `systemPrompt`), which is adapter-specific.

**Permissions and auth.** `session/request_permission` with options of kind `allow_once`, `allow_always`, `reject_once`, `reject_always`; the answer is `selected { optionId }` or `cancelled`. No input editing. Auth: `authMethods` advertised at `initialize`; `terminal` auth asks the client to launch the agent's own login command. claude-agent-acp advertises "Claude Subscription" and "Anthropic Console" terminal logins and ships `--hide-claude-auth`, whose source says "this integration must never bill a claude.ai subscription"; codex-acp advertises `api-key`, `chat-gpt`, `chat-gpt-device-code`; OpenCode advertises "Run `opencode auth login`".

**Adapter status.** `@agentclientprotocol/claude-agent-acp` 0.78.0 (2026-09-15, Node 22+, Agent SDK 0.3.270 underneath, Zed-dominated commit history; Anthropic closed the "add ACP support" request in `anthropics/claude-code` as not planned). `@agentclientprotocol/codex-acp` 1.12.0 (2026-09-15, TypeScript, wraps `codex app-server`, JetBrains-dominated commit history; the old Rust adapter was archived in July 2026). OpenCode: built in, see above. The registry lists 41 agents including Gemini CLI, Copilot CLI, Cursor, Goose, Kimi and Qwen Code, so an ACP adapter is the cheapest way to support "any other agent".

**Cannot.** Hand the agent host tools without running an MCP server; disable built-in tools; get per-turn usage (draft RFD) or raw token deltas; use hooks or subagent control portably; edit tool input during approval.

## Open risks

1. **Anthropic policy on subscription use.** The legal page permits an end user signing in to the unmodified binary with their own subscription, but the Agent SDK overview says third parties may not offer "claude.ai login or rate limits for their products" unless approved. monday spawning the user's own `claude` from PATH, never initiating login and never touching `~/.claude/.credentials.json`, is the closest to the permitted case, but whether an email client "offers Claude rate limits" is a legal question, not a technical one. Actions: default the docs to API key for Claude; label the local-CLI option as the user's own choice; do not bundle the SDK's binary; consider asking Anthropic (the docs point to contact sales) before release. Also track the paused "Agent SDK credits" change, which would move `claude -p` usage off plan limits.
2. **Codex app-server is labelled experimental** and OpenAI ships new versions two to three times a week. Mitigation: stay on the non-experimental subset, generate bindings with `codex app-server generate-ts` for the minimum supported version, and detect the installed version at startup. `dynamicTools` is the nicer tool path but experimental; MCP is the safe one.
3. **OpenCode has no API stability contract** and shipped a breaking SDK change in 1.4.0. Mitigation: pin a minimum version, use `/v2` types, and keep the adapter thin.
4. **Approval inside MCP tools blocks the tool call** until the user answers. Each harness has a tool timeout (Claude `timeout` per MCP server, Codex `tool_timeout_sec`, OpenCode `timeout`); set them high for monday's server and handle timeouts as "ask again". Codex also applies its own MCP approval mode on top (`default_tools_approval_mode`), which should be set to `auto` for monday's server to avoid double prompts.
5. **Two copies of the tool surface if ACP is added later:** an ACP client can only pass MCP servers, which is the same server, so this is fine; but ACP adapters spawn their own bundled agent binaries via `npx`, which duplicates installs and, for Claude, reopens risk 1.
6. **Bun packaging.** The Claude SDK needs `extractFromBunfs` or an external binary under `bun build --compile`; the Codex TS SDK has an open JSONL-splitting bug on Bun 1.4.x. Spawning the CLIs directly and parsing newline-delimited JSON avoids both.
7. **Windows.** All three CLIs ship native Windows binaries, but OpenCode still recommends WSL and has open Windows ACP issues; Codex's Windows sandbox needs configuration; Claude Code has no native sandbox on Windows. The adapters do not need sandboxes if built-in tools are disabled, which is the plan.
8. **Local process security.** `opencode serve` is unauthenticated without `OPENCODE_SERVER_PASSWORD`; Codex ws transport is unauthenticated on non-loopback; monday's MCP server on loopback should carry a per-launch bearer token (Codex supports `bearer_token_env_var`, Claude `headers`, OpenCode `headers`).
9. **What cannot run on the server when the user is on a local CLI only** (for #14): nothing. All three surfaces live on the laptop; server-side routing, tagging and workflows need an API-key model or must wait until the client is open, exactly as the design's "catches up on launch" cells say.
