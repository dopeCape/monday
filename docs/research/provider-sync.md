# Provider push, sync and OAuth requirements

Research for issue #3 (part of the v1 map, #1). Checked against primary sources on 2026-09-16: Google Gmail API and Cloud Pub/Sub docs, Google OAuth verification and CASA pages, Microsoft Learn (Graph, Entra, Exchange Online), RFCs 8620, 8621, 8887 and Fastmail developer and help pages, and RFCs 2177, 3461, 4549, 4954, 5465, 6154, 6186, 6409, 6851, 7162, 7628, 8314, 8474, 9051 plus vendor IMAP and SMTP pages. Where a live server was probed (pre-authentication IMAP CAPABILITY and SMTP EHLO on 2026-09-16) the text says so. Anything that could not be traced to a primary source is listed under "Open risks" rather than stated as fact.

## Summary

### What makes self-hosting painful

1. **Gmail is the hard one, and it is about credentials, not protocol.** Every real mail scope (`gmail.readonly`, `gmail.modify`, `https://mail.google.com/`) is Restricted. Restricted scopes need brand verification plus an annual CASA security assessment by an ADA lab for any app that touches a third party server, which monday's sync server is. The only escape is the "personal use" path: each self-hoster creates their own Google Cloud project and Desktop OAuth client, sets the consent screen to External and **In production** (not Testing, because Testing refresh tokens expire after 7 days), and clicks through the "unverified app" screen. An open-source project must not ship a shared Google client id: Google's OAuth policy forbids committing client credentials to public repos, and a shared client would need CASA. Consumer @gmail.com accounts cannot use the Internal user type (that requires a Cloud Organization). Push additionally requires a Pub/Sub topic in that project and a billing account attached for the Pub/Sub free tier, though a pull subscription avoids any public endpoint. Gmail API quotas also changed on 2026-05-01 for new projects: `messages.get` now costs 20 units against a 6,000 unit per user per minute budget, so a cold sync of a large mailbox must be paced.
2. **Microsoft Graph push needs a public HTTPS URL, full stop.** Webhooks must answer a validation handshake within 10 seconds from a publicly reachable endpoint; the only alternatives (Azure Event Hubs, Event Grid) need an Azure subscription and a work tenant. A local sidecar behind NAT cannot receive Graph notifications and must poll delta per folder. App registration needs an Entra tenant (personal accounts can register apps, in a default directory), single tenant registrations sidestep publisher verification entirely, and `Mail.ReadWrite` is listed as requiring admin consent on the permissions reference, so work tenants with locked down consent policies will need an admin. EWS is being switched off from 2026-10-01 so it is not a fallback.
3. **Fastmail is easy but plan gated and OAuth is by email.** API tokens are created in the web UI in under a minute and EventSource push works with them, but "API tokens are not available to users on Basic subscription plans", Fastmail OAuth clients are registered manually via partnerships@fastmailteam.com, PushSubscription is not implemented, and calendars are CalDAV only until the JMAP Calendars RFC publishes.
4. **Generic IMAP is only generic for Fastmail, iCloud, Yahoo and self-hosted servers.** Gmail and every Microsoft account require XOAUTH2 on IMAP and SMTP, so the IMAP path for those two providers needs the same Google and Entra registrations as the API path, with the same verification burden. Gmail's IMAP scope is `https://mail.google.com/`, which is Restricted, so IMAP saves nothing on the Gmail side. Incremental sync quality varies wildly: Fastmail has QRESYNC, Microsoft 365 advertises neither CONDSTORE nor QRESYNC, Gmail advertises neither before login.
5. **Push everywhere is renewal work.** Gmail watch dies after 7 days (renew daily), Graph subscriptions after 10,080 minutes (renew before expiry, handle lifecycle events), IMAP IDLE must be re-issued every 29 minutes and covers one folder per connection, and JMAP EventSource streams drop and must be reconnected. Every provider also needs a periodic reconciliation pass because notifications are lossy by contract (Gmail drops above one event per second, Graph sends `missed`, IMAP servers may log the client off).

### Recommended sync strategy per provider

| Provider | New mail signal | Incremental sync | Sending | Credentials a self-hoster must produce |
| --- | --- | --- | --- | --- |
| Gmail | `users.watch` to a Pub/Sub topic with a **pull** subscription (no public endpoint), renewed daily; poll `history.list` every few minutes as a safety net | `history.list(startHistoryId)`; full resync via `messages.list` plus batched `messages.get` on 404 | `messages.send` with raw MIME and `threadId`; large attachments via resumable upload | Own Cloud project, Gmail API enabled, Desktop OAuth client, consent screen External and In production, Pub/Sub topic with `gmail-api-push@system.gserviceaccount.com` as publisher, billing account for Pub/Sub |
| Microsoft 365 and Outlook.com | Cloud server: change notification webhook on `/me/messages` renewed before 10,080 minutes, with lifecycle URL; local sidecar: poll `/me/mailFolders/{id}/messages/delta` every 1 to 2 minutes for hot folders | Per folder delta query with `$select` and `Prefer: odata.maxpagesize`; folder list via `/me/mailFolders/delta`; restart on 410 | `POST /me/sendMail` for messages under 4 MB total; draft plus `createUploadSession` plus `/send` above that | Entra app registration (single tenant for a work account, "personal accounts" type for outlook.com), Mobile and desktop platform with `http://localhost` redirect, delegated Mail.ReadWrite, Mail.Send, MailboxSettings.Read, Calendars.ReadWrite, User.Read, offline_access |
| JMAP (Fastmail, Stalwart, Cyrus) | Long-lived EventSource connection from the sync server (`types=Email,EmailDelivery,Mailbox,Thread`), reconnect with backoff; `Email/changes` poll as fallback | `Mailbox/changes`, `Email/changes`, `Email/queryChanges` with stored state strings; full refetch on `cannotCalculateChanges` | `EmailSubmission/set` with `onSuccessUpdateEmail` to move the draft to Sent | Fastmail: API token with Email plus Email submission scopes (Standard plan or above); other servers: app password or their OAuth |
| Generic IMAP and SMTP | IDLE on INBOX plus a small bounded set of hot folders (one connection each), re-issued every 29 minutes or less; STATUS polling for the rest | QRESYNC when advertised, else CONDSTORE `CHANGEDSINCE` plus UID scan for expunges, else the RFC 4549 full UID FETCH FLAGS scan; tier chosen per mailbox after `ENABLE` | SMTP submission on 465 (implicit TLS) or 587 (STARTTLS), AUTH PLAIN or XOAUTH2, honour EHLO SIZE, APPEND to \Sent unless the provider auto-copies (Gmail, Exchange) | App password for Fastmail, iCloud, Yahoo, Dovecot; XOAUTH2 via the Google or Entra registration above for Gmail and Microsoft |

Onboarding consequences: the first-run flow needs a guided "make your own Google client" wizard (project, API, consent screen, Desktop client, optional Pub/Sub topic) and a guided "register an Entra app" wizard, each ending with the user pasting a client id. Fastmail onboarding is a token paste. Generic IMAP onboarding should run Thunderbird autoconfig, then RFC 6186 SRV, then host guessing, then manual entry, and must detect `AUTH=XOAUTH2` plus `LOGINDISABLED` and route Gmail and Microsoft domains to the OAuth wizards.

## Gmail (Gmail REST API)

### Detecting new mail

- `users.watch` plus Cloud Pub/Sub. "You must call the watch method at least once every 7 days or you'll stop receiving updates for the user. We recommend calling watch once per day." The watch response carries `historyId` and `expiration` (epoch ms). https://developers.google.com/workspace/gmail/api/guides/push and https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/watch
- The notification payload is only `{"emailAddress": "...", "historyId": "..."}`; the client must call `history.list` from its last stored historyId to learn what changed. "Each Gmail user being watched has a maximum notification rate of one event per second. The service drops any user notifications exceeding that rate." https://developers.google.com/workspace/gmail/api/guides/push
- The Pub/Sub topic must live in the Cloud project that has the Gmail API enabled, and the self-hoster must "Grant publish privileges to gmail-api-push@system.gserviceaccount.com" on that topic. Organization domain restricted sharing policies can block this and need an exception. https://developers.google.com/workspace/gmail/api/guides/push
- Pull subscriptions are explicitly supported: "Configure the subscription type to be either a webhook push (that is, an HTTP POST callback) or a pull (that is, initiated by your app)." Push subscriptions need "An HTTPS server with non-self-signed certificate accessible on the public web"; pull ones do not, so a sidecar behind NAT can still get push. https://developers.google.com/workspace/gmail/api/guides/push and https://docs.cloud.google.com/pubsub/docs/subscriber
- Pub/Sub subscription defaults: message retention 7 days, ack deadline 10 seconds, and subscription expiry after 31 days of inactivity unless set to never expire (a sync server that is offline for a month loses the subscription and must recreate it). https://docs.cloud.google.com/pubsub/docs/subscription-properties
- Pricing: "the first 10 GiB of throughput identified as the Message Delivery Basic SKU for a billing account is free. After that, the price is $40 per TiB". The Free Tier requires a billing account attached to the project. A single user's notifications are a few hundred bytes each, so the real cost is the billing account requirement, not money. https://cloud.google.com/pubsub/pricing and https://docs.cloud.google.com/free/docs/free-cloud-features
- `watch` accepts `labelIds` and `labelFilterBehavior` (include or exclude) to restrict notifications. Scopes: mail.google.com, gmail.modify, gmail.readonly or gmail.metadata. https://developers.google.com/workspace/gmail/api/reference/rest/v1/users/watch
- Polling fallback is officially recommended: "fall back to periodically calling the history.list method after a period with no notifications for a user." https://developers.google.com/workspace/gmail/api/guides/push

### Incremental sync

- `history.list` with `startHistoryId` returns records newer than that id. "History IDs increase chronologically but are not contiguous with random gaps in between valid IDs." "A historyId is typically valid for at least a week, but in some rare circumstances may be valid for only a few hours. If you receive an HTTP 404 error response, your application should perform a full sync." `historyTypes`: messageAdded, messageDeleted, labelAdded, labelRemoved; `maxResults` defaults to 100, max 500. https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list and https://developers.google.com/workspace/gmail/api/guides/sync
- Full sync: `messages.list` pages of ids, then batched `messages.get`. "You're limited to 100 calls in a single batch request", "We recommend sending batches of no more than 50 requests", and "A set of n requests batched together counts toward your usage limit as n requests, not as one request." https://developers.google.com/workspace/gmail/api/guides/batch
- Formats: MINIMAL (id and labels), METADATA (plus headers, with `metadataHeaders` to pick which), FULL (parsed payload), RAW (base64url RFC 2822). Partial responses via the `fields` parameter and gzip via `Accept-Encoding: gzip` plus a User-Agent containing "gzip". https://developers.google.com/workspace/gmail/api/reference/rest/v1/Format and https://developers.google.com/workspace/gmail/api/guides/performance
- Message resource: `historyId` is the last history record that touched the message; `internalDate` (epoch ms) "determines ordering in the inbox" and is more reliable than the Date header. https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages
- Labels are many-to-many with messages and threads, not folders. System labels include INBOX, SPAM, TRASH, UNREAD, STARRED, IMPORTANT, SENT, DRAFT and the CATEGORY_* labels; up to 5,000 user labels. Threads break "when the subject line changes, or the conversation gets to more than 100 emails." https://developers.google.com/workspace/gmail/api/guides/labels , https://support.google.com/mail/answer/118708 , https://support.google.com/mail/answer/5900

### Sending

- `messages.send` takes an RFC 2822 message base64url encoded in `raw`; `drafts.send` sends an existing draft. To land in a thread the request must set `threadId`, the References and In-Reply-To headers, and a matching Subject. https://developers.google.com/workspace/gmail/api/guides/sending and https://developers.google.com/workspace/gmail/api/guides/threads
- Attachments: simple upload (`uploadType=media`) is meant for "5 MB or less"; larger bodies go through multipart or resumable upload at `POST https://gmail.googleapis.com/upload/gmail/v1/users/{userId}/messages/send`. The reference pages no longer print a maximum for send; Gmail's product limit is 25 MB per message for attachments and `messages.import` allows 150 MB. https://developers.google.com/workspace/gmail/api/guides/uploads , https://support.google.com/mail/answer/6584 , https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/import
- Sending limits are the account's normal limits, shared across all clients: consumer accounts are blocked after "more than 500 recipients in a single email and or more than 500 emails sent in a day"; Workspace users get 2,000 messages per day (500 on trial) with per-message and per-day recipient caps. The API adds "a limit of 500 recipients per email message." https://support.google.com/mail/answer/22839 , https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace , https://developers.google.com/workspace/gmail/api/reference/quota
- SMTP with XOAUTH2 at smtp.gmail.com (465 or 587) is still supported, but its scope is the restricted `https://mail.google.com/`, so it saves nothing on verification. Gmail auto-copies SMTP sent mail to Sent: "Sent messages are automatically copied to the Gmail/Sent folder if your email client uses SMTP." https://developers.google.com/workspace/gmail/imap/imap-smtp , https://developers.google.com/workspace/gmail/imap/xoauth2-protocol , https://support.google.com/mail/answer/78892

### Rate limits (changed on 2026-05-01)

- "As of May 1, 2026, the usage limits for this API were updated." Projects that used the API between November 2025 and April 2026 keep their old quotas for now; projects created on or after May 1, 2026 get the new ones. Every self-hoster's fresh project gets the new quotas. https://developers.google.com/workspace/gmail/api/reference/quota
- Current table: 1,200,000 quota units per minute per project, 6,000 quota units per minute per user per project, and a new 80,000,000 units per day per project billing threshold ("Usage under this threshold doesn't incur extra charges and your Google Cloud account isn't billed"). Exceeding limits "is planned to incur charges to your Google Cloud billing account later in 2026", and quota increase requests will require billing. https://developers.google.com/workspace/gmail/api/reference/quota and https://developers.google.com/workspace/tools-safety
- Method costs that matter: history.list 2, messages.list 5, messages.get 20, messages.attachments.get 20, messages.modify 5, messages.batchModify 50, messages.send 100, drafts.send 100, threads.get 40, watch 100, stop 50, getProfile 1. At 20 units per messages.get a user can fetch at most 300 messages per minute, so the initial sync of a large mailbox has to be paced and cached (format does not change the unit cost). https://developers.google.com/workspace/gmail/api/reference/quota
- 429 `rateLimitExceeded` and `userRateLimitExceeded`, 403 `dailyLimitExceeded`; "You can't increase per-user limits." There are also unpublished per-user bandwidth limits "equal to, but independent of, IMAP" and a per-user concurrent request limit. Backoff: `min(((2^n)+random_number_milliseconds), maximum_backoff)` with a 32 to 64 second cap, starting at least one second after the error. https://developers.google.com/workspace/gmail/api/guides/handle-errors
- The IMAP side bandwidth caps are published on the Workspace admin page: 2500 MB per day IMAP download, 500 MB per day IMAP upload, suspension "typically lasts for 1 hour, but can last up to 24 hours". https://knowledge.workspace.google.com/admin/gmail/gmail-bandwidth-limits

### Credentials and verification burden

- Scope sensitivity today: Restricted covers `https://mail.google.com/`, gmail.readonly, gmail.compose, gmail.insert, gmail.modify, gmail.metadata, gmail.settings.basic, gmail.settings.sharing. gmail.send is Sensitive. gmail.labels is Non-sensitive. Any real client needs gmail.readonly or gmail.modify, so restricted scope rules apply. https://developers.google.com/workspace/gmail/api/auth/scopes and https://support.google.com/cloud/answer/13464325
- Verification: "Apps requesting sensitive or restricted Google API scopes to access consumer data require additional verification and potentially a security assessment." Any app that "has the ability to access data from or through a third-party server must go through a security assessment from Google-empanelled security assessors", repeated "at least every 12 months". A sync server is a third party server in this sense. https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification
- CASA: restricted scope apps "must undergo an annual security assessment" at assurance level AL1 or AL2 by an ADA authorized lab; the older CASA Tier 2 self scan is "deprecated". No USD cost is published on any primary page any more. https://support.google.com/cloud/answer/13465431 , https://appdefensealliance.dev/casa/casa-tiering , https://appdefensealliance.dev/casa/tier-2/tier2-overview
- Personal use path (the only exemption relevant to a self-hoster; there is no open-source exemption on any Google page): "if you are the only user of your app or if your app is used by only a few users, all of whom are known personally to you. You and your limited number of users might be comfortable with advancing through the unverified app screen". Help center: "If the app is for your personal use (fewer than 100 users), you and your limited number of users can continue using the app without going through verification". Unverified production apps cap at "100 new users in total, after the app presents the unverified app screen". https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification , https://support.google.com/cloud/answer/13464323 , https://support.google.com/cloud/answer/7454865
- The Testing trap: a project "with an OAuth consent screen configured for an external user type and a publishing status of 'Testing' is issued a refresh token expiring in 7 days". Testing is also limited to 100 listed test users. The self-hoster must set the consent screen to In production (unverified), not leave it in Testing, or re-login weekly. https://developers.google.com/identity/protocols/oauth2#expiration and https://support.google.com/cloud/answer/15549945
- Internal user type skips review entirely ("use of restricted or sensitive scopes doesn't require further review by Google") but requires a Google Cloud Organization, which only Workspace tenants have; a consumer @gmail.com account cannot pick Internal. https://developers.google.com/workspace/guides/configure-oauth-consent and https://support.google.com/cloud/answer/15549945
- Other refresh token expiry triggers: six months unused, password change on an account with Gmail scopes, and "a limit of 100 refresh tokens per Google Account per OAuth 2.0 client ID". https://developers.google.com/identity/protocols/oauth2#expiration
- Client type: "Desktop app" OAuth clients are public clients that "do not use client secrets" in any meaningful sense. Redirect via loopback `http://127.0.0.1:port` (localhost also works "but this configuration may cause issues with client firewalls"). PKCE is "Recommended" with S256. The OOB flow is dead since 2023-01-31. Google's OAuth policy says "You must never commit client credentials into publicly available code repositories", so an open-source client should not ship a client id at all. https://support.google.com/cloud/answer/6158849 , https://developers.google.com/identity/protocols/oauth2/native-app , https://developers.google.com/identity/protocols/oauth2/resources/oob-migration , https://developers.google.com/identity/protocols/oauth2/policies
- Fallbacks: IMAP is always on since January 2025 and app passwords still work for accounts with 2-Step Verification, but "aren't recommended and are unnecessary in most cases"; less secure app passwords stopped working for Workspace on 2025-03-14 ("CalDAV, CardDAV, IMAP, SMTP, and POP will no longer work with legacy passwords"). https://support.google.com/mail/answer/7126229 , https://support.google.com/accounts/answer/185833 , https://knowledge.workspace.google.com/admin/sync/transition-from-less-secure-apps-to-oauth

## Microsoft 365 and Outlook.com (Microsoft Graph)

### Detecting new mail

- Change notifications (webhooks) on `/me/messages` or `/me/mailFolders('inbox')/messages`. Lifetime for Outlook message subscriptions is "10,080 minutes (under seven days)"; rich notification subscriptions (with resource data) last "1440 minutes (under one day)". Renew with `PATCH /subscriptions/{id}` and a new `expirationDateTime`; "When you renew your subscription, your access token is also refreshed." Average latency "Less than 1 minute", maximum "3 minutes". https://learn.microsoft.com/en-us/graph/api/resources/subscription , https://learn.microsoft.com/en-us/graph/change-notifications-overview , https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks
- The endpoint must be public: "To use webhooks, you need to define a publicly accessible HTTPS-secured endpoint that receives the notifications." and "If your endpoint isn't publicly accessible, Microsoft Graph doesn't send notifications to your endpoint." On create, Graph POSTs `?validationToken=...` and "The client must respond ... within 10 seconds" with 200, `text/plain` and the decoded token, else the create fails with 400. Delivery is considered done on a 2xx within 3 seconds; otherwise Graph retries "for up to 4 hours", and endpoints that are slow more than 15% of the time get notifications dropped for 10 minute windows. https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks
- Lifecycle notifications (`reauthorizationRequired`, `subscriptionRemoved`, `missed`) go to `lifecycleNotificationUrl`, which cannot be added to an existing subscription. On `subscriptionRemoved` or `missed` Microsoft's guidance is to resync with delta query. https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events
- Rich notifications (`includeResourceData: true`) are supported for Outlook messages in v1.0, but require an RSA encryption certificate, `$select` on the resource, AES-CBC decryption plus HMAC and JWT validation on receipt, and the one day lifetime. Not worth it for a single user client: the notification is only a trigger for delta. https://learn.microsoft.com/en-us/graph/change-notifications-with-resource-data and https://learn.microsoft.com/en-us/graph/outlook-change-notifications-overview
- Alternatives without a public webhook are Azure Event Hubs ("You don't rely on publicly exposed notification URLs") and Azure Event Grid, but both require an Azure subscription and a work or school tenant whose domain matches the subscription, so they are out for personal accounts and heavy for a self-hoster. Microsoft's stated model for delta is pull: "Delta query uses a pull model". https://learn.microsoft.com/en-us/graph/change-notifications-delivery-event-hubs , https://learn.microsoft.com/en-us/azure/event-grid/subscribe-to-graph-api-events , https://learn.microsoft.com/en-us/graph/delta-query-overview
- There is no way to get Graph push to a server behind NAT without a public HTTPS endpoint or an Azure resource. The sync server therefore needs two modes: webhook when it has a public URL (cloud deployment, or a tunnel the user provides), otherwise delta polling on a short interval.
- Personal Microsoft accounts are supported for message subscriptions (the permissions table lists Mail.ReadBasic and Mail.Read under "Delegated (personal Microsoft account)"). A subscription needs only a read scope; "Microsoft Graph subscriptions don't support write access permissions when only read access permissions are needed." Max "1,000 active subscriptions per mailbox for all applications"; duplicates return 409. https://learn.microsoft.com/en-us/graph/api/subscription-post-subscriptions?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/change-notifications-overview

### Incremental sync

- "Delta query is a per-folder operation. To track the changes of the messages in a folder hierarchy, you need to track each folder individually." `GET /me/mailFolders/{id}/messages/delta`; there is no mailbox wide `/me/messages/delta`. Folder hierarchy changes come from `GET /me/mailFolders/delta`. https://learn.microsoft.com/en-us/graph/delta-query-messages , https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0 , https://learn.microsoft.com/en-us/graph/api/mailfolder-delta?view=graph-rest-1.0
- A page carries either `@odata.nextLink` (`$skiptoken`) or `@odata.deltaLink` (`$deltatoken`), never both. Tokens encode the original `$select`, so later requests must not repeat query parameters. Deletions appear as `"@removed": {"reason": "deleted"}` with only an id. "Your application must be prepared for replays". https://learn.microsoft.com/en-us/graph/delta-query-overview
- Query support: `$select`, `$top`, `$expand`; `$filter` only on `receivedDateTime ge|gt` and capped at 5,000 messages; `$orderby` only `receivedDateTime desc`; no `$search`; `Prefer: odata.maxpagesize` for page size; `changeType=created|updated|deleted` as a custom option. A 2026 note warns that read/unread changes and `@removed` entries leak through filters. https://learn.microsoft.com/en-us/graph/delta-query-messages and https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0
- Token lifetime is unbounded but not guaranteed: for Outlook entities "the upper limit isn't fixed; it's dependent on the size of the internal delta token cache" and old tokens are evicted. Expired tokens yield a 40x such as `syncStateNotFound`; a `410 Gone` with a `Location` header carrying an empty `$deltatoken` means restart with a full sync. https://learn.microsoft.com/en-us/graph/delta-query-overview
- Raw MIME: `GET /me/messages/{id}/$value` generates MIME on the fly (Outlook does not store MIME). Attachments under 3 MB are a single POST; 3 MB to 150 MB use `createUploadSession` and ranged PUTs under 4 MB each. https://learn.microsoft.com/en-us/graph/outlook-get-mime-message and https://learn.microsoft.com/en-us/graph/outlook-large-attachments

### Sending

- `POST /me/sendMail` with a JSON message (`saveToSentItems` defaults true) or a base64 MIME body with `Content-Type: text/plain`; returns 202, which "doesn't indicate that the request processing has completed." Or create a draft with `POST /me/messages` then `POST /me/messages/{id}/send`. `reply`, `replyAll`, `forward` and their `create*` draft variants exist and honour Reply-To. https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0 , https://learn.microsoft.com/en-us/graph/api/message-send?view=graph-rest-1.0 , https://learn.microsoft.com/en-us/graph/api/message-reply?view=graph-rest-1.0 , https://learn.microsoft.com/en-us/graph/outlook-send-mime-message
- "Write requests in the Microsoft Graph API have a size limit of 4 MB", failing with 413, so any message with attachments over about 3 MB must be built as a draft, get its attachments via upload sessions, then be sent. "Microsoft Graph does not support editing or updating MIME properties individually." https://learn.microsoft.com/en-us/graph/use-the-api
- Exchange Online limits: "Recipient rate limit: 10,000 recipients per day", "Message rate limit: 30 messages per minute", recipients per message customizable up to 1,000, default message size 35 MB send and 36 MB receive, admin configurable up to 150 MB. Outlook.com (Microsoft 365 subscribers): 5,000 daily recipients, 500 per message, and "Limits may vary based on usage history and will be lower for non-subscribers", with new accounts starting on a temporary low quota. https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits and https://support.microsoft.com/en-us/office/sending-limits-in-outlook-com-279ee200-594c-40f0-9ec8-bb6af7735c2e
- SMTP AUTH with OAuth (XOAUTH2, scope `https://outlook.office.com/SMTP.Send`) at `smtp.office365.com:587` works for both Microsoft 365 and Outlook.com, capped at 3 concurrent connections, 30 messages per minute and 10,000 recipients per day, and Exchange stores a copy in Sent Items by default (`MessageCopyForSMTPClientSubmissionEnabled`); SMTP AUTH is disabled by default for tenants created after January 2020 and must be enabled per mailbox. Basic auth for SMTP AUTH stays until "End of December 2026" when it "will be disabled by default for existing tenants", is unavailable for new tenants after that, with the final removal date to be announced in 2027. https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth , https://learn.microsoft.com/en-us/troubleshoot/exchange/send-emails/smtp-submission-improvements , https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/authenticated-client-smtp-submission , https://techcommunity.microsoft.com/blog/exchange/updated-exchange-online-smtp-auth-basic-authentication-deprecation-timeline/4489835

### Rate limits

- Outlook service limits are per app id and mailbox pair: "10,000 API requests in a 10-minute period", "Four concurrent requests", "150 megabytes (MB) upload (PATCH, POST, PUT) in a 5-minute period". https://learn.microsoft.com/en-us/graph/throttling-limits#outlook-service-limits

## JMAP (Fastmail first, generic JMAP second)

### Detecting new mail

- RFC 8620 defines two push mechanisms. Section 7.2 PushSubscription: the server POSTs StateChange objects to a client-owned URL, which "MUST be https", may be encrypted with RFC 8291 Web Push keys, needs a verificationCode round trip, and "A server MAY reject or limit push subscriptions". Section 7.3 Event Source: the Session object carries an `eventSourceUrl` URI template that "MUST contain variables called types, closeafter, and ping"; the server streams `state` events carrying StateChange objects plus periodic `ping` events, and may close the connection at its discretion. https://www.rfc-editor.org/rfc/rfc8620.html#section-7
- RFC 8621 section 1.5 adds the `EmailDelivery` pseudo type: servers implementing the mail capability "MUST support pushing state changes for a type called EmailDelivery", whose state changes only when a new Email is added to the store. This is the cheap "new mail arrived" signal; `Email` state also bumps for flag changes, expunges and moves. https://www.rfc-editor.org/rfc/rfc8621.html#section-1.5
- RFC 8887 (JMAP over WebSocket) adds `urn:ietf:params:jmap:websocket` with a `supportsPush` flag and `WebSocketPushEnable` with `pushState` for resumable push over one socket. https://www.rfc-editor.org/rfc/rfc8887.html
- Fastmail status: EventSource works for third party clients that authenticate with a personal API token; Fastmail staff (rjbs) confirmed this hit production in 2022 after years where the endpoint rejected non-Fastmail clients. PushSubscription was "on the road map" in 2022 and is still not listed in Fastmail's developer docs as of 2026-09. In 2023 a client author reported Fastmail's event stream used `type` instead of `@type` and ignored `ping` and `closeafter`; Fastmail acknowledged it as a bug. The parser should accept both spellings. https://github.com/fastmail/JMAP-Samples/issues/7 and https://www.fastmail.com/dev/
- Fastmail does not advertise the WebSocket capability in its developer docs. https://www.fastmail.com/dev/
- Implication for monday: the sync server holds one long-lived EventSource connection per JMAP account (`types=Email,EmailDelivery,Mailbox,Thread`), with reconnect and backoff, and treats every StateChange as a trigger to run `/changes`. This works behind NAT because the server dials out. PushSubscription is not needed. A slow poll of `Email/changes` (say every 5 minutes) is the fallback when the stream dies.

### Incremental sync

- RFC 8620 section 5.2 `Foo/changes` takes `sinceState` and optional `maxChanges`, returns `newState`, `hasMoreChanges`, created, updated and destroyed ids. Servers "SHOULD be able to calculate changes from any state string that was given to a client within the last 30 days". On `cannotCalculateChanges` the client must refetch everything for that type. https://www.rfc-editor.org/rfc/rfc8620.html#section-5.2
- Section 5.6 `Foo/queryChanges` keeps a sorted list view (for example the inbox list) in sync without refetching; a server may return `tooManyChanges`, and the client then reruns the query. https://www.rfc-editor.org/rfc/rfc8620.html#section-5.6
- Session object limits the client must honour (`urn:ietf:params:jmap:core`): maxSizeUpload, maxConcurrentUpload, maxSizeRequest, maxConcurrentRequests, maxCallsInRequest, maxObjectsInGet, maxObjectsInSet. Exceeding them yields request level `urn:ietf:params:jmap:error:limit` or method level `requestTooLarge`. Fastmail returns concrete values in the session response but does not publish them in docs; read them at connect time rather than hardcoding. https://www.rfc-editor.org/rfc/rfc8620.html#section-2
- RFC 8621 section 4.2 `Email/get` supports `fetchTextBodyValues`, `fetchHTMLBodyValues`, `fetchAllBodyValues` and `maxBodyValueBytes` so list views can fetch previews cheaply; full MIME comes from the blob download URL template (section 6.2 of RFC 8620). Keywords with fixed meaning: `$draft`, `$seen`, `$flagged`, `$answered`, `$forwarded`, `$phishing`, `$junk`, `$notjunk`. Mailbox roles follow RFC 8457 (inbox, drafts, sent, trash, junk, archive). https://www.rfc-editor.org/rfc/rfc8621.html
- Discovery: RFC 8620 section 2.2 says hosts "SHOULD publish a SRV record _jmap._tcp.example.com" and the session resource is `https://{hostname}[:{port}]/.well-known/jmap` following redirects. Fastmail's session URL is `https://api.fastmail.com/jmap/session`. https://www.rfc-editor.org/rfc/rfc8620.html#section-2.2

### Sending

- RFC 8621 section 7 `EmailSubmission/set` submits an existing Email object through an Identity (section 6). `onSuccessUpdateEmail` and `onSuccessDestroyEmail` let one call move the message out of Drafts, clear `$draft` and add it to Sent atomically. `sendAt` plus the submission capability's `maxDelayedSend` give server side scheduled or undo send; `undoStatus` moves from `pending` to `final` or `canceled`. `submissionExtensions` lists SMTP extensions (SIZE, DSN, FUTURERELEASE) the server relays. https://www.rfc-editor.org/rfc/rfc8621.html#section-7
- Raw MIME can be uploaded with the blob upload endpoint (RFC 8620 section 6.1) then turned into an Email with `Email/import` (RFC 8621 section 4.8), useful for migration and for messages authored by a MIME library.
- SMTP fallback: `smtp.fastmail.com` port 465 (or 587 STARTTLS) with an app password, PLAIN auth; the regular password does not work. Live EHLO on 2026-09-16 advertised `SIZE 71000000`. https://www.fastmail.help/hc/en-us/articles/1500000278342-Server-names-and-ports

### Rate limits

- Fastmail publishes no JMAP request rate; the developer docs only state that Masked Email creation has "rate limits in place" and returns a `rateLimit` SetError. https://www.fastmail.com/dev/
- Fastmail account limits that matter: emails must be under 70 MB total (so attachments about 50 MB), daily send caps of 4,000 / 8,000 / 16,000 messages (Basic / Standard / Professional) with an hourly cap of half the daily figure, trials capped at 120 messages per day, and "500 (successful) logins per 10 minutes". https://www.fastmail.help/hc/en-us/articles/1500000277382-Account-limits

## Generic IMAP and SMTP

### Detecting new mail

- IDLE (RFC 2177, folded into RFC 9051): "clients using IDLE are advised to terminate the IDLE and re-issue it at least every 29 minutes to avoid being logged off." RFC 9051 restates that the autologout timer during IDLE "MUST NOT be shorter than 30 minutes". During IDLE "the server is now free to send untagged EXISTS, EXPUNGE, and other messages at any time", including untagged FETCH with FLAGS, but only for the selected mailbox. https://www.rfc-editor.org/rfc/rfc2177.html section 3 and https://www.rfc-editor.org/rfc/rfc9051.html sections 5.4 and 6.3.13
- One mailbox per connection: "IDLE only applies to the selected mailbox, thus requiring an additional TCP connection per mailbox." NOTIFY (RFC 5465) watches many mailboxes on one connection but is only implemented by Dovecot (requires `mailbox_list_index = yes`) and Cyrus; Gmail, Microsoft 365, iCloud, Yahoo and Fastmail did not advertise it before login on 2026-09-16. https://www.rfc-editor.org/rfc/rfc5465.html section 1 , https://doc.dovecot.org/main/core/summaries/rfc.html , https://www.cyrusimap.org/imap/rfc-support.html , https://developers.google.com/workspace/gmail/imap/imap-extensions
- Polling fallback: NOOP on the selected mailbox, STATUS (MESSAGES UIDNEXT UNSEEN HIGHESTMODSEQ) on others. https://www.rfc-editor.org/rfc/rfc9051.html section 6.1.2
- Connection budgets: Gmail "You can add Gmail to up to 15 email clients at a time per account" (else "Too many simultaneous connections"); Dovecot defaults `mail_max_userip_connections` to 10; Exchange Online publishes no IMAP connection cap (on-premises default is 16); Fastmail limits "500 (successful) logins per 10 minutes". So IDLE should be bounded to INBOX plus a few hot folders, with STATUS polling for the rest. https://support.google.com/mail/answer/7126229 , https://doc.dovecot.org/main/core/summaries/settings.html , https://learn.microsoft.com/en-us/exchange/set-connection-limits-for-imap4-exchange-2013-help , https://www.fastmail.help/hc/en-us/articles/1500000277382-Account-limits
- Exchange also documents a 30 minute default inactivity timer that can be configured lower, and only sends capabilities on an explicit CAPABILITY command, so always issue CAPABILITY after login. https://learn.microsoft.com/en-us/openspecs/exchange_standards/ms-stanximap/7513f9b5-501b-4f96-9fd8-0fdb3432d1e7
- Live pre-authentication CAPABILITY on 2026-09-16 (post-login capabilities may differ):
  - imap.gmail.com: `IMAP4rev1 UNSELECT IDLE NAMESPACE QUOTA ID XLIST CHILDREN X-GM-EXT-1 XYZZY SASL-IR AUTH=XOAUTH2 AUTH=PLAIN AUTH=PLAIN-CLIENTTOKEN AUTH=OAUTHBEARER`
  - outlook.office365.com: `IMAP4 IMAP4rev1 AUTH=XOAUTH2 LOGINDISABLED SASL-IR UIDPLUS MOVE ID UNSELECT CHILDREN IDLE NAMESPACE LITERAL+`
  - imap.mail.me.com: `XAPPLEPUSHSERVICE IMAP4 IMAP4rev1 SASL-IR AUTH=ATOKEN AUTH=PLAIN AUTH=ATOKEN2 AUTH=XOAUTH2`
  - imap.mail.yahoo.com: `IMAP4rev1 SASL-IR AUTH=PLAIN AUTH=XOAUTH2 AUTH=OAUTHBEARER ID MOVE NAMESPACE XYMHIGHESTMODSEQ UIDPLUS LITERAL+ CHILDREN UNSELECT X-MSG-EXT OBJECTID IDLE ENABLE UIDONLY X-UIDONLY LIST-EXTENDED LIST-STATUS SPECIAL-USE PARTIAL APPENDLIMIT=41697280`
  - imap.fastmail.com: `IMAP4 IMAP4rev1 IMAP4rev2 LITERAL+ ENABLE UIDPLUS SASL-IR NAMESPACE CONDSTORE SORT LIST-EXTENDED QRESYNC MOVE SPECIAL-USE CREATE-SPECIAL-USE IDLE AUTH=PLAIN AUTH=LOGIN AUTH=XOAUTH2 AUTH=OAUTHBEARER`

### Incremental sync

- IMAP4rev2 (RFC 9051) folds in NAMESPACE, UNSELECT, UIDPLUS, ESEARCH, SEARCHRES, ENABLE, IDLE, SASL-IR, LIST-EXTENDED, LIST-STATUS, MOVE, LITERAL-, the FETCH side of BINARY and the SPECIAL-USE attributes, but only Fastmail advertised it live; Dovecot's support is "experimental partial" since 2.4.2 (2025-10-24). The client must speak IMAP4rev1 plus individual extensions. https://www.rfc-editor.org/rfc/rfc9051.html Appendix E and https://raw.githubusercontent.com/dovecot/core/main/NEWS
- UID rules: UIDs "SHOULD NOT change between sessions"; if they do, UIDVALIDITY "MUST be greater than the one used in the earlier session". On a UIDVALIDITY mismatch "the client MUST empty the local cache of that mailbox and remove any pending 'actions' that refer to UIDs in that mailbox." https://www.rfc-editor.org/rfc/rfc9051.html section 2.3.1.1 and https://www.rfc-editor.org/rfc/rfc4549.html section 4.1
- Baseline without CONDSTORE or QRESYNC (RFC 4549): `UID FETCH <lastseenuid+1>:* <descriptors>` for new mail plus `UID FETCH 1:<lastseenuid> FLAGS` for flags and expunge detection ("All messages that didn't have a matching untagged FETCH response MUST be removed from the local cache"). Cost is proportional to mailbox size on every resync. https://www.rfc-editor.org/rfc/rfc4549.html section 4.3.1
- CONDSTORE and QRESYNC (RFC 7162): CONDSTORE adds MODSEQ, HIGHESTMODSEQ and `UID FETCH 1:* (FLAGS) (CHANGEDSINCE n)`, but "the client still has to issue a UID FETCH or a UID SEARCH command" to find expunges. QRESYNC ("MUST issue ENABLE QRESYNC") lets SELECT carry the last UIDVALIDITY, HIGHESTMODSEQ and known UIDs, and returns `VANISHED (EARLIER)` for removed UIDs. https://www.rfc-editor.org/rfc/rfc7162.html sections 3.1.4.1, 3.2.1, 3.2.3, 3.2.5, 3.2.10
- Support: Dovecot and Cyrus (so Fastmail) implement RFC 7162; Microsoft 365 advertises neither and its IMAP standards document references only RFC 3501 and states "Microsoft Exchange does not support client-defined keywords"; Gmail's IMAP extensions page never mentions CONDSTORE or QRESYNC and neither appears pre-login; Yahoo has a proprietary `XYMHIGHESTMODSEQ` plus OBJECTID. Three tiers (QRESYNC, CONDSTORE, RFC 4549) chosen per mailbox are unavoidable. https://doc.dovecot.org/main/core/summaries/rfc.html , https://www.cyrusimap.org/imap/rfc-support.html , https://learn.microsoft.com/en-us/openspecs/exchange_standards/ms-stanximap/7513f9b5-501b-4f96-9fd8-0fdb3432d1e7 , https://developers.google.com/workspace/gmail/imap/imap-extensions
- Useful extensions: OBJECTID (RFC 8474) EMAILID survives COPY and MOVE (Cyrus, Yahoo; not Dovecot); MOVE (RFC 6851) with COPYUID; SPECIAL-USE (RFC 6154) \Sent, \Drafts, \Trash, \Junk, \Archive, \All (Gmail uses the older XLIST); BINARY section fetches; ESEARCH (RFC 4731); FUZZY (RFC 6203) only where a full text driver exists; Gmail's X-GM-MSGID, X-GM-THRID, X-GM-LABELS and X-GM-RAW; LITERAL+ and LITERAL- (RFC 7888); COMPRESS=DEFLATE (RFC 4978, Dovecot and Cyrus, not seen at any provider pre-login). https://www.rfc-editor.org/rfc/rfc8474.html , https://www.rfc-editor.org/rfc/rfc6851.html , https://www.rfc-editor.org/rfc/rfc6154.html , https://www.rfc-editor.org/rfc/rfc4731.html , https://www.rfc-editor.org/rfc/rfc6203.html , https://developers.google.com/workspace/gmail/imap/imap-extensions , https://www.rfc-editor.org/rfc/rfc7888.html , https://www.rfc-editor.org/rfc/rfc4978.html
- Gmail over IMAP: "Gmail treats labels as folders for the purposes of IMAP", so a message appears in every label folder with a different UID and X-GM-MSGID is the only stable key; syncing All Mail plus INBOX plus labels multiplies download volume against the 2500 MB per day cap. https://developers.google.com/workspace/gmail/imap/imap-extensions and https://knowledge.workspace.google.com/admin/gmail/gmail-bandwidth-limits

### Sending

- Submission (RFC 6409): "Port 587 is reserved for email message submission"; the MSA must reject MAIL without authentication. RFC 8314: "clients and servers SHOULD implement both STARTTLS on port 587 and Implicit TLS on port 465" and "Implicit TLS SHOULD be advertised in preference to servers supporting STARTTLS"; TLS 1.2 or later is mandatory; port 993 is implicit TLS for IMAP. https://www.rfc-editor.org/rfc/rfc6409.html sections 3.1 and 4.3 , https://www.rfc-editor.org/rfc/rfc8314.html sections 3.2, 3.3, 4
- AUTH (RFC 4954) PLAIN and LOGIN over TLS; OAUTHBEARER (RFC 7628) vs XOAUTH2 (Google and Microsoft, not an RFC, `base64("user=" + user + "^Aauth=Bearer " + token + "^A^A")`). Live: Gmail, Yahoo and Fastmail advertise both on IMAP and SMTP; Microsoft advertises only XOAUTH2; iCloud advertises XOAUTH2 for Apple's own use plus PLAIN and LOGIN. https://www.rfc-editor.org/rfc/rfc4954.html , https://www.rfc-editor.org/rfc/rfc7628.html , https://developers.google.com/workspace/gmail/imap/xoauth2-protocol , https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth
- SIZE (RFC 1870) advertises the maximum in EHLO and returns 552 above it. Live EHLO SIZE on 2026-09-16: smtp.gmail.com 35882577, smtp.office365.com 157286400, smtp.fastmail.com 71000000, smtp.mail.me.com 28319744, smtp.mail.yahoo.com 41697280. Documented product limits: Gmail 25 MB attachments, Microsoft 365 default 35 MB send and 36 MB receive (admin up to 150 MB), Fastmail 70 MB message, iCloud 20 MB (Mail Drop to 5 GB), Yahoo 25 MB. Read SIZE at runtime and refuse locally. https://www.rfc-editor.org/rfc/rfc1870.html , https://support.google.com/mail/answer/6584 , https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits , https://www.fastmail.help/hc/en-us/articles/360060591253-Sending-and-receiving-attachments , https://support.apple.com/en-us/102198 , https://help.yahoo.com/kb/SLN5673.html
- 8BITMIME and SMTPUTF8 (RFC 6531) for non-ASCII addresses; DSN (RFC 3461) advertised by Microsoft and iCloud but not Gmail, Yahoo or Fastmail; BURL (RFC 4468) is advertised by none of the six probed servers and is not in Dovecot or Cyrus, so do not depend on it. https://www.rfc-editor.org/rfc/rfc6531.html , https://www.rfc-editor.org/rfc/rfc3461.html , https://www.rfc-editor.org/rfc/rfc4468.html
- Sent copies: SMTP stores nothing, so the generic path is IMAP APPEND to the \Sent mailbox. Gmail ("Sent messages are automatically copied to the Gmail/Sent folder if your email client uses SMTP") and Exchange Online (`MessageCopyForSMTPClientSubmissionEnabled` defaults to true) copy automatically, so a per-account "server saves sent copy" flag must default true for those two and false elsewhere, or the client double-appends. https://support.google.com/mail/answer/78892 and https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/set-mailbox
- Provider sending caps over SMTP match the API caps: Gmail 500 messages or recipients per day for consumers, Exchange Online 30 messages per minute and 10,000 recipients per day with 3 concurrent SMTP AUTH connections, Fastmail 4,000 to 16,000 per day, iCloud 1,000 messages and 1,000 recipients per day with 500 per message. https://support.google.com/mail/answer/22839 , https://learn.microsoft.com/en-us/troubleshoot/exchange/send-emails/smtp-submission-improvements , https://www.fastmail.help/hc/en-us/articles/1500000277382-Account-limits , https://support.apple.com/en-us/102198

## Open risks

1. **Gmail credential model is the biggest onboarding risk.** The "personal use" path is described in Google help text, not in a policy document, and Google reserves the right to change the unverified app screen or the 100 user cap. If Google ever tightens the personal-use exemption, monday's Gmail support degrades to app passwords over IMAP (consumer accounts with 2SV only) or nothing. Decision needed: whether the project will ever pursue verification plus CASA for a shared client (cost is no longer published; historically five figures per year).
2. **Gmail quota billing.** The 80,000,000 unit per day threshold and paid overage "later in 2026" mean a self-hoster's project may eventually need billing enabled even for normal use; the exact pricing is not yet published.
3. **Graph push for the local sidecar.** No documented path exists without a public HTTPS endpoint. Options are polling delta (recommended default), a user supplied tunnel, or a small relay the project hosts, which contradicts "everything self-hosted". Polling per folder every 1 to 2 minutes at 4 concurrent requests stays far under 10,000 per 10 minutes, so polling is acceptable.
4. **Graph admin consent for Mail.ReadWrite.** The permissions reference marks it as admin consent required; whether a plain user in a default tenant can self-consent depends on tenant policy and could not be confirmed without a live tenant. Onboarding must handle AADSTS90094 style consent failures gracefully and suggest Mail.Read plus Mail.Send as a reduced mode.
5. **Fastmail plan gating and OAuth.** Basic plan users cannot create API tokens at all; those users would need the IMAP path with an app password. Fastmail OAuth registration is manual by email, so a shared monday client id is possible but depends on Fastmail's goodwill.
6. **Fastmail EventSource conformance.** The 2023 report of non-conformant events (`type` vs `@type`, `ping` and `closeafter` ignored) was acknowledged as a bug; whether it has been fixed could not be verified without a token. The parser must be lenient and a poll fallback is mandatory.
7. **JMAP Calendars.** Fastmail is CalDAV only until the RFC publishes; the calendar UI in v1 needs a CalDAV client for Fastmail regardless, and Fastmail OAuth has no calendar scope, only app passwords for CalDAV.
8. **IMAP incremental sync on Microsoft 365 and Gmail.** Neither advertises CONDSTORE or QRESYNC before login, so the RFC 4549 full flag scan may be the only option, which is expensive on large folders. Post-login CAPABILITY for Gmail, Microsoft 365, iCloud and Yahoo was not verified; the sync engine must probe after `ENABLE` and pick a tier per mailbox.
9. **IMAP connection budget.** A server side daemon holds IDLE connections permanently, eating into Gmail's 15 client cap and Dovecot's default 10 per user per IP; users who also run a phone client can hit "Too many simultaneous connections". IDLE should be capped at INBOX plus a small configurable set.
10. **Sent folder duplication over SMTP.** Gmail and Exchange auto-copy; other providers do not. A wrong default produces duplicates or missing sent mail. Detect by provider host and, where possible, by checking the \Sent folder for the Message-ID after sending.
11. **Deadlines that land during v1 development.** EWS disablement starts 2026-10-01 (irrelevant if monday never uses EWS, but rules it out as a fallback); Microsoft SMTP AUTH basic disabled by default at the end of December 2026; Gmail quota billing later in 2026. Re-check these pages before the sync slice ships.
12. **Unverified figures deliberately left out.** Exchange Online IMAP concurrent connection limit, any provider's sub 30 minute IMAP idle cutoff, iCloud and Yahoo IMAP extension support, a distinct MSA refresh token lifetime, the "35 MB via media upload" figure for Gmail send, and the current CASA assessment cost. None of these should be assumed in the spec.
