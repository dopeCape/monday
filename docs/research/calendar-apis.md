# Calendar APIs and invite handling: Google, Microsoft Graph, CalDAV

Research for issue #6 (part of the v1 map, #1). Checked against primary sources on 2026-09-16. Facts carry a URL; anything we could not confirm on a first-party page is marked "unverified" and listed again under open risks.

## Summary

- Every provider in v1 can do the four things the calendar UI needs: list calendars, read events in a window, detect changes, and create an event with attendees. Only Google and Microsoft can mint a meeting link; CalDAV carries a link but cannot create one.
- The "set up a call Thursday 15:00" flow is one create call on Google and Graph (the server mails the invitations), and one PUT on Fastmail (RFC 6638 implicit scheduling makes the server mail them too). Only a bare CalDAV server without scheduling, or an IMAP-only account, needs monday to produce and send the iMIP mail itself.
- Free/busy for other people is the weakest leg: Google exposes it only where the calendar is shared or same-domain, Microsoft only for work or school accounts, CalDAV only inside one organisation, and there is no cross-provider answer. v1 should always check the user's own calendar and treat other people's availability as best effort.
- Push exists only as HTTPS webhooks (Google channels, Graph subscriptions). CalDAV has no push. Since the sync server may run as a local sidecar with no public address, polling with incremental sync tokens is the baseline on every provider and webhooks are an optimisation for cloud deployments.
- Invitations in mail are `text/calendar; method=REQUEST` parts (RFC 6047). Google, Exchange and Fastmail all auto-place the event on the recipient's calendar before the user answers, so on those accounts the invite bar should read state from and RSVP through the calendar API, and never re-process the mail into calendar writes. Sending a `METHOD:REPLY` mail is the universal fallback and is processed by Google, Exchange and Fastmail organizers, with caveats noted below.

## Recommended minimum surface for v1

The calendar module exposes one interface per account with these operations. Anything not listed is out of v1.

| Operation | Google | Microsoft Graph | Fastmail and CalDAV | IMAP/SMTP only |
| --- | --- | --- | --- | --- |
| List calendars | `calendarList.list` | `GET /me/calendars` | PROPFIND `calendar-home-set`, Depth 1 | none (optional linked CalDAV URL) |
| Read window | `events.list` with `singleEvents=true`, `timeMin`, `timeMax` | `GET /me/calendarView?startDateTime&endDateTime` | `sync-collection` + `calendar-multiget`, expand recurrences locally | none |
| Incremental sync | `syncToken`, full resync on 410 | `calendarView/delta` per calendar | `DAV:sync-token`, full resync on `valid-sync-token` 403 | none |
| Change detection | poll; `events.watch` webhook when the server is public | poll; `POST /subscriptions` on `/me/events` when public | poll `sync-token` | none |
| Own availability | local cache | local cache | local cache | none |
| Others' availability | `freebusy.query` (best effort) | `getSchedule` (work or school only) | RFC 6638 outbox POST (intra-org, unverified on Fastmail) | none |
| Create with attendees | `events.insert`, `sendUpdates=all` | `POST /me/events` (server mails invites) | PUT with `ATTENDEE`, server mails invites when `calendar-auto-schedule` | monday sends iMIP REQUEST over SMTP |
| Meeting link | `conferenceData.createRequest` `hangoutsMeet` | `isOnlineMeeting: true`, `teamsForBusiness` | user-configured link written to `CONFERENCE` and `DESCRIPTION` | same |
| RSVP | `events.patch` own `attendees[].responseStatus` + `sendUpdates` | `POST /me/events/{id}/accept`, `tentativelyAccept`, `decline` | PUT with own `PARTSTAT`, server sends REPLY | monday sends iMIP REPLY over SMTP |
| Cancel | `events.delete` with `sendUpdates=all` | `DELETE /me/events/{id}` | DELETE (server sends CANCEL) | monday sends iMIP CANCEL |

Shared pieces:

- One iCalendar parser (`ical.js`) and one generator (`ical-generator`) on the server; the invite bar in mail is driven by the parsed `text/calendar` part on every account type.
- Scopes: Google `calendar.events` + `calendar.calendarlist.readonly` + `calendar.freebusy`; Microsoft delegated `Calendars.ReadWrite` (add `Calendars.Read.Shared` only if `findMeetingTimes` is wanted later); Fastmail OAuth bearer or app password over CalDAV.
- Deliberately out of v1: `findMeetingTimes`, COUNTER (propose new time), delegation, resource and room booking, JMAP Calendars (spec still in the RFC Editor queue), WebDAV Push (not an IETF draft), writing to shared calendars.

The agent flow "set up a call Thursday 15:00" then is: resolve attendees from contacts; read own calendar for the slot from the local cache; query others' free/busy where the provider allows it and say so when it does not; ask the user before anything leaves the mailbox (standing preference); create the event with attendees and a meeting link through the account's API; confirm with the link. Provider mail is sent by Google, Exchange and Fastmail themselves, so monday must not also send an invitation mail on those accounts.

## Detail with sources

### Google Calendar API v3

Reading. `events.list` takes `timeMin` ("Lower bound (exclusive) for an event's end time") and `timeMax` ("Upper bound (exclusive) for an event's start time"), so overlapping events are returned; `singleEvents=true` expands recurrences and is required for `orderBy=startTime`; `maxResults` defaults to 250 with a ceiling of 2500; `eventTypes` filters `birthday`, `default`, `focusTime`, `fromGmail`, `outOfOffice`, `workingLocation`. `syncToken` cannot be combined with `timeMin`, `timeMax`, `orderBy`, `q` and others. https://developers.google.com/workspace/calendar/api/v3/reference/events/list

Sync. Store `nextSyncToken` from the last page; incremental results "will always contain deleted entries"; on 410 "trigger a full wipe of the client's store and a new full sync". No token lifetime is documented. https://developers.google.com/workspace/calendar/api/guides/sync and https://developers.google.com/workspace/calendar/api/guides/errors

Calendars. `calendarList.list` (max 250 per page, own `syncToken`) returns `accessRole` in `freeBusyReader`, `reader`, `writerWithoutPrivateAccess`, `writer`, `owner`, and `conferenceProperties.allowedConferenceSolutionTypes` which is the runtime check for Meet support. https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list

Scopes. `calendar.events` (read and write events on all calendars), `calendar.events.readonly`, `calendar.freebusy`, `calendar.calendarlist.readonly`, plus granular `calendar.events.owned`, `calendar.events.freebusy`, `calendar.app.created`. Google's guidance: "choose the most narrowly focused scope possible". The Calendar auth page does not label scopes as sensitive or restricted; the general scopes page says sensitive scopes require review. Treat all Calendar data scopes as sensitive (basic plus additional verification) until the Cloud Console consent screen says otherwise (unverified). https://developers.google.com/workspace/calendar/api/auth and https://developers.google.com/identity/protocols/oauth2/scopes and https://developers.google.com/workspace/guides/configure-oauth-consent

Free/busy. `freebusy.query` takes `timeMin`, `timeMax`, `timeZone`, `items[].id`, `groupExpansionMax` (max 100), `calendarExpansionMax` (max 50); the response maps calendar id to `busy[]` of `{start, end}` and `errors[]` with reasons `groupTooBig`, `tooManyCalendarsRequested`, `notFound`, `internalError`. Workspace domain policy can cap sharing at free/busy for outsiders. Treat `notFound` as "not visible to you", not "no such user" (unverified beyond observed behaviour). https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query and https://developers.google.com/workspace/calendar/api/concepts/sharing

Create. `events.insert` requires `start` and `end`; `sendUpdates` is `all`, `externalOnly` or `none` (`sendNotifications` is deprecated); "Attendees receive the invitation from the organizer's email address"; "The event you create appears on all the primary Google Calendars of the attendees you included with the same event ID". `attendees[].email` is required per attendee; `responseStatus` values are `needsAction`, `declined`, `tentative`, `accepted`; `guestsCanModify` defaults false, `guestsCanInviteOthers` and `guestsCanSeeOtherGuests` default true. https://developers.google.com/workspace/calendar/api/v3/reference/events/insert and https://developers.google.com/workspace/calendar/api/v3/reference/events and https://developers.google.com/workspace/calendar/api/guides/create-events

Meet link. Send `conferenceDataVersion=1` and `conferenceData.createRequest` with a fresh `requestId` and `conferenceSolutionKey.type` `hangoutsMeet`; "The immediate response to this call might not yet contain the fully-populated conferenceData; this is indicated by a status code of pending". Entry points come back as `entryPoints[]` with `entryPointType` in `video`, `phone`, `sip`, `more` and a `uri`. Whether consumer gmail.com accounts can create Meet links through the API is not stated on a developer page; use `allowedConferenceSolutionTypes` as the check (unverified). https://developers.google.com/workspace/calendar/api/guides/create-events

Import. `events.import` adds "a private copy of an existing event" keyed by `iCalUID`, has no `sendUpdates`, and only accepts `eventType` `default`. This is how a parsed mail invitation could be placed on a Google calendar if the user's setting kept it off. https://developers.google.com/workspace/calendar/api/v3/reference/events/import

Push. `events.watch` body: `id`, `type: "web_hook"`, `address` (HTTPS with a valid certificate), optional `token`, `expiration`, `params.ttl` (default 604800 seconds). Headers on delivery: `X-Goog-Channel-ID`, `X-Goog-Message-Number`, `X-Goog-Resource-ID`, `X-Goog-Resource-State` (`sync`, `exists`, `not_exists`), `X-Goog-Resource-URI`. Notifications "do not include a message body", so the handler re-lists with the stored `syncToken`. Stop with `channels.stop`. An older localised copy of the guide still requires domain verification of the webhook host; the current English page does not mention it, so test with the real project. There is no Pub/Sub option. https://developers.google.com/workspace/calendar/api/guides/push and https://developers.google.com/workspace/calendar/api/v3/reference/events/watch and https://developers.google.com/workspace/calendar/api/v3/reference/channels/stop

RSVP through the API. "The only event change that is propagated from attendees back to the organizer is the attendee's response status, stored in the attendees[].responseStatus property"; use `update` (or `patch`, which costs 3 quota units and overwrites array fields, so send the whole `attendees[]` with the `self: true` entry changed) plus `sendUpdates`. https://developers.google.com/workspace/calendar/api/concepts/inviting-attendees-to-events and https://developers.google.com/workspace/calendar/api/v3/reference/events/patch

Inbound invitations. The user setting "Add invitations to my calendar" has three values: "From everyone" (all invitations added), "Only if the sender is known" (contacts, same organisation, or prior interaction; otherwise the mail offers Add to calendar and RSVP), and "When I respond to the invitation in email". The default is from everyone; the known-senders option shipped July 2022 for Workspace and personal accounts, and admins can set a domain default. https://support.google.com/calendar/answer/13159188 and https://workspaceupdates.googleblog.com/2022/07/invitations-from-known-senders-only-google-calendar.html and https://knowledge.workspace.google.com/admin/calendar/automatically-add-events-to-calendars

Replies by mail to a Google organizer. Google's August 2026 announcement of the per-event "Get an email when guests respond" toggle (on by default) says that when it is off "responses from third-party calendar users won't register", which confirms that with it on Google does process iMIP REPLY mail from other systems into the guest list. A reply written in Outlook "is indeed sent via email but it's not stored as a note in the calendar event". https://workspaceupdates.googleblog.com/2026/08/suppress-email-responses-to-calendar-invitations-and-updates.html and https://support.google.com/a/users/answer/156467

Quotas and pricing. 10000 requests per minute per project, 600 per minute per user per project, 1000000 per day per project (no increase possible on the daily limit). "All standard use of the Google Calendar API is available at no additional cost. Exceeding the quota request limits is planned to incur charges to your Google Cloud billing account later in 2026", with at least 90 days notice; projects created on or after 2026-05-01 are on the new tiering. Over-quota returns 403 or 429 `usageLimits`; use exponential backoff. https://developers.google.com/workspace/calendar/api/guides/quota

Recent changes. 2026-07-14 `showOwnOrganizationOnly` on `calendarList.list`; 2026-07-07 `writerWithoutPrivateAccess` role and event labels via `eventLabelVersion=1`; 2026-05-01 quota tiering; 2025-10-27 `dataOwner` on secondary calendars. No new scopes and no change to invite handling in the window. https://developers.google.com/workspace/calendar/release-notes

### Microsoft Graph v1.0

Reading. `GET /me/events` returns "single instance meetings and series masters"; `GET /me/calendarView?startDateTime=&endDateTime=` returns "the occurrences, exceptions, and single instances of events" in the window, with times "interpreted using the timezone offset specified in the value" and UTC when none. `Prefer: outlook.timezone="..."` sets the zone of returned times; `Prefer: outlook.body-content-type="text"` avoids HTML bodies. https://learn.microsoft.com/en-us/graph/api/user-list-events?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/api/user-list-calendarview?view=graph-rest-1.0

Delta. v1.0 only offers `GET /me/calendarView/delta?startDateTime=&endDateTime=`; the response ends in `@odata.nextLink` or `@odata.deltaLink`; `$select`, `$filter`, `$orderby` are unsupported; `Prefer: odata.maxpagesize` works. Quirk: `@removed` entries include events "outside the date range and that have been added, deleted, or updated since the previous delta call", so filter them by range. "To track the changes in multiple calendars, you need to track each calendar individually." A date-unbounded `/me/events/delta` exists only in beta. No maximum window is documented. https://learn.microsoft.com/en-us/graph/api/event-delta?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/delta-query-events

Calendars and permissions. `GET /me/calendars` returns `allowedOnlineMeetingProviders`, `defaultOnlineMeetingProvider`, `canEdit`, `owner`. Delegated `Calendars.Read`, `Calendars.ReadWrite`, `Calendars.ReadBasic` and `Calendars.Read.Shared` do not need admin consent and are available to personal Microsoft accounts. https://learn.microsoft.com/en-us/graph/api/user-list-calendars?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/permissions-reference

Free/busy. `POST /me/calendar/getSchedule` takes `schedules[]` (SMTP addresses of users, lists or resources), `startTime`, `endTime`, `availabilityViewInterval` (default 30, min 5, max 1440 minutes) and returns per address an `availabilityView` string (0 free or working elsewhere, 1 tentative, 2 busy, 3 out of office) plus `scheduleItems[]` and `workingHours`. Personal accounts: "Not supported". https://learn.microsoft.com/en-us/graph/api/calendar-getschedule?view=graph-rest-1.0

findMeetingTimes. `POST /me/findMeetingTimes` with `attendees[]` (`type` `required` or `resource`), `timeConstraint` (`activityDomain` `work` default, `personal`, `unrestricted`; `timeSlots[]`), `meetingDuration` as ISO 8601 (`PT1H`, default 30 min), `maxCandidates`, `isOrganizerOptional`, `returnSuggestionReasons`, `minimumAttendeePercentage` (default 50). Confidence: free counts 100 percent, unknown 49, busy 0, averaged. Needs delegated `Calendars.Read.Shared`; personal accounts and application permissions are not supported. `emptySuggestionsReason` values are on the resource page and were not re-read (unverified). https://learn.microsoft.com/en-us/graph/api/user-findmeetingtimes?view=graph-rest-1.0

Create. `POST /me/events`: "When you create an event that includes attendees, the server sends invitations to all attendees. This ensures consistency between the organizer's and attendees' views of the event and can't be configured." Attendees are `{ emailAddress: { address, name }, type: "required" }` (also `optional`, `resource`); up to 500. `isOnlineMeeting: true` with `onlineMeetingProvider: "teamsForBusiness"` (enum also `skypeForBusiness`, `skypeForConsumer`, `unknown`) returns `onlineMeeting.joinUrl`; `onlineMeetingUrl` is being deprecated. Check `allowedOnlineMeetingProviders` on the calendar first; once set, the provider cannot be changed. `transactionId` makes retries idempotent and cannot be changed later. `responseRequested` defaults true. https://learn.microsoft.com/en-us/graph/api/user-post-events?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/api/resources/event?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/outlook-calendar-online-meetings

Update. `PATCH /me/events/{id}`: a body with only `attendees` "sends a meeting update to only the attendees that have changed"; updating a series master and separately updated instances sends one mail per item. https://learn.microsoft.com/en-us/graph/api/event-update?view=graph-rest-1.0

Push. `POST /subscriptions` with `resource` `/me/events` or `/users/{id}/events`, `changeType` `created,updated,deleted`, `notificationUrl` (HTTPS, publicly reachable), `clientState` (max 128 chars, validate it), `expirationDateTime` up to 10080 minutes ("under seven days") for Outlook `message`, `event`, `contact`, or 1440 minutes with resource data. Graph validates the URL by POSTing `?validationToken=` and expects the token echoed as `text/plain` within 10 seconds; deliveries expect a 2xx within 3 seconds and are retried for up to 4 hours. Lifecycle notifications via `lifecycleNotificationUrl` carry `reauthorizationRequired`, `subscriptionRemoved`, `missed`; after `missed`, "perform a full data resync using the delta query". Rich notifications with encrypted resource data are supported for `event` on v1.0. Limit: 1000 active subscriptions per mailbox across all apps. https://learn.microsoft.com/en-us/graph/outlook-change-notifications-overview and https://learn.microsoft.com/en-us/graph/api/resources/subscription?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks and https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events

RSVP. `POST /me/events/{id}/accept`, `tentativelyAccept`, `decline` take `comment`, `sendResponse` (default true) and, for the latter two, `proposedNewTime` (requires `sendResponse: true`); they return 202. A request "arrives in an invitee's mailbox as an eventMessage instance with the meetingMessageType of meetingRequest. In addition, Outlook automatically creates an event instance in the invitee's calendar, with the showAs property as tentative"; the `event` navigation property links the two. `meetingMessageType` values: `none`, `meetingRequest`, `meetingCancelled`, `meetingAccepted`, `meetingTentativelyAccepted`, `meetingDeclined`. Replies land in the organizer's mailbox as `eventMessageResponse` with `responseType` and `proposedNewTime`. https://learn.microsoft.com/en-us/graph/api/event-accept?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/api/resources/eventmessage?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/api/resources/eventmessagerequest?view=graph-rest-1.0 and https://learn.microsoft.com/en-us/graph/api/resources/eventmessageresponse?view=graph-rest-1.0

Replies by mail to an Exchange organizer. Outlook's iCalendar spec (covering classic and new Outlook) says on REPLY import only the first VEVENT is used, `UID` must match, "Exactly one ATTENDEE property MUST have the PARTSTAT parameter set or the import fails", `SEQUENCE` resolves out of order delivery, and a REPLY from an uninvited user is shown but ignored. Server side, the Calendar Attendant (`AutomateProcessing` `AutoUpdate` for user mailboxes) "processes meeting requests and responses"; `AddNewRequestsTentatively` defaults to true; `ProcessExternalMeetingMessages` defaults to false and governs resource mailboxes' handling of external requests, not user mailboxes. A processed response is stamped `PR_PROCESSED` and the organizer item's `PR_RECIPIENT_TRACKSTATUS` becomes `respAccepted`, `respDeclined` or `respTentative`. https://learn.microsoft.com/en-us/openspecs/exchange_standards/ms-stanoical/fa3c5473-b0d3-4a9a-aec0-3d42cd80a1ec and https://learn.microsoft.com/en-us/powershell/module/exchangepowershell/set-calendarprocessing and https://learn.microsoft.com/en-us/troubleshoot/outlook/calendaring/meeting-tracking-tab-not-updated

Throttling and pricing. Outlook limits per app and mailbox: "10,000 API requests in a 10-minute period", "Four concurrent requests", 150 MB upload per 5 minutes; batches run at most 4 Outlook requests in parallel. Calendar, mail and subscriptions are not metered. https://learn.microsoft.com/en-us/graph/throttling-limits and https://learn.microsoft.com/en-us/graph/metered-api-list

Recent changes. Outlook REST is decommissioned (March 2024), Graph is the only API. July 2026 preview adds Web Push fields (`vapidPublicKey`, `webPushEncryptionP256dhPublicKey`, `webPushEncryptionSecret`) on `subscription` "without operating a public webhook"; whether Outlook resources are covered is not stated, and it is beta. August 2026 preview adds anonymous free/busy sharing permissions. https://learn.microsoft.com/en-us/outlook/rest/compare-graph and https://learn.microsoft.com/en-us/graph/whats-new-overview

### CalDAV (RFC 4791) and Fastmail

Discovery (RFC 6764 section 6). SRV lookup `_caldavs._tcp` on the mail domain, TXT `path` or `/.well-known/caldav` (server MUST redirect to the context path), PROPFIND for `DAV:current-user-principal` (RFC 5397), then `CALDAV:calendar-home-set` on the principal, then PROPFIND Depth 1 on the home; each calendar advertises `CALDAV:supported-calendar-component-set`. Fastmail live: `_caldavs._tcp.fastmail.com` resolves to port 443 and `https://caldav.fastmail.com/.well-known/caldav` 301s to `/dav/calendars`; principal path is `/dav/principals/user/<user@domain>/`. https://www.rfc-editor.org/rfc/rfc6764.txt and https://www.rfc-editor.org/rfc/rfc5397.html and https://www.rfc-editor.org/rfc/rfc4791.html and https://www.fastmail.help/hc/en-us/articles/1500000278342-Server-names-and-ports and https://www.fastmail.help/hc/en-us/articles/360058752934-Manual-setup-of-Calendar-on-Mac

Reading. `CALDAV:calendar-query` REPORT with `comp-filter VCALENDAR > VEVENT > time-range start end` (UTC, start inclusive, end exclusive; "Time range tests MUST consider every recurrence instance"), requesting `DAV:getetag` and `CALDAV:calendar-data`; `calendar-multiget` fetches by href. `CALDAV:expand` (9.6.5) returns one component per instance but "MUST NOT use recurrence properties" and "MUST NOT have reference to or include VTIMEZONE components", so use it only for a rendered view and keep the master resource for editing. `getetag` is a strong ETag on every calendar object. https://www.rfc-editor.org/rfc/rfc4791.html#section-7.8 and https://www.rfc-editor.org/rfc/rfc4791.html#section-9.6.5

Writes. "New calendar object resources MUST be created with a PUT request targeted at an unmapped URI" with `If-None-Match: *`; updates PUT to the mapped URI with `If-Match`; DELETE is plain WebDAV. For events with attendees RFC 6638 says clients "SHOULD use the If-Schedule-Tag-Match header ... instead of HTTP ETag-based precondition tests" because attendee replies change the ETag but not the `Schedule-Tag`. Re-GET after PUT: the server rewrites `SCHEDULE-STATUS` parameters. https://www.rfc-editor.org/rfc/rfc4791.html#section-5.3.2 and https://www.rfc-editor.org/rfc/rfc6638.txt

Sync. RFC 6578 `DAV:sync-collection` REPORT with an opaque `DAV:sync-token` and `DAV:sync-level 1`; removed members come back with status 404; a stale token fails the `DAV:valid-sync-token` precondition (403) and needs a full resync. `CS:getctag` is an Apple extension now "deprecated in favor of support for the WebDAV Sync REPORT". Cyrus (Fastmail's backend) lists RFC 6578 as supported. https://www.rfc-editor.org/rfc/rfc6578.html and https://raw.githubusercontent.com/apple/ccs-calendarserver/master/doc/Extensions/caldav-ctag.txt and https://www.cyrusimap.org/imap/rfc-support.html

Push. None in the standards. `draft-bitfire-webdav-push` is a GitHub-rendered draft from the DAVx5 authors (Web Push RFC 8030 with VAPID); the IETF datatracker has no document by that name as of 2026-09-16, and only Nextcloud and DAVx5 have demonstration support. Apple's push discovery is APNs-only. Poll. https://bitfireat.github.io/webdav-push/draft-bitfire-webdav-push-00.html and https://datatracker.ietf.org/api/v1/doc/document/?name__contains=webdav-push and https://raw.githubusercontent.com/apple/ccs-calendarserver/master/doc/Extensions/caldav-pubsubdiscovery.txt

Free/busy. `CALDAV:free-busy-query` REPORT (RFC 4791 7.10) returns a VFREEBUSY for calendars the user can read (`CALDAV:read-free-busy`). Other users need RFC 6638: POST an iCalendar `METHOD:REQUEST` with one `VFREEBUSY`, `ORGANIZER` set to one of the requester's `calendar-user-address-set` values and `ATTENDEE` per queried user, to `schedule-outbox-URL`; the response is `CALDAV:schedule-response` with a `request-status` (for example `2.0;Success` or `3.7;Invalid calendar user`) and a VFREEBUSY per recipient. This only works for users the server knows. Whether Fastmail exposes cross-user free/busy this way is unverified. https://www.rfc-editor.org/rfc/rfc4791.html#section-7.10 and https://www.rfc-editor.org/rfc/rfc6638.txt

Scheduling. Capability is the `calendar-auto-schedule` token in the `DAV:` header of OPTIONS. Organizer PUT of a VEVENT with `ATTENDEE`s makes the server send an iTIP REQUEST per attendee with `SCHEDULE-AGENT=SERVER` (the default); modifying re-sends; DELETE sends CANCEL. Attendee side (3.2.2.3): "If the Attendee changes one or more PARTSTAT iCalendar property values on any component ... then the server MUST deliver an iTIP REPLY scheduling message to the Organizer". `Schedule-Reply: F` on DELETE suppresses the automatic DECLINED reply. Fastmail confirmed this in 2015: "create a new event with attendees from your computer or mobile device - invitation emails are automatically sent to all attendees" and "update your participation status ... an RSVP email is automatically sent". https://www.rfc-editor.org/rfc/rfc6638.txt and https://www.fastmail.com/blog/announcing-caldav-scheduling-support-for-clients/

Fastmail inbound invitations. Fastmail parses iMIP on delivery (headers `X-ME-Cal-Method`, `X-ME-Cal-UID`) and by default adds new invitations from contacts to the default calendar and applies updates to events already on the calendar; it never auto-sends an RSVP. The current setting offers three modes (auto-add new and apply updates, only apply updates to events you RSVPed, never). Mail RSVP buttons "send a response to the sender via email". https://www.fastmail.com/blog/automatic-invitatation-processing/ and https://www.fastmail.help/hc/en-us/articles/360058752694-Calendar-events-and-invitations

Fastmail auth and JMAP. CalDAV requires an app password or OAuth; `OPTIONS https://caldav.fastmail.com/dav/` advertises `Basic` and `Bearer`. Fastmail's developer page says calendars are "via CalDAV. We will be opening up JMAP access as well, as soon as the specification is finalized"; `draft-ietf-jmap-calendars-29` is in the RFC Editor queue (state "Stream Hold" as of 2026-09-16) and now references JSCalendar 2.0 (`draft-ietf-calext-jscalendarbis`) rather than RFC 8984. Plan CalDAV for v1 with a JMAP Calendars adapter later. https://www.fastmail.com/dev/ and https://datatracker.ietf.org/doc/draft-ietf-jmap-calendars/ and https://jmap.io/spec/index.html

Other servers, one line each. sabre/dav (Baikal) implements RFC 6638 since 2.1.0 including free/busy for server users and optional iMIP via `mail()`, no Schedule-Tag. Nextcloud sends invitation mail when configured and has instance-wide free/busy. Radicale documents free-busy reports and sync tokens but not RFC 6638, so assume no implicit scheduling. iCloud requires an app-specific password and does not document scheduling behaviour for third parties. https://sabre.io/dav/scheduling/ and https://docs.nextcloud.com/server/stable/admin_manual/groupware/calendar.html and https://radicale.org/v3.html and https://support.apple.com/en-us/102654

### Invites in mail: iCalendar, iTIP and iMIP

This is the part every account type shares. Even Google and Microsoft accounts get invitations from people on other systems, so the mail-side parser is not optional.

The wire format (RFC 5545).

- A `VEVENT` needs `UID` and `DTSTAMP`; `DTSTART` is required unless a `METHOD` is present (3.6.1). In practice every invite has all three plus `DTEND` or `DURATION`. https://www.rfc-editor.org/rfc/rfc5545.html#section-3.6.1
- `ATTENDEE` carries what the RSVP bar needs: `CN`, `ROLE` (`CHAIR`, `REQ-PARTICIPANT` default, `OPT-PARTICIPANT`, `NON-PARTICIPANT`), `PARTSTAT` (for VEVENT `NEEDS-ACTION` default, `ACCEPTED`, `DECLINED`, `TENTATIVE`, `DELEGATED`), `RSVP` (`TRUE`/`FALSE`, default `FALSE`), `CUTYPE` (`INDIVIDUAL`, `GROUP`, `RESOURCE`, `ROOM`, `UNKNOWN`), `DELEGATED-TO`, `DELEGATED-FROM`. https://www.rfc-editor.org/rfc/rfc5545.html#section-3.2.12
- `SEQUENCE` (3.8.7.4) is the revision the organizer bumps on a material change; `RECURRENCE-ID` (3.8.4.4) with optional `RANGE=THISANDFUTURE` addresses one instance or a tail; `STATUS` for VEVENT is `TENTATIVE`, `CONFIRMED` or `CANCELLED` (3.8.1.11). https://www.rfc-editor.org/rfc/rfc5545.html#section-3.8.7.4
- Time zones: "An individual VTIMEZONE calendar component MUST be specified for each unique TZID parameter value specified in the iCalendar object" (3.2.19). Exchange uses Windows zone names such as `Pacific Standard Time`; map TZID to IANA (CLDR `windowsZones.xml`) and fall back to the embedded VTIMEZONE rules only when no mapping exists. https://www.rfc-editor.org/rfc/rfc5545.html#section-3.2.19
- Lines fold at 75 octets (3.1); text values escape `\,` `\;` `\\` `\n` (3.3.11). Use a parser. https://www.rfc-editor.org/rfc/rfc5545.html#section-3.1
- RFC 7986 adds `CONFERENCE` (5.11: a URI with `FEATURE` in `AUDIO`, `VIDEO`, `PHONE`, `CHAT`, `SCREEN`, `FEED`, `MODERATOR`, and `LABEL`), `COLOR`, `IMAGE`, `NAME`, `URL`, `REFRESH-INTERVAL`, `SOURCE`. Google and Microsoft mostly put meeting links in `LOCATION`, `DESCRIPTION` and vendor properties, so the link extractor must look at all of them. https://www.rfc-editor.org/rfc/rfc7986.html#section-5.11
- Vendor properties: MS-OXCICAL (revision 15.0, May 2025) defines the `X-MICROSOFT-*` set, for example `X-MICROSOFT-CDO-BUSYSTATUS` (on import Outlook ignores `TRANSP` when it is present) and `X-MICROSOFT-CDO-INTENDEDSTATUS`. https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxcical/cd68eae7-ed65-4dd3-8ea7-ad585c76c736 and https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxcical/a685a040-5b69-4c84-b084-795113fb4012

The scheduling protocol (RFC 5546).

- Who sends what (1.4): organizer sends `PUBLISH`, `REQUEST`, `ADD`, `CANCEL`, `DECLINECOUNTER`; attendee sends `REPLY`, `REFRESH`, `COUNTER` (and `REQUEST` only for delegation). https://www.rfc-editor.org/rfc/rfc5546.html#section-1.4
- A VEVENT `REPLY` (3.2.3) carries `UID` (must equal the REQUEST's), `DTSTAMP`, `ORGANIZER`, exactly one `ATTENDEE` (the replier with the new `PARTSTAT`), `SEQUENCE` if non-zero, and `RECURRENCE-ID` when replying to one instance. Exchange's own REPLY example is exactly this plus `SUMMARY:Accepted: ...` and a few `X-MICROSOFT-*` lines. https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.3 and https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxcical/703406b8-e8ed-4603-9b33-4994d09d60fd
- `SEQUENCE` (2.1.4): the organizer MUST increment it when `DTSTART`, `DTEND`, `DURATION`, `DUE`, `RRULE`, `RDATE`, `EXDATE` or `STATUS` change; `REPLY`, `REFRESH`, `COUNTER`, `DECLINECOUNTER` never do. A REQUEST with a higher SEQUENCE than the stored copy means "ask the user again"; same SEQUENCE and newer DTSTAMP is a cosmetic update that keeps the existing PARTSTAT. https://www.rfc-editor.org/rfc/rfc5546.html#section-2.1.4
- `CANCEL` (3.2.5): `METHOD:CANCEL`, one or more VEVENTs with the same UID, `SEQUENCE`, `ORGANIZER`, `DTSTAMP`, `UID`; `STATUS:CANCELLED` for a full cancellation; `RECURRENCE-ID` for one instance; `ATTENDEE` lines list only removed people on a partial cancel. https://www.rfc-editor.org/rfc/rfc5546.html#section-3.2.5
- `COUNTER` and `DECLINECOUNTER` (3.2.7, 3.2.8) implement "propose a new time"; out of v1.

How it travels by email (RFC 6047).

- The part is `Content-Type: text/calendar; method=REQUEST; charset=UTF-8` and the MIME `method` parameter MUST equal the `METHOD` property (2.4). Different methods in one message MUST be split across `multipart/mixed`; `multipart/alternative` is the normal wrapper for `text/plain`, `text/html` and `text/calendar` together. https://www.rfc-editor.org/rfc/rfc6047.html#section-2.4
- Identity MUST be read from `ORGANIZER` and `ATTENDEE` inside the part, not from `From`, `Sender` or `Reply-To` (2.3), and implementations SHOULD verify the creator before acting (2.2.1). For monday: trust a REQUEST only when `From` matches `ORGANIZER`, apply a REPLY to an event we organise only when `From` matches the single `ATTENDEE`, and show a warning banner on mismatch. https://www.rfc-editor.org/rfc/rfc6047.html#section-2.3
- Real senders: Google and Exchange send `multipart/alternative` with `text/plain`, `text/html` and `text/calendar; method=REQUEST`; Google also attaches the same object as `application/ics; name="invite.ics"`. Microsoft's own note describes Google invitations reaching Outlook as an "ICS file that is attached to the invitation email". https://learn.microsoft.com/en-us/troubleshoot/outlook/calendaring/no-meeting-reminder-for-google-calendar-invites
- Parsing rule: walk the MIME tree, take the first `text/calendar` part (the `application/ics` attachment is a duplicate), read `METHOD`, key on `UID` + `RECURRENCE-ID`. Thunderbird does exactly this in `calItipUtils.sys.mjs`: find the existing item by UID, compare `SEQUENCE` (falling back to `X-MICROSOFT-CDO-APPT-SEQUENCE`) then `DTSTAMP`, pick the bar (`imipAcceptButton`, `imipTentativeButton`, `imipDeclineButton`, or the `*RecurrencesButton` variants), and send the REPLY through the mail account via `CalItipMessageSender`. https://searchfox.org/comm-central/source/calendar/base/modules/utils/calItipUtils.sys.mjs

RSVP by mail versus API, the rule for monday.

- Google, Microsoft 365 and Fastmail already put the invitation on the calendar (subject to the user settings above). On those accounts the invite bar reads the event's current PARTSTAT from the calendar module and RSVPs through the calendar API; the provider sends the reply mail. Never turn the mail part into a calendar write on these accounts, it would double-process.
- Generic CalDAV without `calendar-auto-schedule`, and IMAP/SMTP accounts, are the only cases where monday builds the iMIP REPLY (and REQUEST or CANCEL when organising) and sends it over SMTP. The body is a `text/calendar; method=REPLY` part plus a short `text/plain` alternative, `From` equal to the attendee address.
- Both Google and Exchange organizers process a well-formed REPLY mail from a third-party client; Google does so only while the per-event "Get an email when guests respond" toggle is on (default on, August 2026).

## Open risks

1. Free/busy across providers is partial and the failure mode is silent: Google returns `notFound` per calendar, Graph refuses on personal accounts, CalDAV works only intra-org. The agent must say "I could not see X's calendar" rather than pick a slot as if it had.
2. Google Meet through the API on consumer gmail.com accounts is not documented on a developer page; rely on `allowedConferenceSolutionTypes` at runtime and test with a personal account.
3. Google push may still require domain verification of the webhook host (present in an older localised guide, absent from the current English page). Test with the real Cloud project before relying on it.
4. Google quota billing for over-quota use starts "later in 2026" with new tiering for projects created on or after 2026-05-01; a self-hosted install uses the user's own project, so document the limits in onboarding.
5. Graph `calendarView/delta` has no documented maximum window; the `@removed` list includes out-of-range changes and must be filtered. Sync per calendar, not per mailbox.
6. Graph subscriptions expire in under seven days and are dropped on password reset or account disable; the sidecar deployment has no public URL at all, so polling is the baseline and webhooks are a cloud-only optimisation. The July 2026 Web Push preview on `subscription` might remove the public URL requirement later; it is beta and not confirmed for Outlook resources.
7. Fastmail cross-user free/busy over the RFC 6638 outbox and Fastmail exposing `urn:ietf:params:jmap:calendars` to third-party tokens are both unverified; JMAP Calendars (`draft-ietf-jmap-calendars-29`) is still in the RFC Editor queue.
8. Exchange processing of an external iMIP REPLY into the organizer's tracking is supported by the Outlook iCalendar spec and the Calendar Attendant docs but not by a single explicit statement; test with a Microsoft 365 tenant. The same applies to Fastmail organizers.
9. Google's per-event "Get an email when guests respond" toggle (August 2026), when off, discards replies from third-party clients entirely. Monday cannot detect it; the RSVP UI should not claim the organizer saw the reply on IMAP-only accounts.
10. Google's "Only if the sender is known" setting means invitations sent by monday from a fresh address may not land on the recipient's calendar and may show an unknown-sender banner; the invitation mail still arrives.
11. `CALDAV:expand` strips RRULE and VTIMEZONE; storing expanded data would lose the ability to edit the series. Expand locally with `ical.js` and keep master resources.
12. Time zone names from Exchange are Windows names; a missing mapping table would render invites at the wrong hour. Ship the CLDR mapping and a test corpus of real Google, Exchange and Fastmail invites.
13. WebDAV Push is not an IETF draft and has demonstration-only implementations; do not plan on it.
