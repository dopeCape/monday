# Encryption at rest with a user-held key, and what it does to search and AI

Research note for issue #5 (part of the wayfinder map #1). Written 2026-09-16. Sources are primary where one exists; each claim links to the page it came from. Things that could not be verified are marked as such.

## Summary

The tension in the ticket is real and cannot be engineered away: if the cloud server computes briefs, tags and workflows while the laptop is closed, the server process holds the key and reads plaintext at that moment. Every product that keeps the server blind (Proton, Tuta, Skiff) pays for it by moving all content features to the client, and every product that offers server-side content features (Fastmail, Inbox Zero, Zero) keeps plaintext access. There is no third option, only choices about how narrow the window is and what is written to disk.

The recommendation for v1 is therefore an honest middle: **application-layer envelope encryption with the root key resident only in the server's process memory**, provisioned by the client and, on the cloud server, optionally sealed at rest by a systemd encrypted credential bound to the host so the service can restart unattended. Postgres never sees a key or a plaintext body. Disk images, volume snapshots, database dumps, backups and a leaked database password yield ciphertext. A live compromise of the running host does not, and the product must say so in plain words.

Search lives on the client. The client already decrypts everything it syncs, SQLite FTS5 ships in the Tauri SQL stack, and a client index is the only place a full-text index of encrypted bodies can exist without becoming a plaintext copy of them. The server keeps a headers-only index for agent-driven lookups while the laptop is closed and decrypts a bounded candidate set when a workflow needs body text.

### Recommendation in one paragraph

Model A below. Per-message data keys (AES-256-GCM), wrapped by a per-workspace key, wrapped by a root key the user generated on their device and keeps as a recovery file. The server holds the root key in memory only. Bodies, subjects, attachments, and every artefact derived from them (briefs, tags with their reasoning, summaries, extracted attachment text, embeddings) are encrypted the same way. Header metadata needed for sync and routing (addresses, dates, thread and message ids, flags, labels, sizes) is plaintext. Interactive search is a client-side FTS5 index; the server offers headers-only FTS plus decrypt-and-filter for agents. Onboarding shows the sentence: "While your server is running it can read your mail, because it writes your briefs. Your disk, backups and database dumps cannot."

## The models compared

| | A. Key resident in server memory, unlocked at boot (recommended) | B. Key present only while a client session is open | C. Plaintext in Postgres, disk encryption only | D. Client-only (Proton/Tuta style) |
|---|---|---|---|---|
| Where bodies are encrypted | Bun server, before the INSERT | Bun server, before the INSERT | Not encrypted above the block device | Client, before upload |
| Where the key lives | Client keychain + recovery file; copy in server RAM; optional sealed copy on the server host (TPM2/host key) | Client keychain; server RAM only while a client is connected | Volume key on the host or with the cloud provider | Client only |
| Briefs while laptop closed | Yes | No (server is locked when the client is away) | Yes | No |
| Server-side full-text search | Headers only, plus decrypt-and-filter of a candidate set | Headers only | Full Postgres FTS with ranking and snippets | None |
| Client-side search | FTS5 over the cache (required) | FTS5 over the cache (required) | Optional (offline benefit only) | FTS5 or equivalent (required) |
| Protects against stolen disk, snapshot, backup, pg_dump, leaked DB credentials | Yes | Yes | Disk theft yes; snapshots, dumps and credential leaks no | Yes |
| Protects against live root on the host | No | Only while no client is connected | No | Yes |
| Restart without the user present | Yes if the sealed credential is enabled; otherwise the server waits locked | No, waits for a client | Yes | n/a |
| Precedent | Dovecot mail-crypt, Posteo, mailbox.org Guard (all decrypt on the server with a server-held wrapped key) | Posteo (key unlocked per access) | Fastmail, mailcow default, Inbox Zero | Proton, Tuta, Skiff |
| Honest one-line claim | "The running server can read your mail; disks and dumps cannot" | "The server can read your mail only while you are connected" | "Only the disk is encrypted" | "The server never reads your mail" |

pgcrypto is not a row in the table because it is not a distinct model; it is a worse implementation of A or C. See the pgcrypto section below.

### Why A over B for v1

B is a real option and Posteo ships it, but it contradicts the requirement that started this ticket: briefs and workflows must run while the laptop is closed. B becomes a configuration knob on top of A ("lock the server when I disconnect"), not the default. It costs almost nothing to build later because the only difference is whether the server keeps the root key after the last client disconnects.

### Why A over C

C is what Fastmail argues for and is the cheapest to build, but the extra protection A buys covers exactly the failure modes a self-hoster is most likely to hit: an unencrypted `pg_dump` in an object store, a cloud volume snapshot, a reused database password, a SQL injection in a future endpoint. The cost is a few hundred lines of crypto code in the server and giving up Postgres FTS on bodies, which the client can do better anyway. The Postgres project itself frames disk encryption as protecting only against "the drives or the entire computer" being stolen and states it "does not protect against attacks while the file system is mounted" ([encryption-options](https://www.postgresql.org/docs/current/encryption-options.html)).

### Why not D

D is the only model where the claim "user-held key" is true in the strong sense, and it is incompatible with the server computing anything from content while the user is away. Proton says this directly about its own assistant: Scribe "does not train on your inbox data" and "cannot because of Proton Mail's zero-access encryption" ([proton.me](https://proton.me/blog/proton-scribe-writing-assistant)). If monday ever wants a D mode, it is the sidecar-only deployment (no cloud server): the key never leaves the laptop and briefs run only while it is open. That is a legitimate configuration and should be described as the strongest privacy setting, not a degraded one.

## Model A in detail

### Key hierarchy

Envelope encryption as defined by the KMS vendors: encrypt data with a data encryption key (DEK), encrypt the DEK with a key encryption key (KEK), store the wrapped DEK next to the data ([AWS KMS](https://docs.aws.amazon.com/kms/latest/developerguide/kms-cryptography.html#enveloping), [Google Cloud KMS](https://docs.cloud.google.com/kms/docs/envelope-encryption)). NIST's terms are data-encryption key and key-wrapping key, the latter providing "both confidentiality and integrity protection for other keys" ([NIST glossary, citing SP 800-57 Part 1 Rev. 5](https://csrc.nist.gov/glossary/term/key_wrapping_key)).

Proposed levels, top down:

1. **Root key (K_root)**, 32 random bytes generated on the user's device at first run. This is the "user-held key". Stored in the OS keychain on the client (the Rust `keyring` crate 4.x supports macOS Keychain, Windows Credential Manager, and Linux secret-service or keyutils stores, [docs.rs](https://docs.rs/keyring/latest/keyring/)), and exported once as a recovery file the user is told to keep. Never stored in Postgres.
2. **Workspace key (K_ws)** per mail account, random, wrapped by K_root, stored in Postgres wrapped. Rotating K_ws means re-wrapping DEKs, not re-encrypting bodies, which is the stated benefit of the envelope pattern ("re-encrypt only the data keys", AWS above).
3. **Data key (DEK)** per message (and per attachment), random, wrapped by K_ws, stored in the row next to the ciphertext. Google's guidance is "Generate a new DEK every time you write the data" ([Google Cloud KMS](https://docs.cloud.google.com/kms/docs/envelope-encryption)). One DEK per message also removes the AES-GCM random-nonce budget problem (2^32 messages per key with random nonces, per the [libsodium AEAD table](https://doc.libsodium.org/secret-key_cryptography/aead)) because each key encrypts one object; large attachments are chunked with a counter nonce under the same DEK.

Wrapping can be AES-256-GCM as well, or AES Key Wrap with padding ([RFC 5649](https://www.rfc-editor.org/rfc/rfc5649.html)); one primitive everywhere is simpler and the integrity property is the same.

### Cipher and runtime

AES-256-GCM through `crypto.createCipheriv` with a 12-byte random IV and the 16-byte auth tag. Node documents that tampering makes `decipher.final()` throw when the tag is set ([nodejs.org](https://nodejs.org/api/crypto.html)). Bun's `node:crypto` is listed as partially implemented and backed by BoringSSL; the gaps it names are CCM, OCB, XTS and chacha20-poly1305, not AES-GCM, and Bun's Web Crypto is "fully implemented" including ChaCha20-Poly1305 ([bun.sh](https://bun.sh/docs/runtime/nodejs-apis)). libsodium's recommendation is XChaCha20-Poly1305 or AEGIS-256 ([libsodium](https://doc.libsodium.org/secret-key_cryptography/aead)); XChaCha's 192-bit nonce would remove the nonce budget concern entirely, but it needs a userland library in Bun, and the per-message DEK already removes it. Stay with AES-256-GCM in v1.

Secrets in JavaScript memory cannot be reliably zeroed. Node's `--secure-heap` covers OpenSSL-internal allocations only ([nodejs.org CLI docs](https://nodejs.org/api/cli.html), [nodejs/node#30956](https://github.com/nodejs/node/issues/30956)) and Bun returns `undefined` from `secureHeapUsed()` ([bun.sh](https://bun.sh/docs/runtime/nodejs-apis)). This is another reason model A's threat model must exclude live memory access: it does not pretend to defend the key against root.

If the user prefers a passphrase to a recovery file, derive K_root with Argon2id: RFC 9106 recommends t=1, p=4, m=2 GiB, or t=3, p=4, m=64 MiB when memory constrained ([RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html)). Bun ships `argon2()` ([bun.sh](https://bun.sh/docs/runtime/nodejs-apis)). A passphrase weaker than a random 256-bit key is the trade the user makes for memorability; the default should be the random key plus recovery file.

### Provisioning the key to the server

- **Cloud server, first run.** The client connects over the authenticated channel (issue #13) and sends K_root to an `unlock` endpoint. The server keeps it in process memory. Nothing is written.
- **Cloud server, restart while the laptop is closed.** Two choices, exposed as a setting:
  - *Sealed auto-unlock (default on cloud).* The server host stores K_root as a systemd encrypted credential. `systemd-creds` encrypts with AES-256-GCM under a key derived from the TPM2 and/or the host key in `/var/lib/systemd/credential.secret`; the decrypted credential is exposed to the service in `$CREDENTIALS_DIRECTORY`, "placed in non-swappable memory", restricted to the service's user and "not propagated down the process tree" ([systemd.io/CREDENTIALS](https://systemd.io/CREDENTIALS/)). This is the same class of protection Posteo and Dovecot mail-crypt give (a server-held, wrapped key), with the wrapping key in the host's TPM instead of the user's password. An attacker who images the disk without the TPM gets nothing; an attacker with root on the running host gets everything. Non-systemd hosts (containers on a managed platform) fall back to an environment variable or mounted secret, which is what Bun's own docs say production secrets look like ([Bun.secrets docs](https://bun.com/docs/runtime/secrets)); that is weaker and the settings screen should say "sealed by the host" versus "stored by the platform".
  - *Manual unlock.* The server starts locked, serves metadata only, queues sync, and resumes briefs when a client next connects. This is model B's behaviour on restart and is the right default when the user has said "lock when I am away".
- **Sidecar server.** Runs beside the client; receives K_root from the client at launch, never persists it. When both servers run against one Postgres (issue #12) they share the same K_ws and DEKs, so either can decrypt.

### What is plaintext in Postgres

Encrypted (inside the envelope): body (all parts), subject, attachment bytes, extracted attachment text, and every derived artefact: brief text, tag rationale, summaries, workflow outputs that quote content, embeddings. The last item matters: text embeddings can be inverted, recovering "92% of 32-token text inputs exactly" ([Morris et al., EMNLP 2023](https://arxiv.org/abs/2310.06816)), so a plaintext pgvector column over encrypted bodies is a plaintext copy of the bodies. This means no server-side ANN index in v1; semantic search, if wanted, is a client-side feature or a decrypt-and-scan for agents.

Plaintext: message id, thread id, in-reply-to and references, from, to, cc, bcc (own sent mail), date, size, flags, labels and folders, list-unsubscribe presence, has-attachments, attachment names and MIME types, provider ids and sync cursors. These are needed for sync, threading and routing rules and are the same fields Proton leaves non-E2E and Tuta leaves unencrypted ([proton.me](https://proton.me/support/proton-mail-encryption-explained), [tuta.com](https://tuta.com/encryption)). Subject is content and goes in the envelope; routing rules that match on subject run in the Bun server after decrypt, which is cheap because the server holds the key anyway under model A. Tag names themselves (short labels like "invoice") are plaintext because they are labels; the tag's reasoning text is encrypted.

### Threat model, stated plainly

What model A defends against:

- Theft or imaging of the server disk, a cloud volume snapshot, or a hardware decommission.
- Leaked or misplaced backups and `pg_dump` output.
- Leaked Postgres credentials, SQL injection, or a read-only replica exposed by mistake. Postgres holds only ciphertext and wrapped keys.
- A hosting provider or co-tenant with storage-level access but no memory access to the running VM.

What it does not defend against:

- Root, a debugger, or a memory dump on the running server host. The key and plaintext are in the Bun process by design.
- A compromised server binary or supply chain (the server would ship plaintext wherever it likes).
- The mail provider. Gmail, Microsoft 365 and Fastmail hold the plaintext already; nothing on monday's server changes that.
- The AI provider. Briefs are computed by sending plaintext to a model API (issue #14). Encryption at rest changes nothing about what the model sees. Inbox Zero's approach of redacting credentials and card numbers before the call ([getinboxzero.com](https://docs.getinboxzero.com/essentials/security-and-data)) and a local model option are the levers here, not encryption.
- A compromised client device, which holds the key and the plaintext cache.

Fastmail's argument that a server without content access "reverts to a featureless blob store" ([fastmail.com](https://www.fastmail.com/blog/why-we-dont-offer-pgp/)) is correct, and model A does not dispute it; it keeps content access in the process and denies it to the storage.

## Search: where it lives and why

### Server-side FTS over encrypted bodies is a plaintext copy

A Postgres `tsvector` is "a sorted list of distinct lexemes" with positions and weights ([datatype-textsearch](https://www.postgresql.org/docs/current/datatype-textsearch.html)); with positions stored, word order is reconstructable modulo stemming and stop words. `to_tsvector` requires the plaintext document, GIN indexes contain "an index entry for each word (lexeme), with a compressed list of matching locations" ([textsearch-indexes](https://www.postgresql.org/docs/current/textsearch-indexes.html)), and `ts_headline` "uses the original document, not a tsvector summary" ([textsearch-controls](https://www.postgresql.org/docs/current/textsearch-controls.html)), so snippets need plaintext at query time. Any of these on the server is a plaintext derivative sitting in Postgres, which is the exact thing model A is meant to keep out of Postgres. Dovecot makes the same point structurally: mail-crypt encrypts mail, and the FTS index is a separate artefact that must be wrapped by a separate `fs-crypt` layer ([Dovecot mail-crypt](https://doc.dovecot.org/2.3/configuration_manual/mail_crypt_plugin/)). Stalwart states the consequence: "When encryption at rest is enabled, only message headers are stored in the full-text index" ([stalw.art](https://stalw.art/docs/storage/fts/)).

### Encrypted-index approaches do not give full-text search

Blind indexes (truncated HMAC of a normalised value) give equality only and leak equality and frequency; CipherSweet documents the sizing rule for the false-positive budget and warns that many blind indexes on one field let an observer infer identical plaintexts ([ciphersweet.paragonie.com](https://ciphersweet.paragonie.com/security)). CipherStash's EQL adds a bloom-filter "match" index over downcased 3-grams that is probabilistic, "order- and multiplicity-insensitive", and reveals "probabilistic token overlap, repeated token sets, and approximate token-set size"; their own guidance for sensitive content is "use storage-only encryption and filter a smaller candidate set after decryption in the application" ([cipherstash.com](https://cipherstash.com/docs/concepts/searchable-encryption), [EQL text reference](https://cipherstash.com/docs/reference/eql/text)). MongoDB Queryable Encryption, the most widely shipped searchable-encryption product, supports equality and range in GA, has prefix/suffix/substring only in preview, and lists `$text` as always unsupported ([mongodb.com](https://www.mongodb.com/docs/manual/core/queryable-encryption/reference/supported-operations/)). The academic literature explains why: searchable-encryption schemes are defined by a leakage profile, and leakage-abuse attacks recover queries and plaintext from it ([Cash, Grubbs, Perry, Ristenpart, CCS 2015](https://eprint.iacr.org/2016/718); [Islam, Kuzu, Kantarcioglu, NDSS 2012](https://www.ndss-symposium.org/ndss2012/ndss-2012-programme/access-pattern-disclosure-searchable-encryption-ramification-attack-and-mitigation/)). None of these give ranking, phrase search or snippets, and all of them are more code and more risk than the two honest options.

### Recommendation: client FTS5 for people, headers plus decrypt-and-filter for agents

**Client.** SQLite FTS5 over the client cache, as an external-content table so the index does not duplicate the bodies ([sqlite.org/fts5](https://www.sqlite.org/fts5.html)). Default `unicode61` tokenizer (diacritics folded); do not use `porter` because it "is designed for use with English language terms only". Columns: subject, from, to, body; rank with `bm25()` with a higher weight on subject; `snippet()` for result previews; `NEAR` and phrase queries come free; `:*` prefix for as-you-type. Add a second, small trigram-tokenized table over subject and addresses only if substring matching is wanted (trigram needs a 3-character minimum and supports indexed `LIKE`). Index size reference from the FTS5 docs: 1636 MiB of email produced a 743 MiB index with `detail=full`, 340 MiB with `detail=column`; `detail=full` is right for a mail client because `detail=column` drops phrase and NEAR queries. Run `merge` incrementally after sync batches rather than `optimize`.

FTS5 availability: `tauri-plugin-sql`'s `sqlite` feature enables sqlx's `sqlite` feature ([plugins-workspace Cargo.toml](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/Cargo.toml)), which expands to `sqlite-bundled` ([sqlx Cargo.toml](https://github.com/launchbadge/sqlx/blob/main/Cargo.toml)), and the bundled `libsqlite3-sys` build sets `-DSQLITE_ENABLE_FTS5` ([rusqlite build.rs](https://github.com/rusqlite/rusqlite/blob/master/libsqlite3-sys/build.rs)). If the client instead uses rusqlite directly with `bundled`, the same flag applies. Bun's `bun:sqlite` has FTS5 on Linux since 0.6.12 ([oven-sh/bun#3468](https://github.com/oven-sh/bun/discussions/3468)); a 2026 issue reports macOS builds shipping an older SQLite where FTS5 updates corrupt ([oven-sh/bun#31247](https://github.com/oven-sh/bun/issues/31247)), so the sidecar should not rely on `bun:sqlite` FTS5 without pinning and testing.

This is the model Proton ("The index is created in your browser and never leaves it", [proton.me](https://proton.me/support/search-message-content)), Tuta ("The search index is encrypted and stored locally on the client", [tuta.com](https://tuta.com/blog/first-search-encrypted-data)) and Skiff ("client-side search indexing algorithms", [skiff.com/security-model](https://skiff.com/security-model)) all converged on. Their limitation, one index per browser with a "how far back you can search" horizon, does not apply here because the Tauri client has a real SQLite file and syncs the whole mailbox.

**Server.** Postgres FTS (GIN on a generated `tsvector`, weight A for addresses) over the plaintext header fields only, plus `pg_trgm` on addresses for fuzzy matching ([pgtrgm](https://www.postgresql.org/docs/current/pgtrgm.html)). For agent tasks that need body text while the laptop is closed, the server narrows candidates by headers, labels, dates and tags, then decrypts the candidate set and filters in Bun. For a single user this is bounded and fine; it is exactly the CipherStash guidance quoted above. The tag layer is the important accelerator: tags the server already computed at ingest (encrypted rationale, plaintext label) let an agent ask "unpaid invoices from last month" without scanning bodies.

The `textsearch` limits (1 MB per `tsvector`, 2 KB per lexeme, [textsearch-limitations](https://www.postgresql.org/docs/current/textsearch-limitations.html)) become irrelevant on the server because it never indexes bodies; on the client FTS5 has no comparable per-document limit.

## pgcrypto: why not

- All pgcrypto functions "run inside the database server", so "all the data and passwords move between pgcrypto and client applications in clear text", and the docs' own advice is "If you cannot [trust both system and database administrator], then better do crypto inside client application" ([pgcrypto](https://www.postgresql.org/docs/current/pgcrypto.html)). Here "client application" is the Bun server.
- Keys passed as SQL parameters land in `log_statement` output ("Logged statements might reveal sensitive data", [runtime-config-logging](https://www.postgresql.org/docs/current/runtime-config-logging.html)) and in `pg_stat_activity.query` ([monitoring-stats](https://www.postgresql.org/docs/current/monitoring-stats.html)).
- The raw `encrypt()` family "don't provide any integrity checking", uses the user key directly as the cipher key, defaults the IV to all zeroes, offers only cbc/cfb/ecb (no authenticated mode), and the docs say usage "is discouraged" ([pgcrypto](https://www.postgresql.org/docs/current/pgcrypto.html)). `pgp_sym_encrypt` is better (S2K, integrity) but still runs in the database process with the passphrase in the statement.
- The Postgres "Encryption Options" page describes the column-encryption model as one where "the decrypted data and the decryption key are present on the server for a brief time" and can be intercepted "by someone with complete access to the database server" ([encryption-options](https://www.postgresql.org/docs/current/encryption-options.html)). Application-layer encryption removes the database from the trusted set entirely.

Transparent Data Encryption is not in core Postgres: the TDE wiki design page was last updated in 2022 and the PostgreSQL 18 release notes (September 2025) contain no TDE item ([wiki](https://wiki.postgresql.org/wiki/Transparent_Data_Encryption), [release-18](https://www.postgresql.org/docs/18/release-18.html)); PostgreSQL 19 is in beta as of this note ([release index](https://www.postgresql.org/docs/release/)). Percona's `pg_tde` requires their patched server and leaves system catalogs and `work_mem` spill files unencrypted ([pg_tde limitations](https://docs.percona.com/pg-tde/index/tde-limitations.html)); `pg_vault_tde` is a new extension (v1.7.1, announced 2026-09-10) with a KMS or HSM dependency ([postgresql.org news](https://www.postgresql.org/about/news/pg_vault_tde-v171-transparent-data-encryption-for-postgresql-17-and-18-3376/)). Both are TDE in the sense that the database process holds the key, so they protect the same things disk encryption does plus dumps, at the cost of a non-standard Postgres. For a self-hoster who may be on a managed Postgres, application-layer encryption is the only portable choice.

## How the comparable products land

- **Proton.** Body and attachments E2E; subject and addresses encrypted but not E2E ([encryption-explained](https://proton.me/support/proton-mail-encryption-explained)). Spam filtering and Sieve run in the pre-encryption window at delivery, "in memory", and Sieve filters "don't have access to the actual content" ([spam filtering post](https://proton.me/blog/encrypted-email-spam-filtering), [Sieve](https://proton.me/support/sieve-advanced-custom-filters)). Search index built and kept in the browser ([search](https://proton.me/support/search-message-content)). Scribe cannot read the inbox; a local-LLM mode exists ([Scribe](https://proton.me/support/proton-scribe-writing-assistant)).
- **Tuta.** Subjects, bodies, attachments, calendar, contacts and the search index encrypted; only addresses and dates in the clear ([tuta.com/encryption](https://tuta.com/encryption)). Search over an encrypted local index, now a full local mirror as of 2026-08 ([tuta.com](https://tuta.com/blog/tuta-mail-search-is-now-faster)). Second-stage spam filtering is on-device ML ([tuta.com](https://tuta.com/blog/tuta-improved-spam-filters)). Inbox rules match on sender and subject keywords ([release notes](https://tuta.com/blog/release-notes-2-8)); whether they execute client- or server-side is not stated in an official page.
- **Skiff.** Acquired by Notion, announced 2024-02-09, shut down 2024-08-09, forwarding until 2025-02-09 ([skiff.com](https://skiff.com/)). Its search library is still public in `skiff-apps` ([github](https://github.com/skiff-org/skiff-apps/tree/main/libs/skiff-front-search)); the design post is gone.
- **Posteo.** Crypto mail storage encrypts content, attachments and metadata with a key pair stored in Posteo's database "protected by your personal password", decrypted "only for the moment of access"; password reset and backup restore stop working ([posteo.de](https://posteo.de/en/help/how-do-i-activate-posteo-crypto-mail-storage)); disks are also LUKS ([posteo.de/encryption](https://posteo.de/en/site/encryption)). This is model B.
- **mailbox.org.** PGP applied by a server-side Sieve filter on arrival; the private key "will be temporarily unlocked on the server" with the Guard password ([kb.mailbox.org](https://kb.mailbox.org/en/private/encryption/read-encrypted-e-mails-with-guard/)); the Sent folder is not encrypted ([kb.mailbox.org](https://kb.mailbox.org/en/private/encryption/your-encrypted-mailbox/)). Also model B. No KB page states the effect on full-text search (unverified).
- **Fastmail.** Plaintext with disk encryption; explicitly argues that content access is what makes search, previews and spam checking possible ([fastmail.com](https://www.fastmail.com/features/security/)). Model C.
- **Stalwart.** OpenPGP or S/MIME encryption before write, per account; headers-only FTS as a consequence ([stalw.art](https://stalw.art/docs/encryption/), [FTS](https://stalw.art/docs/storage/fts/)). Model D at the storage layer.
- **Dovecot mail-crypt / mailcow.** Per-user or global key pairs; the user private key is unlocked by the login password from userdb ([Dovecot](https://doc.dovecot.org/2.3/configuration_manual/mail_crypt_plugin/)); mailcow uses one server-held global key ([mailcow](https://docs.mailcow.email/manual-guides/Dovecot/u_e-dovecot-mail-crypt/)). mailcow's default is effectively model A with the key on disk beside the data.
- **Inbox Zero / Zero.** Server-side AI over provider APIs with plaintext; Inbox Zero does not persist bodies, redacts secrets before LLM calls, supports Ollama ([privacy](https://www.getinboxzero.com/privacy), [LLM setup](https://docs.getinboxzero.com/hosting/llm-setup)); Zero caches threads in Cloudflare Durable Objects and R2 with no stated encryption ([github](https://github.com/Mail-0/Zero)). Model C.

## Open risks

1. **Recovery.** Losing the recovery file and every client keychain loses the mailbox cache on the server, though not the mail itself, which still lives at the provider and can be re-synced. Onboarding must make the recovery file a required step, and re-sync must be a documented recovery path. Posteo's "no forgotten-password function" is the honest precedent.
2. **The sealed credential is host-bound.** Migrating the cloud server to a new host means re-provisioning K_root from a client; document this in the deployment guide (issue #23). Managed platforms without systemd degrade to platform-stored secrets and the settings screen must say so.
3. **Key in JS memory.** Cannot be zeroed reliably in Bun or Node. The threat model already excludes live memory access; do not let marketing copy claim otherwise.
4. **Derived artefacts drift.** Every future feature that stores something computed from bodies (embeddings, attachment text, quoted workflow outputs, notification previews) must go through the envelope. Worth a single `store_content()` seam in the server so it cannot be bypassed by accident (codebase-design ticket material).
5. **Attachment size and streaming.** Per-DEK chunked AES-GCM needs a defined chunk format; decide it before the attachments ticket lands.
6. **Client cache is plaintext SQLite.** The client holds the key, so encrypting the cache with SQLCipher adds little against a compromised device and a lot of build complexity (the Tauri SQL plugin manifest carries a `bundled-cipher` TODO). Recommend relying on OS disk encryption on the laptop for v1 and saying so.
7. **Agent search while away is bounded by decrypt-and-filter.** For very large mailboxes a workflow that needs full-body search across everything will be slow on the server. The mitigation is tags computed at ingest; if that proves insufficient, the fallback is an encrypted client-built index pushed to the server as an opaque blob for the server to decrypt into memory, which is more design than v1 needs.
8. **Provider-side plaintext.** None of this reduces what Google, Microsoft or Fastmail can read, nor what the AI provider sees. The privacy page should list these three parties explicitly so the at-rest story is not mistaken for end-to-end encryption.
9. **Bun FTS5 on macOS** is version-sensitive per the 2026 issue above; the sidecar should not host the search index. The Tauri client owns it.
