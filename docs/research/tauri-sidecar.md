# Tauri 2 for a bundled sidecar server and desktop integration

Research ticket: [#4](https://github.com/dopeCape/monday/issues/4). Part of the map in #1.
Researched 2026-09-16 against primary sources (Tauri 2 docs and source, tauri-apps plugin sources, Bun docs and issues, Apple, Microsoft, freedesktop and SQLite docs). Every claim carries a URL. Claims that could not be confirmed from a primary source are marked "unverified".

Versions on the day of research (crates.io API): `tauri` 2.11.5 (2026-09-15), `tauri-bundler` 2.9.4, `tauri-plugin-shell` 2.3.6, `tauri-plugin-updater` 2.11.0, `tauri-plugin-sql` 2.4.1, `tauri-plugin-notification` 2.4.0, `tauri-plugin-autostart` 2.5.1, `tauri-plugin-fs` 2.5.2, `tauri-plugin-stronghold` 2.3.2, `keyring` 4.2.0, `rusqlite` 0.40.2, `notify` 8.2.0, `auto-launch` 0.6.0. Bun 1.4.2 (2026-09-05, https://github.com/oven-sh/bun/releases). Tauri 3.0.0-alpha.0 and alpha.1 were published on 2026-09-13 and 2026-09-15 (https://github.com/tauri-apps/tauri/releases); they are alphas and are not considered here beyond the pinning note in the risks.

## Summary and recommendation

monday can ship the Bun + Hono server as a Tauri sidecar on all three platforms. Nothing in the ticket is blocked. The shape that falls out of the sources:

1. **Sidecar.** `bun build --compile --target=<bun-target>` once per platform, rename to the Rust target triple, list it under `bundle.externalBin`. Spawn it from Rust in `setup` with `tauri-plugin-shell`'s `sidecar()`, keep the `CommandChild` in managed state, kill it on `RunEvent::ExitRequested` and `RunEvent::Exit`. The shell plugin already kills direct children on a normal exit, but nothing handles a force-quit or crash of the parent on any OS, so the Bun process must watch its own parent (stdin EOF or parent pid poll) and exit on its own.
2. **Port discovery.** The Rust side picks a free loopback port, passes it plus a per-launch bearer token to the sidecar through argv and env, and the sidecar binds `127.0.0.1` only. TCP loopback is the only transport that is uniform on all three platforms; Bun's unix sockets do not exist on Windows and its named pipe support is partial. The webview talks to the sidecar with `fetch` and WebSocket, which needs `http://127.0.0.1:*` and `ws://127.0.0.1:*` in the CSP `connect-src`. `tauri-plugin-localhost` is not needed and is explicitly discouraged by its own README.
3. **Secrets.** Wrap the `keyring` crate (v4, default `v1` feature set) in a handful of Rust commands. OAuth refresh tokens and the user-held key never cross the IPC boundary; Rust does the refresh. Stronghold is a password-encrypted vault file, not the OS keychain, and its engine has had no release since May 2024. `tauri-plugin-store` is plaintext JSON. There is no official keyring plugin; the community ones are single-maintainer and mostly stale. Linux is the weak platform (needs a running Secret Service), so ship a fallback path.
4. **Config watch.** Build the path as `config_dir()/monday/monday.toml`, not `app_config_dir()` (which would be `~/.config/com.monday`). Watch the parent directory from Rust with `notify-debouncer-full` and emit a Tauri event; do not watch the file itself, because editors that save by rename lose an inotify watch on the file. No webview fs scope is then required.
5. **Autostart.** `tauri-plugin-autostart` is fine on Windows (HKCU Run) and Linux deb/rpm (XDG autostart). It is fragile for AppImage (absolute path baked in), broken for Flatpak (needs the Background portal), and weakest on macOS (legacy LaunchAgent plist or AppleScript login item rather than `SMAppService`). Use `MacosLauncher::AppleScript` so the user sees an "Open at Login" entry.
6. **Notifications.** `tauri-plugin-notification` works for plain banners on all three. Desktop click callbacks do not exist on any platform (open since 2022), Windows toasts only work for an installed app, and macOS notifications only work from a bundled `.app` (dev builds send as Terminal). Accept banners without click actions for v1 and track `user-notify` as the successor crate.
7. **Updater and signing.** Use `tauri-plugin-updater` with a minisign key held in CI secrets. In-place updates cover AppImage, `.app.tar.gz`, NSIS and MSI; plugin 2.11.0 also added deb and rpm installs through `pkexec`. Disable the updater in Flatpak, AUR and Snap builds. macOS needs the Apple Developer Program (99 USD per year) for Developer ID plus notarization; the bundler signs sidecars on macOS and applies the same entitlements file to every binary, so the Bun JIT entitlements land on the main binary too. On Windows the bundler does **not** sign external binaries, so the Bun exe must be signed before `tauri build` (possible since Bun 1.2.19). Azure Artifact Signing accepts individual developers only in the US or Canada; otherwise an OV certificate. Linux has no meaningful code signing beyond the updater signature.
8. **SQLite.** Use a Rust command layer over `rusqlite` (`bundled` plus `fts5`) for the client cache, not `tauri-plugin-sql`. The plugin runs every statement on a pooled `sqlx` connection, so `BEGIN`/`COMMIT` from JS is not guaranteed to hit the same connection (open issue since January 2024), results are untyped JSON, and there is no pragma or extension control. Return big lists through `tauri::ipc::Response` (raw bytes) or a `Channel`, and page the mail list. The sidecar keeps Postgres; it does not share the SQLite file.

Weakest platform per capability, in one line each: sidecar lifecycle, Windows; Bun compile and signing, Windows (macOS second); port discovery, none; secrets, Linux; config watch, Windows (macOS close); autostart, macOS; notifications, macOS (Windows close); updater, Linux (packaging fragmentation); code signing, Windows (cost and eligibility) with macOS a close second (mandatory paid program); SQLite from the webview, unclear until benchmarked, with the IPC delivery path differing on macOS.

## 1. Sidecar mechanism: `bundle.externalBin`

Sources: https://v2.tauri.app/develop/sidecar/, https://v2.tauri.app/reference/config/#externalbin, bundler source https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/settings.rs.

- Config: `"bundle": { "externalBin": ["binaries/server"] }`, relative to `src-tauri/tauri.conf.json`. Tauri looks for `binary-name{-target-triple}{.system-extension}`, so the files are `binaries/server-x86_64-unknown-linux-gnu`, `binaries/server-aarch64-apple-darwin`, `binaries/server-x86_64-pc-windows-msvc.exe` and so on. "Don't forget to provide binaries for all targeted platforms."
- Find the triple with `rustc --print host-tuple` (older toolchains: `rustc -Vv | grep host`). The Node.js sidecar guide (https://v2.tauri.app/learn/sidecar-nodejs/) does exactly this in a rename script, which is the template for a Bun rename script.
- The bundler strips the `-{target}` suffix on copy (`.replace(&format!("-{}", self.target), "")` in `Settings::copy_binaries`), so at runtime the file is `server` or `server.exe` next to the main executable.
- Where it lands: macOS `Contents/MacOS/`; `.deb` `usr/bin`; AppImage reuses the deb data dir so `usr/bin` inside the AppDir; NSIS `$INSTDIR` next to the main exe; MSI via a WiX fragment (id `Bin_<name>`, per the 1.0.4 bundler changelog, not re-verified in v2 source); RPM unverified but expected to match deb.
- Signing of the sidecar by the bundler:
  - macOS: every external binary is a `SignTarget` and is signed individually before the `.app`, "per apple, signing must be done inside out" (https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/macos/app.rs). `sign.rs` calls `keychain.sign(path, entitlements, is_an_executable && hardened_runtime)`, that is `codesign --options runtime` with the single `bundle.macOS.entitlements` file applied to all targets (https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-macos-sign/src/keychain.rs). No `--deep`. There is no per-binary entitlements option.
  - Windows: `generate_binaries_data` in both the NSIS and MSI bundlers copies external binaries without calling `try_sign`; the bundler signs NSIS plugin DLLs, WiX extension DLLs, resources with `.exe`/`.dll` extensions, and the installer (https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/nsis/mod.rs, https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/msi/mod.rs, https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-bundler/src/bundle/windows/sign.rs). Sign the Bun exe yourself before `tauri build`.
  - Linux: nothing to sign (see section 9).

Verdict: Linux works; macOS works and signs the sidecar; Windows works but needs `.exe` and manual sidecar signing. Weakest: Windows.

## 2. Spawning, permissions, lifecycle, console window

Sources: https://v2.tauri.app/develop/sidecar/, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/lib.rs, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/src/process/mod.rs, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/shell/permissions/autogenerated/reference.md, https://docs.rs/tauri/latest/tauri/enum.RunEvent.html.

- Rust: `app.shell().sidecar("server")?.args([..]).env(k, v).spawn()` returns `(Receiver<CommandEvent>, CommandChild)`. Events: `Stdout(Vec<u8>)`, `Stderr`, `Error`, `Terminated`. `CommandChild` has `write`, `kill(self)`, `pid()`. Pass only the file name on the Rust side, not `binaries/server`.
- JS: `Command.sidecar('binaries/server', args, { cwd, env })`, `spawn()`, `child.kill()`, `command.stdout.on('data', ..)`. Permissions: `shell:allow-spawn` for `spawn()`, `shell:allow-execute` for `execute()`, `shell:allow-kill`; scope entry `{ "name": "binaries/server", "sidecar": true, "args": [...] }`. Rust-side calls through `ShellExt::shell()` are not scope-validated since shell plugin 2.2.1. Recommendation: spawn from Rust only and grant the webview no shell permission at all.
- `tauri-plugin-process` is only `exit()` and `relaunch()` (https://v2.tauri.app/plugin/process/). `tauri::process` in core has only `current_binary` and `restart`; `tauri::api::process::Command` was removed in 2.0 (https://v2.tauri.app/start/migrate/from-tauri-1/).
- Does Tauri kill sidecars on exit? Only on a normal exit, and only the direct child. The shell plugin registers `on_event(|app, event| if let RunEvent::Exit = event { ... for child in children { child.kill() } })` (lib.rs lines 132 to 142). `kill()` is the direct child only; there is no process group, `PDEATHSIG` or Windows Job Object. A parent crash, `SIGKILL` or Force Quit runs no `RunEvent::Exit`, so the sidecar is orphaned on every OS. Related: https://github.com/tauri-apps/tauri/issues/4949 (children cannot be killed on Windows, closed not planned), https://github.com/tauri-apps/plugins-workspace/issues/3062 (sidecar lifecycle plugin request, open since 2025-10).
- Recommended pattern (maintainer answers in https://github.com/tauri-apps/tauri/discussions/3273 and https://github.com/tauri-apps/tauri/discussions/5504): spawn in `setup`, store `Arc<Mutex<Option<CommandChild>>>`, on `RunEvent::ExitRequested { .. } | RunEvent::Exit` take and kill it. Bun is a single process that statically links SQLite, so a direct-child kill is enough; add a parent watchdog inside the Bun server for the force-quit case (this is our design, not something Tauri offers).
- Upgrades on Windows: the NSIS installer kills the main exe but not the sidecar; https://github.com/tauri-apps/tauri/issues/9950 was fixed by PR #14479 (Restart Manager, merged 2026-09-15) which is not yet in a published `tauri-bundler` (2.9.4).
- Windows console: the shell plugin always sets `CREATE_NO_WINDOW` (`0x0800_0000`) on spawned commands (process/mod.rs). There is no public `creation_flags` option (https://github.com/tauri-apps/plugins-workspace/issues/2135, open). Bun also offers `--windows-hide-console` at compile time.

Verdict: Linux fine; macOS fine (Cmd+Q runs the exit path, Force Quit orphans); Windows weakest (no tree kill, hidden console only through the plugin's hard-coded flag, NSIS upgrade fix unreleased).

## 3. Port discovery and the localhost boundary

Sources: https://v2.tauri.app/develop/sidecar/, https://docs.rs/tauri-plugin-shell/latest/tauri_plugin_shell/process/struct.Command.html, https://github.com/tauri-apps/plugins-workspace/tree/v2/plugins/localhost, https://bun.sh/docs/api/http, https://v2.tauri.app/security/csp/.

- Tauri prescribes nothing. The verified primitives are argv (`.args()`), env (`.env()`, `.envs()`) and line-mode stdout (`CommandEvent::Stdout`, or `set_raw_out(true)` for raw bytes). Both patterns work: parent picks a free port and passes `--port N` (Tauri's own localhost plugin README uses `portpicker::pick_unused_port()`), or the sidecar binds `port: 0` and prints the port; Bun's `Bun.serve({ port: 0 })` exposes `server.port` and `server.url`.
- Recommendation: parent picks the port and also generates a random bearer token passed by env; the sidecar binds `hostname: "127.0.0.1"` (Bun's default hostname is `0.0.0.0`, which would expose the server on the LAN) and rejects requests without the token. Bun's default `idleTimeout` is 10 seconds, which matters for long-polling or streaming responses; set it explicitly.
- Unix sockets and named pipes: `Bun.serve({ unix })` exists on Linux and macOS (with abstract sockets on Linux). Windows named pipes were added for `node:net` (https://github.com/oven-sh/bun/issues/13042, closed by PR #13838) but `node:http` cannot listen on a named pipe (https://github.com/oven-sh/bun/issues/24682) and `Bun.serve` docs do not mention Windows. Not portable enough; use TCP loopback.
- `tauri-plugin-localhost` serves the *frontend* over localhost instead of the custom protocol and its README says it "brings considerable security risks and you should only use it if you know what you are doing." It is not needed for talking to a sidecar.
- CSP: Tauri's example `connect-src` is `ipc: http://ipc.localhost`; add `http://127.0.0.1:*` and `ws://127.0.0.1:*` to it. Use the IP literal rather than `localhost` so a resolver that returns `::1` cannot bypass a v4-only bind.

Verdict: all three fine over TCP loopback. Weakest: none (Windows only if sockets were wanted).

## 4. Bun `bun build --compile`

Sources: https://bun.sh/docs/bundler/executables, https://bun.sh/docs/api/sqlite, https://bun.sh/guides/runtime/codesign-macos-executable, https://bun.sh/blog/bun-v1.2.19, https://bun.sh/blog/bun-v1.3.10, https://bun.sh/blog/bun-v1.4, https://bun.sh/docs/installation.

- Targets: `bun-linux-x64`, `bun-linux-arm64`, `bun-linux-x64-musl`, `bun-linux-arm64-musl`, `bun-darwin-x64`, `bun-darwin-arm64`, `bun-windows-x64`, `bun-windows-arm64` (added in 1.3.10, 2026-02-26). `-baseline` and `-modern` suffixes are accepted for compatibility but resolve to the same binary; x64 selects AVX2/AVX-512 paths at runtime. Cross-compilation from any host is supported with `--target`.
- glibc: "Bun's glibc binaries require glibc 2.17 or newer"; use the musl target for older or musl distributions.
- Windows flags: `--windows-hide-console`, `--windows-icon`, `--windows-title` and friends; "Except for `hideConsole`, you can't use these flags when cross-compiling because they depend on Windows APIs." So icon and version resources need a Windows build host (or post-processing).
- `--bytecode` (ESM supported since 1.4), `--minify`, `--sourcemap` (embedded, zstd). Workers must be listed as extra entrypoints. N-API addons can be embedded but there are Windows crash reports (https://github.com/oven-sh/bun/issues/23771); avoid native addons in the sidecar.
- `bun:sqlite` works under `--compile`: "Linux and Windows: Bun statically links its own SQLite build"; "macOS: Bun uses the system-provided SQLite", which does not support `loadExtension` unless `Database.setCustomSQLite(path)` points at a Homebrew or bundled dylib.
- Size: Bun 1.4 runtime binaries are about 77 MB (Linux x64), 85 MB (Windows x64), macOS about 1 MB larger; expect roughly 75 to 90 MB per platform for the sidecar plus the bundled app. Bun's docs say "Bun's binary is still way too big and we need to make it smaller."
- macOS signing: supported since Bun 1.2.4 with an entitlements file containing `com.apple.security.cs.allow-jit`, `allow-unsigned-executable-memory`, `disable-executable-page-protection`, `allow-dyld-environment-variables`, `disable-library-validation`. Notarization is not mentioned in Bun docs (unverified whether Apple accepts these entitlements at notarization; they are standard hardened-runtime exceptions, so probably yes). Signing regressions in 1.3.12 and 1.3.13 (https://github.com/oven-sh/bun/issues/29361, https://github.com/oven-sh/bun/issues/32159, macOS 27 SIGKILL at launch) were fixed by 1.4; require Bun 1.4.2 or newer.
- Windows Authenticode: since 1.2.19 "Bun now embeds the bundled source code and assets into a dedicated `.bun` section within the PE ... allowing it to be signed with tools like `signtool.exe` without invalidating the signature." Before that the appended trailer broke signatures.

Verdict: Linux strongest; macOS fine with Bun 1.4.2 or newer plus entitlements, and no SQLite extensions; Windows weakest (resources not cross-compilable, N-API reports, manual signing).

## 5. Secrets in the OS keychain

Sources: https://v2.tauri.app/plugin/stronghold/, https://crates.io/crates/iota_stronghold, https://github.com/open-source-cooperative/keyring-rs, https://docs.rs/keyring/latest/keyring/v1/index.html, https://docs.rs/apple-native-keyring-store/latest/apple_native_keyring_store/, https://docs.rs/windows-native-keyring-store/latest/windows_native_keyring_store/, https://docs.rs/dbus-secret-service-keyring-store/latest/dbus_secret_service_keyring_store/, https://docs.rs/linux-keyutils-keyring-store/latest/linux_keyutils_keyring_store/, https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw, https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains, https://developer.apple.com/documentation/security/access-control-lists, https://docs.flatpak.org/en/latest/sandbox-permissions.html, https://v2.tauri.app/plugin/store/.

- Stronghold: an IOTA Stronghold encrypted vault file (`vault.hold` plus salt) with an argon2-derived key. It is not the OS keychain, so the vault password must itself be stored somewhere. `iota_stronghold` last released 2.1.0 on 2024-05-13; the repo is not archived but last pushed 2025-04-23. Not recommended for tokens.
- `keyring` 4.2.0: API moved to `keyring-core`, backends are separate store crates; `keyring = "4"` with the default `v1` feature selects macOS Keychain (file-based login keychain, `security-framework`), Windows Credential Manager, and Linux Secret Service over zbus, and sets the default store. Otherwise pick stores explicitly and call `keyring_core::set_default_store` at startup. v3 (`keyring = "3"`) has no default features and requires `apple-native`, `windows-native`, `sync-secret-service` and so on.
- Linux: needs a running Secret Service (gnome-keyring or KWallet); "known issues with getting dbus and secret-service and the gnome keyring to work properly in headless environments"; no default collection under WSL; each call is an IPC round trip of "tens if not hundreds of milliseconds". The keyutils store is in-memory and "will not persist across reboots". Flatpak needs a D-Bus talk permission for the secrets service (`--talk-name=org.freedesktop.secrets` is what Flathub manifests use; not stated in official Flatpak docs) and the Secret portal only hands out a per-app secret for encrypting local data.
- Windows: generic credentials, `CredentialBlobSize` at most 2560 bytes, so store one credential per token, never a JSON blob of all tokens.
- macOS: the file-based keychain uses ACLs of trusted apps; an untrusted or altered app triggers the "wants to use your confidential information" prompt. Apple's TN3137 says the trusted-app record checks that the app "hasn't been altered", so unsigned or ad-hoc rebuilds re-prompt on every rebuild (inference from TN3137 plus the ACL docs, not stated verbatim). The Data Protection keychain (`protected` feature) needs entitlements from a provisioning profile.
- No official Tauri keyring plugin in plugins-workspace. Community: `tauri-plugin-keyring` 0.1.0 (2024-12, keyring 3.6.1, Tauri 2.1.0, untouched since 2025-01), `charlesportwoodii/tauri-plugin-keyring` 0.2.1 (keyring-core 1.0, last push 2026-06, 6 stars), `tauri-plugin-keyring-store` 0.2.0, `tauri-plugin-secure-storage` 1.5.0. All single-maintainer.
- `tauri-plugin-store` writes `serde_json::to_vec` to a file under `AppData` with no encryption. Unsuitable for secrets.

Verdict: Windows strong; macOS good once signed with a stable Developer ID; Linux weakest (daemon dependency, latency, Flatpak permission, non-persistent fallback). Plan a "no keyring available" path: re-auth on launch with keyutils, or an explicit user-chosen encrypted file.

## 6. Config file watching and paths

Sources: https://v2.tauri.app/plugin/file-system/, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/fs/src/watcher.rs, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/fs/permissions/autogenerated/reference.md, https://docs.rs/notify/latest/notify/, https://github.com/notify-rs/notify/blob/main/notify/src/inotify.rs, https://github.com/notify-rs/notify/blob/main/notify/src/windows.rs, https://github.com/notify-rs/notify/blob/main/notify/src/fsevent.rs, https://docs.rs/notify-debouncer-full/latest/notify_debouncer_full/, https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html, https://docs.rs/tauri/latest/tauri/path/enum.BaseDirectory.html, https://specifications.freedesktop.org/basedir/latest/, https://docs.flatpak.org/en/latest/sandbox-permissions.html.

- Paths: `PathResolver::config_dir()` is `$XDG_CONFIG_HOME` or `~/.config` on Linux, `~/Library/Application Support` on macOS, `FOLDERID_RoamingAppData` on Windows. `app_config_dir()` is `config_dir/<identifier>`, so with `com.monday` it would be `~/.config/com.monday`. To get `~/.config/monday/monday.toml` use `app.path().config_dir()?.join("monday/monday.toml")`, which yields `~/Library/Application Support/monday/monday.toml` on macOS and `%APPDATA%\monday\monday.toml` on Windows. Under Flatpak `$XDG_CONFIG_HOME` is `~/.var/app/<id>/config`, so the same code lands at `~/.var/app/<id>/config/monday/monday.toml` with no change.
- `tauri-plugin-fs` watch: `watch` (debounced, `delayMs`) and `watchImmediate`, `recursive` option, cargo feature `watch` which pulls `notify = "8"` and `notify-debouncer-full = "0.6"`. Permissions `fs:allow-watch` and `fs:allow-unwatch` plus a scope such as `{ "path": "$CONFIG/monday/**" }`; `$CONFIG` and `$APPCONFIG` are valid scope variables, JS `BaseDirectory.Config = 3`. The plugin does not expose notify's `Config` (no fsevent latency or symlink settings).
- Editor rename-over: notify docs say editors differ ("Some truncate the file on save, some create a new one and replace the old one") and that deletions of a watched path require watching its parent. In the inotify backend a watch on a file follows the inode, so a rename-over ends the watch (`DELETE_SELF`, `MOVE_SELF`, then `IGNORED`). Windows already emulates file watches by watching the parent directory. So: watch `$CONFIG/monday` non-recursively, filter events whose path ends in `monday.toml`, and debounce 300 to 500 ms so the temp-write plus rename becomes one event.
- Backends: inotify (Linux), FSEvents (macOS, file-level events, latency window, "some events cannot be observed easily when trying to follow files that do not belong to you"), `ReadDirectoryChangesW` (Windows, 16 KiB buffer, renames as two events; events can fire while the writer still holds the file, which is a well-known property but not stated verbatim in notify docs; retry the read on parse failure).
- Recommendation: do the watching in Rust with `notify-debouncer-full` directly and emit a Tauri event with the parsed config. Then the webview needs no fs permission at all, and the same watcher can also feed the sidecar over its API.

Verdict: Linux strong (watch the directory); macOS good (coalesced); Windows weakest by a small margin (parent emulation, early events). No blocker anywhere.

## 7. Autostart

Sources: https://v2.tauri.app/plugin/autostart/, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/autostart/src/lib.rs, https://docs.rs/auto-launch/latest/auto_launch/, https://github.com/zzzgydi/auto-launch (linux.rs, macos.rs, windows.rs), https://specifications.freedesktop.org/autostart/latest/, https://developer.apple.com/documentation/servicemanagement/smappservice, https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Background.html, https://github.com/tauri-apps/plugins-workspace/issues/634, https://github.com/tauri-apps/plugins-workspace/issues/771, https://github.com/tauri-apps/plugins-workspace/issues/3166.

- Plugin 2.5.1 wraps `auto-launch = "0.5"` (upstream is 0.6.0, which adds a systemd mode the plugin does not use). Init: `tauri_plugin_autostart::init(MacosLauncher::LaunchAgent | AppleScript, Some(vec!["--minimized"]))`; JS `enable`, `disable`, `isEnabled`; permissions `autostart:allow-enable`, `autostart:allow-disable`, `autostart:allow-is-enabled`.
- Linux: writes `~/.config/autostart/<name>.desktop` with `Exec=<path> <args>` (literally `~/.config`, not `$XDG_CONFIG_HOME`). The plugin prefers the `APPIMAGE` env var for the path, so a moved or renamed AppImage leaves a dangling entry. Flatpak: the Exec line is wrong (`/app/bin/...` instead of `flatpak run <id>`, issue #3166 open) and the sanctioned route is the Background portal's `RequestBackground` with `autostart: true`, which `auto-launch` does not use.
- macOS: `LaunchAgent` writes `~/Library/LaunchAgents/<name>.plist` with `RunAtLoad` and the absolute app path (users see it under "Allow in the Background"); `AppleScript` creates a login item through System Events (users see it under "Open at Login"; only `--hidden` and `--minimized` are honoured as args). Neither uses `SMAppService`, which is Apple's supported API since macOS 13. Issue #634 (app not starting) is open with "help wanted".
- Windows: `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` plus the Task Manager `StartupApproved` override; one open report of the entry vanishing after a reboot (#771).

Verdict: Windows good; Linux good for deb/rpm, fragile for AppImage, broken for Flatpak; macOS weakest (legacy mechanisms, path baked in, open issue). Prefer `MacosLauncher::AppleScript`, ship signed and notarized, and test from `/Applications`.

## 8. Desktop notifications

Sources: https://v2.tauri.app/plugin/notification/, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/notification/Cargo.toml, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/notification/src/desktop.rs, https://github.com/hoodie/notify-rust, https://github.com/tauri-apps/winrt-notification, https://github.com/h4llow3En/mac-notification-sys, https://github.com/tauri-apps/plugins-workspace/issues/2150, https://github.com/tauri-apps/plugins-workspace/issues/2143.

- Plugin 2.4.0 uses `notify-rust 4.11` on all desktop targets, which in turn uses zbus D-Bus `org.freedesktop.Notifications` on Linux, `mac-notification-sys` on macOS and `tauri-winrt-notification` on Windows. Optional `windows7-compat` feature.
- API: JS `isPermissionGranted`, `requestPermission`, `sendNotification`; Rust `app.notification().builder().title(..).body(..).show()`. Permission `notification:default` grants all of it.
- Windows: the docs table says "Only works for installed apps. Shows powershell name & icon in development." The plugin sets `app_id(identifier)`, which needs a Start menu shortcut with that AppUserModelID, which the installer provides.
- macOS: the plugin calls `notify_rust::set_application("com.apple.Terminal")` in dev and the bundle identifier in release, so dev notifications need Terminal to have notification permission, and release notifications need a real `.app`. `mac-notification-sys` still uses the deprecated `NSUserNotification`. Issue #2143 (open, 2022 to 2026) collects reports of release builds whose banners go straight to Notification Center unless the alert style is changed to persistent.
- Click and action callbacks: "Actions" are documented as mobile-only. Issue #2150 (open since 2022-03) asks for a desktop onclick; the latest activity (January 2026) points at the community `user-notify` crate (https://crates.io/crates/user-notify) as the way forward. notify-rust's README says actions and `wait_for_action` are Linux-only, and the Tauri plugin does not expose them.
- Sounds and images: Linux full (hints, images, urgency); macOS a "small subset"; Windows limited, no hints or urgency.

Verdict: Linux strongest; Windows fine once installed; macOS weakest (bundle and signing dependent, deprecated API, delivery complaints). For v1: banners only, no click-to-focus; a click-to-focus feature would require the `user-notify` crate behind our own commands.

## 9. Updater and code signing per platform

Sources: https://v2.tauri.app/plugin/updater/, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/src/updater.rs, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/updater/CHANGELOG.md, https://v2.tauri.app/distribute/sign/macos/, https://v2.tauri.app/distribute/sign/windows/, https://v2.tauri.app/distribute/sign/linux/, https://v2.tauri.app/distribute/appimage/, https://v2.tauri.app/distribute/flatpak/, https://v2.tauri.app/distribute/aur/, https://v2.tauri.app/distribute/snapcraft/, https://v2.tauri.app/reference/config/, https://github.com/tauri-apps/tauri-action, https://developer.apple.com/programs/, https://developer.apple.com/support/compare-memberships/, https://learn.microsoft.com/en-us/azure/artifact-signing/overview, https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart.

Updater:

- Keys: `tauri signer generate -w ~/.tauri/monday.key` (minisign). Build with `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` in the environment (not `.env`). "Losing the private key means you cannot publish future updates to existing installations."
- Config: `bundle.createUpdaterArtifacts: true` (or `"v1Compatible"`), `plugins.updater.pubkey` (content, not a path), `plugins.updater.endpoints` with `{{current_version}}`, `{{target}}`, `{{arch}}`, `plugins.updater.windows.installMode` one of `passive`, `basicUi`, `quiet`. Static manifest keys: `version`, `notes`, `pub_date` (RFC 3339), `platforms.<linux-x86_64|darwin-aarch64|windows-x86_64>.{signature,url}`. Dynamic endpoints answer 204 for no update.
- Artifacts: Linux `monday.AppImage` plus `.sig`; macOS `monday.app.tar.gz` plus `.sig`; Windows `monday_x.y.z_x64-setup.exe` (NSIS) and `.msi` plus `.sig`. No `.nsis.zip` is produced in v2.
- Which installs can update in place: the docs page says AppImage, `.app.tar.gz`, NSIS and MSI, and that deb, rpm and Flatpak lack support. The plugin source is ahead of the docs: `installer_for_bundle_type` maps `Deb`, `Rpm`, `AppImage`, `Msi`, `Nsis`, `App`, and `install_deb` / `install_rpm` run `dpkg -i` / `rpm -U` through `pkexec`, then zenity or kdialog, then terminal `sudo`. Changelog 2.11.0: "Updater plugin now supports all bundle types: Deb, Rpm and AppImage for Linux; NSiS, MSI for Windows" (PR #2624). AppImage replacement needs write permission to the AppImage's own path (`APPIMAGE` env var). macOS extracts the tarball over the `.app`, escalating with AppleScript if the directory is not writable. Windows launches the installer with `/S`-style flags per `installMode`.
- Never updatable through the plugin: Flatpak, AUR, Snap (their own channels). Disable the updater in those builds (feature flag or config) so users are not offered a download they cannot apply.
- Architectures: AppImage for arm64 "can only be built on ARM devices or emulators" (linuxdeploy cannot cross-compile); GitHub's `ubuntu-24.04-arm` runners make that practical. `tauri-action` covers macOS `aarch64-apple-darwin` and `x86_64-apple-darwin`, Ubuntu, and Windows x64, and uploads `latest.json` (`uploadUpdaterJson`, `updaterJsonPreferNsis`); Windows arm64 is not covered in its README.

Signing:

- macOS: `bundle.macOS.signingIdentity` or `APPLE_SIGNING_IDENTITY`; CI uses `APPLE_CERTIFICATE` (base64 `.p12`) and `APPLE_CERTIFICATE_PASSWORD`; notarization with `APPLE_ID` + `APPLE_PASSWORD` + `APPLE_TEAM_ID` or `APPLE_API_ISSUER` + `APPLE_API_KEY` + `APPLE_API_KEY_PATH`. `bundle.macOS.hardenedRuntime` defaults to true; `bundle.macOS.entitlements` is one file applied to every signed binary including the sidecar (section 1), so the Bun JIT entitlements loosen the main binary too. Ad-hoc identity `"-"` "does not prevent macOS from requiring users to whitelist the installation in their Privacy & Security settings." Developer ID and notarization need the paid Apple Developer Program, 99 USD per year. `tauri-macos-sign` shells out to `/usr/bin/codesign` and `xcrun notarytool`, so macOS signing needs a macOS runner (the crate depends on `apple-codesign` only for certificate parsing).
- Windows: `bundle.windows.certificateThumbprint`, `digestAlgorithm` (default sha256), `timestampUrl`, `tsp`, or `bundle.windows.signCommand` with `%1` substituted by the file path (used for Azure Artifact Signing, HSM signtool, or any external signer, and for cross-compiling). The docs say "SmartScreen may show a warning to users when they download the app until the file and the certificate build enough reputation" and that EV certificates no longer get preferential SmartScreen treatment as of 2024; OV certificates are cheaper and available to individuals. Azure Trusted Signing was renamed Artifact Signing; Public Trust is available to organizations in the US, Canada, EU, UK, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway and Israel, and "Individual developers must be located in the United States or Canada", with identity validation through the Azure billing account and a government ID. The bundler signs the installer, NSIS/WiX plugin DLLs and `.exe`/`.dll` resources, but not `externalBin` (section 1); sign the Bun exe separately with the same `signCommand`.
- Linux: only optional GPG signing of the AppImage (`SIGN=1`, `SIGN_KEY`, `APPIMAGETOOL_SIGN_PASSPHRASE`, `APPIMAGETOOL_FORCE_SIGN`), and "AppImage does not validate the signature". No rpm signing keys in the config reference. Integrity for updates comes from the minisign `.sig`. Flatpak on Flathub must build offline from source with `cargo-sources.json` and `node-sources.json`; the Tauri guide also shows a manifest that unpacks a prebuilt `.deb`, but a 80 MB prebuilt Bun sidecar inside a Flathub build is a review risk (unverified against Flathub policy text). AUR and Snap both start from the `.deb`.

Verdict: updater is strongest on macOS and Windows (one format each); Linux weakest because only AppImage (and now deb/rpm with a root prompt) can self-update and the rest must be disabled per package. Code signing: Windows weakest (paid certificate or geography-gated Azure service, SmartScreen reputation, manual sidecar signing); macOS a close second (mandatory 99 USD program, notarization, shared entitlements); Linux has no signing to fail.

## 10. SQLite from the webview: SQL plugin vs Rust command layer

Sources: https://v2.tauri.app/plugin/sql/, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/Cargo.toml, https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/sql/src/wrapper.rs, https://github.com/tauri-apps/plugins-workspace/issues/886, https://docs.rs/crate/rusqlite/latest/features, https://v2.tauri.app/develop/calling-rust/, https://docs.rs/tauri/latest/tauri/ipc/struct.Response.html, https://github.com/tauri-apps/tauri/blob/dev/crates/tauri/src/ipc/protocol.rs, https://sqlite.org/wal.html, https://bun.sh/docs/api/sqlite.

- `tauri-plugin-sql` 2.4.1: `sqlx 0.8` with `sqlite` (runtime-tokio), `mysql`, `postgres` features. JS `Database.load('sqlite:cache.db')` (path relative to `BaseDirectory::AppConfig`), `execute`, `select`, `close`; `$1` placeholders; migrations via `Migration { version, description, sql, kind: MigrationKind::Up }` and `Builder::add_migrations`, run inside a transaction. Permissions: `sql:default` allows `load`, `select`, `close`; `sql:allow-execute` for writes. The plugin holds a `sqlx::Pool` per database and every `execute` and `select` borrows a pooled connection, so `BEGIN` and `COMMIT` issued as separate calls are not guaranteed to run on the same connection; that is exactly what issue #886 ("[sql] Add support for transactions", open since 2024-01-10, "help wanted") reports. No pragma, extension or connection-config API; results are untyped JSON arrays.
- Rust command layer: `rusqlite` 0.40.2 with features `bundled` (ships its own SQLite, so FTS5 and JSON are available consistently on all three OSes), `load_extension`, `serde_json`, `backup`, `hooks`, `functions`, `window`, `vtab`. Hold `Mutex<Connection>` (or a small pool) in `tauri::State`. Set `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout` at open. Full control over prepared statements, transactions and FTS5.
- IPC cost: commands return JSON by default; "This can slow down your application if you try to return a large data such as a file". `tauri::ipc::Response::new(Vec<u8>)` returns raw bytes without JSON, `tauri::ipc::Request` accepts a raw `ArrayBuffer` body, and `tauri::ipc::Channel<T>` streams chunks. In the IPC protocol source, JSON and raw responses are delivered through a channel response on Linux, Windows and Android, but through `responder_eval` (JavaScript evaluation with the payload inlined) on macOS and iOS (`protocol.rs` around lines 370 to 400), so macOS is the platform to benchmark for large lists. We did not run a benchmark.
- In-webview SQLite (WASM plus OPFS) was not evaluated for WebKitGTK or WKWebView support and is not needed given a Rust layer.
- Bun sidecar owning SQLite: `bun:sqlite` has a proper `transaction()` API and WAL, and works under `--compile`, but on macOS it uses the system SQLite without extensions. WAL across two processes works "on the same host computer" (sqlite.org/wal.html) so Rust and Bun could share a file, but nothing in the architecture needs that: the server's store is Postgres, and the client cache is the client's.

Ranking for a mail client with thousands of rows: (1) Rust command layer over rusqlite, paging the list and returning raw bytes for bulk payloads; (2) Bun sidecar over loopback HTTP, only if we later want one code path for cache and server; (3) `tauri-plugin-sql`, not recommended (no transactions, untyped rows, no pragmas).

Verdict: all three OSes work with rusqlite. Weakest: macOS for IPC delivery of large payloads until measured; Windows if two processes ever share the WAL file (file locking is stricter, so keep the cache single-owner).

## Open risks

1. **Force-quit orphans.** Nothing in Tauri kills a sidecar when the parent dies abnormally. The Bun server must implement a parent watchdog; without it, users accumulate stray `server` processes holding the loopback port and the config watcher.
2. **Sidecar size.** About 75 to 90 MB per platform before our code. AppImage and DMG grow accordingly; Flathub review of a prebuilt Bun binary is uncertain.
3. **Entitlements bleed on macOS.** One entitlements file is applied to every signed binary. Bun needs `allow-jit`, `allow-unsigned-executable-memory` and `disable-library-validation`; the main Tauri binary gets them too. Whether notarization accepts this for the Bun binary is unverified; test on the first signed build.
4. **Windows signing cost and eligibility.** Azure Artifact Signing accepts individuals only in the US or Canada; otherwise an OV certificate with a SmartScreen reputation ramp. The Bun exe is not signed by the bundler and must be signed in a separate step, on a Windows runner if `signtool` is used.
5. **Windows sidecar on upgrade.** NSIS kills the main exe but not the sidecar until bundler PR #14479 ships; until then the updater may fail to overwrite `server.exe` while it is running. Mitigation: the app kills the sidecar before calling `downloadAndInstall`.
6. **Linux keyring availability.** Minimal desktops, headless sessions, WSL and Flatpak without the D-Bus permission have no Secret Service. Design the re-auth fallback before onboarding is specified (#1 lists onboarding as unspecified).
7. **Notification click-to-focus is unsupported on desktop.** Any product decision that relies on clicking a notification to open a thread needs the `user-notify` crate behind our own commands, which is new (January 2026) and single-maintainer.
8. **macOS notifications and autostart depend on a signed, installed `.app`.** Neither can be tested from `tauri dev`; CI needs a signed build path early.
9. **Updater docs lag the code.** The deb/rpm update path (2.11.0) prompts for root through `pkexec`; decide whether that is acceptable or whether deb/rpm builds get the updater disabled like Flatpak, AUR and Snap.
10. **Tauri 3 alphas.** `tauri = "2"` and plugin `"2"` ranges will not resolve to 3.0.0-alpha, but plugin docs and the plugins-workspace `v2` branch will start moving; pin the 2.x line explicitly and read the v3 alpha notes (runtime chosen through the builder, `gtk3`/`gtk4` features, MSRV 1.95) before any upgrade.
11. **IPC throughput on macOS.** Large JSON responses are delivered by evaluating JavaScript on macOS. Benchmark a 5,000 row list through `invoke` on all three platforms before committing to page sizes.
12. **arm64 Linux.** AppImage for aarch64 must be built on an arm64 runner; add `ubuntu-24.04-arm` to the matrix if arm64 Linux is a v1 target.
