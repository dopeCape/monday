# A single-user Server authenticates devices by pairing, not passwords

A Cloud server has exactly one owner, so the question is device trust, not identity. We decided there is no password. The first device enters a one-time setup code the install produces; every later device is approved from an existing device with a short code, after which the Server mints a long-lived per-device token kept in the OS keychain. A passkey registered at setup, or a new setup code from the host, is the recovery path. The Sidecar accepts its own client on loopback with a loopback token; since ADR 0013 that token is stable across launches (kept in the keychain, read by the background service from a 0600 file) rather than per launch.

## Considered options

- A password set at install. Rejected: phishable, and ends up in a dotfile.
- Third-party OAuth login. Rejected: a self-hosted server should not depend on GitHub or Google to let its owner in.

## Consequences

- Devices are listed and revocable in Settings; revoking one invalidates its token and its Cache key.
- HTTPS is required off loopback. The container ships automatic certificates; self-signed is pinned on first pairing; plain HTTP is allowed only on private networks behind an explicit, persistent warning.
- The external MCP key path (ticket 29) is a second credential type on the same Server, never a reuse of a device token.

## Amendment: phones pair by an invite, over LAN access with a pinned certificate

monday gets Android and iOS apps (Tauri 2 mobile). A phone cannot run the Sidecar, so it is a Device of the user's monday: the desktop's background service (ADR 0013) or a Cloud server. Two things stood in the way. The Sidecar bound 127.0.0.1 only, and pairing went from the new Device to the old one (the new one shows a code, a paired one approves it), which on a phone means typing a Server address first.

We decided:

- **LAN access is a Setting, off by default.** `server.lan.enabled` makes the background service also listen on `0.0.0.0:server.lan.port` (47820) beside its loopback port; it is read when the service starts, so a change applies at its next restart, and the Devices panel says so (`restartNeeded` in `GET /service`'s `lan` and in each invite). The panel warns whatever the state: off, a phone cannot reach this computer; on, anyone on the network can reach the port and only paired Devices get in. The loopback token never opens it (a LAN peer is not loopback), and the LAN listener refuses `/pair/setup`, `/pair/start` and `/pair/claim`, so the six-digit setup code of a Sidecar with no Devices cannot be guessed from the network: a phone pairs by invite only.
- **TLS is self-signed and pinned (`server.lan.tls`, on by default).** The Sidecar makes an ECDSA P-256 certificate with Web Crypto and a few lines of DER (`src/crypto/self-signed.ts`, no openssl, no library), keeps it in `<data dir>/lan-tls/` (0600) so the fingerprint stays valid across restarts, and serves the LAN port with it through `Bun.serve`'s `tls`. Its SHA-256 (base64url) rides in the QR code; the phone accepts exactly that certificate on the private-network https addresses, and a public address keeps the system trust store. A webview cannot pin, so the phone's requests to a pinned address go through the platform's native fetch (`Platform.pinnedFetch`, a rustls verifier in the mobile host), which also keeps iOS App Transport Security out of it: ATS governs URLSession and WKWebView loads, not the native client. A WebSocket from the webview cannot pin either, so the Changes feed's transport ladder steps down to polling through the pinned fetch until the host offers a pinned socket. Turning TLS off is plain HTTP on the private network with a persistent warning (the rule above); on iOS that needs `NSAppTransportSecurity › NSAllowsLocalNetworking` in the app's Info.plist, and on Android cleartext allowed for private addresses in the network security config. Rejected: plain HTTP by default (mail and the Device token cross the Wi-Fi in the clear), and a certificate from a public CA (needs a public name for a laptop on a home network).
- **Phones pair by a Pairing invite.** A paired computer asks `POST /pair/invite`; the Server answers a one-time secret, an eight-character short code (Crockford base32, 40 bits), an expiry (`server.pairing.invite_minutes`, 10), the Server's name (`server.name`, else the computer's), its addresses (the LAN URLs while listening, then `server.public_url`) and the fingerprint, plus the QR code's text (`monday://pair?v=1&n=&u=&s=&c=&e=&f=`). The phone's Connect screen scans it (the barcode scanner plugin on Android and iOS; the camera reason is `strings.mobile.connect.camera_permission`) or takes the address and short code typed, and `POST /pair/redeem {secret | code, name, kind: "phone"}` mints its Device token, once: a second redemption is 409, a late one 410. A new invite cancels the open one, `DELETE /pair/invite` cancels all, and past `server.pairing.max_failures` wrong secrets or codes (10) every open invite is cancelled (429). The invite is a row of `pairing_codes` with `invite` set and confirmed from the start; `devices.kind` records computer or phone (migration 0037). The token goes to the platform's secret store (`server.remote`), and the phone's one Server is that target.
- **A phone never holds the root key.** The Server decrypts for its clients already; a phone works with what it serves. Phones are refused (403 `not_from_a_phone`) `POST /unlock`, `POST /lock`, `GET /recovery`, making or cancelling invites, approving codes, revoking Devices, `/upgrade/*` and `POST /service/stop`. A locked Server serves headers only and the phone says "Your monday is locked. Open it on your computer." Revoking the phone in the Devices panel deletes its token hash; its next request is 401 and it says it was signed out and must pair again (an open Changes feed socket is not cut; it only carries sequence numbers, and every read behind it is refused).
- **Development.** The Android emulator reaches the host's 127.0.0.1 as 10.0.2.2 and the iOS simulator as localhost, so the phone pairs with a running Sidecar on its loopback port (`sidecar.json`) without LAN access: type `http://10.0.2.2:<port>` and the short code. Plain http to a private or loopback address is accepted by the Connect screen; plain http to a public address is refused.
- **Deferred.** Push wake on phones (FCM, APNs): a phone syncs while it is open, through the Changes feed and its Cache per Workspace like the desktop. A pinned WebSocket in the mobile host. A phone joining a Cloud server's pairing from its own screen (the existing code flow covers it).
